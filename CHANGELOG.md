# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Added

- **A global outbound budget per third-party service** (`OUTBOUND_HOURLY_MAX`/`OUTBOUND_DAILY_MAX`, enforced in `trackedFetch` — the one point every outbound call in the app already passes through). Every other limit in the app is per-IP, which protects the app from any one client but not its *keys*: a Steam or ITAD quota doesn't care how many clients spent it, and neither does a retry loop in this app's own code. Past a ceiling, calls to that service fail as an ordinary upstream error (502, no new error path in any route) until the window rolls over — a far better failure than an exhausted or revoked key. Warned once per window rather than per refused call; refused calls aren't counted as requests they never made; current usage exposed as `budgets` on `GET /api/metrics`. Defaults sized well above normal traffic (5000/hour, 50000/day per service); `0` disables.

### Changed

- **Cache TTLs raised substantially now that every tier has a refresh button and states its own age.** Owned games/profile/wishlist 6 hours → **7 days**, store metadata/HLTB/tags/ProtonDB 60 → **180 days**, review scores 30 → **90 days**, Steam ID resolution 90 → **180 days**, game-name search 1 → **7 days**, news 6 hours → **1 day**, ITAD bundles/prices 2 → **4 hours**. Steam's store endpoints are rate-limited hard enough (`storeLimit`: ~4 req/s for the whole process) that a cold load of a large library takes minutes — which is exactly what these TTLs exist to avoid repeating, and shortening them buys freshness nobody asked for at that price. `default.env` now documents the refresh affordance backing each tier.
- **Cached misses no longer inherit those TTLs.** `setCache` takes a per-entry `ttlMs` (new nullable `expires` column), so a confirmed "this appid has no store page" or "this game has no Steam listing" lives 1 day (`MISS_CACHE_TTL_MINUTES`) rather than 180, and a failed vanity-URL resolve 1 hour (`RESOLVE_MISS_CACHE_TTL_MINUTES`) — long enough to stop a retried typo from hitting Steam every time, short enough that a newly-registered custom URL or a newly-listed game isn't wrong for months. `resolveSteamId` didn't cache failures at all before, so an unresolvable identifier cost an upstream `ResolveVanityURL` call on every single submission; it now caches `null` and re-throws the same client error. Cache schema version 7 — the cache wipes itself once on first start.
- **ITAD's identity mappings no longer expire every two hours along with its bundle and price data.** `itad-shop:`, `itad-appid:` and `itad-gid:` (the Steam shop id, and both directions of the gid↔appid resolution) shared the `bundles` cache tier on the reasoning that over-invalidating them was cheap. It isn't: nothing about them is time-sensitive — a game's Steam listing doesn't move — yet every 2 hours the whole mapping was thrown away and re-resolved from scratch on the next bundle open or wishlist price load. They get their own `cache_itad_ids` table and `ITAD_ID_CACHE_TTL_MINUTES` (180 days); `itad-bundles:`/`itad-price:` keep the short tier, where they belong. Shows up as a separate `itad-ids` group in `GET /api/metrics`' `cacheHits`/`cacheEntries`. Cache schema version 6 — the cache wipes itself once on first start.

### Fixed

- **A bare trailing `?` no longer sticks in the address bar once the last query param is removed.** Every URL-writing function wrote `` `?${reorderUrlParams(params)}` ``, which stringifies to a lone `?` when nothing is left — so closing a game panel on `/lists/owned?game=440`, or consuming a one-shot `?tv=` share link, left `/lists/owned?` in the URL (and in whatever the user copied or bookmarked from there). A new shared `urlWithParams(params, pathname?)` in `urlState.ts` returns the bare path in that case, and is what `setPanelParam`/`setLightboxParam`, `tableViewPrefs.ts`' restore/share/reset, and `ListRoute.tsx`' user-list view restore/reset all go through now; `urlWithoutAccountParam` — which already had this logic inline — reuses it too.
- **The bundle list had no refresh at all** — `GET /api/bundles` never read `refresh`, so a bundle that had just gone live (or just expired) was invisible until `BUNDLES_CACHE_TTL_MINUTES` ran out, with nothing the user could do. The browse page gets a ↻ next to "Include expired", `getBundles` gains `{ force }`, and `bundlesListLimit` stops skipping a forced request (a forced call is never a cache hit — the same rule the other limiters already apply). `GET /api/bundles/:id` deliberately gets no equivalent: `findBundleById` walks up to `BUNDLE_SEARCH_MAX_PAGES` pages, so forcing it would spend several upstream calls answering one deep link, and the list ↻ already covers a stale list.
- **"↻ Refresh prices" is back on the Wishlist and Bundle lists** — another affordance lost with `bundles.tsx`/`library.tsx`: `postPrices`' `force` option (and the `?refresh=1` handling behind it, all the way down to ITAD) survived the redesign with no caller, so a price that had gone stale in the server's cache could only be waited out. One page-level control rather than per-game, for the same reason as before: pricing is fetched as a single batched call for the whole list anyway. Re-prices whatever is currently loaded — no re-resolution and no re-streaming of ratings/HLTB/tags.
- **Nothing in the app could force fresh Steam data for an account, and nothing said how old the data on screen was.** The per-account "↻" went with `accountsBar.ts` in the list-centric redesign, so `fetchAccountOverview`/`fetchAccountWishlistItems`' `refresh` option had no caller and the server-side `refresh: true` path was unreachable from the UI. Home's Account card and the Owned/Wishlist lists now both carry an "Updated <when> · ↻ Refresh" line: `/api/common-games` and `/api/wishlist` report a new `fetchedAt` (the *oldest* cache write time across the accounts in the slot, via `lib/cache.js`'s new `getCachedAt` — oldest so the readout never claims data is fresher than its stalest part), and the ↻ re-runs the same load with `refresh: true`, forcing owned games, wishlist and profile past the server's cache in one click.
- **Dropped the presence dot and status label from Home's Account card.** `personastate`/`gameextrainfo` ride the `player:` cache entry, which sits on the library tier — a TTL now measured in weeks — so "Online"/"Playing X" was an assertion about a moment potentially long past, dressed up as live presence; the tooltip's "as of the last refresh" hedge doesn't rescue a green dot. The "Updated <when>" line above replaces it with a fact the app can actually stand behind, and one the user can act on. `toAccountPlayer` no longer maps those fields at all (and `ACCOUNT_STATE_LABELS` is gone), so nothing can quietly start rendering them again; the `.account-status*` CSS went with them.
- **The side panel's "↻ Refresh" button was gone since the list-centric redesign** — `panel.tsx` only renders it when the host passes `onRefresh`, and `AppShell.tsx`'s single `initPanel()` call never did, so `handlePanelRefresh` — the one way to force fresh rating/HLTB/store metadata/tags/news/price/DLC for a single game — was unreachable dead code. The shell now delegates it to the mounted route (`RouteHandlers.refreshGame`), which `ListRoute.tsx` registers: it re-fetches `/api/game-details/:appid?refresh=1` and applies the result to that game's store-backed row, falling back to the panel's plain object for a standalone lookup, exactly as the deleted `library.tsx` did. Registering it on `ListRoute` alone covers every case, since a game panel only ever opens there (`openGameGlobally` navigates to `/game/:appid`, which *is* that route).
- **`?u=` — exploring a specific Steam account by link — worked on no route at all after the list-centric redesign, and works on every route now.** `app.tsx`/`library.tsx` both read the param before they were deleted; nothing in the new SPA picked it back up, leaving `parseUrlState`'s slot parsing as dead code imported only by its own tests. A shared `/?u=alice` or `/lists/owned?u=alice` link silently showed *your* stored account instead (or "No account selected yet"), which also made the whole feature undiscoverable — nothing anywhere named the account a link was meant to open. Now: a new `accountOverride.ts` parses and resolves the param, `accountsStore.ts` holds the result as an in-memory override, and `getEffectiveCurrentAccount()` (override ?? stored) is what every reader of "the current account" calls — Home's account card, `/lists/owned`, `/lists/wishlist`, and the ownership status behind the panel's ✓/☆ badges and the "My Status" column (`myOwnership.ts`), whose badges therefore link back to *that* account's lists. Resolved once for the whole app by `AppShell.tsx` (an effect on the router's `location.search`, keyed on the identifiers so an unrelated `?game=`/`&shot=` write costs no re-resolve) rather than per route, and forwarded across in-app navigation via a new `withAccountParam` (the shell's nav links, Home's four fixed links, `ListRoute`'s bundle ‹/› and `/game/:appid` navigations, the panel's ownership badges) — the stored account is sticky by nature, so an override has to be made sticky by hand or clicking "Owned" quietly switches back to your own library. The panel's 🔗 copy-link stays clean on purpose: that's the game's canonical shareable address, not a place to bake in whichever account the sender was exploring.
  - It stays an **override, never an adoption**: the stored `currentAccount` isn't touched, and the account doesn't enter `recentAccounts` either. Home shows an "Exploring <account> from this link — your own current account is unchanged" note whose "Set as my current account" button is the only way it's ever adopted, at which point the now-redundant param is stripped. That strip goes through the router's `navigate(…, { replace: true })` rather than a bare `history.replaceState`, which is invisible to `@solidjs/router`'s location signal — found live: every forwarded href kept pointing at the account the URL no longer named.
  - `/lists/owned`/`/lists/wishlist` treat the link as authoritative: while it resolves — and if it fails, e.g. the private profile confirmed live — they show the override's own status text rather than loading the stored account in its place, which would both waste a full library fetch/stream on an account the URL didn't ask for and, on a failure, pass someone else's library off as the one the URL names.
  - An old Comparison-page link (`?u=alice&u=bob`) has no single-route equivalent anymore (a comparison is a dynamic list combining two accounts' Owned lists now), so the first slot is honored and the extras are reported — "This link lists 2 accounts to compare. Showing the first; …" — rather than silently unioned into one Family or dropped.
  - Also lands the first half of the redesign's open "live reactivity to `currentAccount`" item: `accountsStore.ts` now broadcasts `scg:account-changed` on every change to the effective account (same plain-module/`window`-event shape as `region.ts`'s `REGION_CHANGED_EVENT`, since it still has no Solid reactivity of its own), which is what lets a link resolving *after* a route mounted re-render Home's card, re-stream Owned/Wishlist in place, and re-stamp a bundle/recents/user list's ✓/☆ markers.
  - Verified live (Playwright) end-to-end against real accounts: Home, `/lists/owned`, `/lists/wishlist`, `/game/:appid`, an in-app navigation carrying the param, an ownership badge click landing on the right account's list, the multi-slot note, the adopt flow, a private-profile failure, and the no-account-at-all fallback. 30 new tests (`test/accountOverride.test.js`, plus `urlState`/`accountsStore`/`myOwnership` additions); full suite (683) and typecheck clean.

### Fixed

- **A game looked up while the "Recently Looked Up" list was already open never got its ✓/☆ ownership marker.** `ListRoute.tsx`'s ownership stamping ran once per load, over the row list that load itself built, so the one row `openOrAddRecentGame` prepends afterwards — which is *every* game looked up from the nav-bar search — rendered with a plain name even when it sat in the current account's own library or wishlist. Only the table was affected: the side panel's own badge re-checks ownership on every open (`panel.tsx`'s `loadOwnership`), which is why the panel could say "☆ On wishlist" while the row right behind it said nothing. Rather than add a stamping call to the one path that was missing it, stamping is now driven off the row list itself — `createEffect(on(() => rowsStore.length, …))`, with `stampMyOwnership` reading `rowsStore` live instead of taking a row array captured at load time — so any row added by any path is covered and the bug class doesn't come back the next time another one appears. Tracking the row *count* (via `on`, whose callback body runs untracked) keeps it off the detail stream's own per-row mutations, which never add or remove a row. A computed `value()` column reading `myOwnership.ts` directly was the other candidate and was rejected: `panel.tsx` needs `inLibrary`/`onWishlist` on plain `Game` objects for standalone lookups that were never rows, so the row fields survive either way and the computed column would have added a second parallel path to the same fact rather than replacing one — plus it would cost `myOwnership.ts` a solid-js dependency (its tests run outside Solid) and `gameColumns.ts` its purity (every column is currently testable against a bare object with no account state). Verified live (Playwright): looking up a wishlisted appid from Home now lands on `/game/:appid` with the row already colored and marked ☆.
- **A game looked up by bare appid or store URL was stuck reading `App <appid>` in the "Recently Looked Up" list, forever.** Nothing client-side knows a name in that case (`gameSearch.ts` passes `name: ''`), and `ListRoute.tsx` baked its `App <appid>` display placeholder straight into the row's own `name` — which then looked like a real name to `applyDetailsEvent`'s `if (!row.name)` guard, so the actual title never landed even once store metadata streamed in. The placeholder is presentational only now (`panel.tsx`'s title renders the fallback; `openStandaloneInPlace` no longer puts it in row data either), and three storage-side holes went with it: `addRecentGame` no longer lets an empty name/thumbnail overwrite one already resolved (looking a known game up again by its appid used to blank its stored name), `openStandaloneInPlace` persists `data.meta?.name` rather than whatever `game.name` had fallen back to, and a new `renameRecentGame` fills in an entry recorded nameless once its details stream in — updating in place rather than through `addRecentGame`, which would jump it to the front of the list on every visit even though nothing was looked up. Verified live (Playwright): a bare-appid lookup now reads "Project Zomboid" in the row, the tab title and the panel, and a pre-seeded nameless entry healed to "Team Fortress 2" on the next visit while keeping its place in the list. 6 new tests in `test/recentGames.test.js`.

The avatar/status-dot/private-badge/name/count rules in the same block stay — Home's Account card reuses them (see above) rather than restating the same treatment — with the block's comment repointed at that card and `.account-status`'s ring color moved off the deleted chip's `--bg3` onto the surface it now actually sits on. - The side panel's "✓ In library"/"☆ On wishlist" badges are no longer underlined — they became `<A>` links (to `/lists/owned`/`/lists/wishlist` for the same game) without a `text-decoration` reset, and an underline drawn through an 11px pill made the status itself harder to read. ### Fixed

- **`/bundles` no longer hides mature-flagged bundles** — `getBundles` (`lib/itad.js`) sent ITAD `mature=false`, which is that API's *include* switch, not an "only mature" filter. Nothing ever overrode it: `GET /api/bundles` never accepted a `mature` query param and `findBundleById` didn't pass one, so a default that read like a deliberate content policy was really just never exercised (it has been there since the original Bundles commit). It cost real bundles — measured live, `false` returned 33 of 35 active bundles, hiding a current Humble "Narrative Masterpieces Bundle" (Immortality, Eliza, Sunless Skies, The Pale Beyond, The Wreck…) not one of whose games carries ITAD's own per-game `mature` flag. This app has no age gate and gives mature games no special treatment in any other list, so there was nothing for a flag that coarse to gate. `mature=true` is now sent unconditionally and the parameter is gone rather than re-defaulted, so it can't drift back into an unexercised policy; `findBundleById` inherits it, which also fixes a deep link to a mature-flagged bundle 404ing (previously defended as unreachable because the app's own UI would never link to one — true, but only because the list was hiding them too). `mature` also leaves the `itad-bundles:` cache key: entries under the old six-segment shape are never read again and age out via the existing TTL, and can't collide with the new one since the segment that took `mature`'s place is always numeric. Two new tests in `test/itad.test.js` assert both call sites request `mature=true`; `test/server-ratelimit.test.js`'s pre-seeded key updated to the new shape. Verified live: `GET /api/bundles` now returns 35 bundles including both previously-hidden ones, and `GET /api/bundles/16538` (a mature-flagged bundle) resolves 200 instead of 404.
- `searchLimit` (`server.js`, backing `POST /api/common-games`/`POST /api/wishlist`) now skips an account whose resolve/player/games (or wishlist) data is already fully cached, mirroring the "cache hits don't count" rule `detailsLimit`/`gameSearchLimit`/the bundles limiters already apply — previously every request counted regardless of cache state, so switching between a handful of already-loaded accounts on Home could burn through `SEARCH_RATE_LIMIT_MAX` (default 10/minute) and 429 (`"Too many searches..."`) on requests that never touched Steam. A full `refresh: true` or a non-empty `refreshIds` (the accounts bar's per-account "↻") still always counts, since those force a real upstream call regardless of cache state. New test in `test/server-ratelimit.test.js` covering both routes against the shared budget. `default.env`'s `SEARCH_RATE_LIMIT_MAX` comment updated to match.
- Home's account resolve input (`HomeRoute.tsx`) now strips a pasted `steamcommunity.com/profiles/<id>` or `.../id/<vanity>` URL down to the bare identifier via `normalizeInput` (`utils.ts`) before sending it to `/api/common-games`/`/api/wishlist` — a regression from the list-centric redesign: `app.tsx` used to call this on every typed input before it was deleted, and nothing in the new SPA picked the call back up, so a pasted profile URL (vanity or numeric) was sent to the server verbatim and failed to resolve (the server only special-cases a bare 17-digit SteamID64; anything else, URL included, was passed straight through to Steam's `ResolveVanityURL`, which can't resolve a URL). `normalizeInput` itself was unchanged and still unit-tested throughout — only the call site was missing.
- `ListRoute.tsx`'s `kind === 'bundle'` load path now passes the current region (`resolveRegion(getStoredRegion())`) to `fetchBundleById` — another list-centric-redesign regression: `fetchBundleById` already supported a `country` option (still unit-tested in `test/bundleData.test.js`) and the browse list / per-game price lookup in the same file already passed it correctly (lines 61, 607, 676), but the bundle-detail fetch that actually populates Tier Price never did, so `server.js`'s `parseCountry` silently defaulted every bundle open to `US` regardless of the stored region preference — Tier Price showed USD no matter what region was set. Distinct from the documented, genuine "some shops only ever price in USD upstream regardless of country" caveat (see the Bundles section above) — that explains occasional per-shop USD, not every bundle showing USD unconditionally.

### Security

- Side panel (`public/panel.js`): a game's store `short_description` was interpolated directly into `panelBody.innerHTML` with no escaping (every other field in the same template went through `esc()`), and the panel opens for any appid with no ownership check — a malicious/compromised Steam listing's description could run arbitrary script in the app's origin the moment its panel opened. `esc()` alone wasn't the right fix since the field can legitimately contain literal HTML entities (e.g. "Baldur's Gate... Dungeons &amp; Dragons") that `esc()` would double-escape into visible `&amp;` text. It's now decoded via an inert `DOMParser` document (no scripts run, no resources load) and inserted with `textContent` instead.
- Side panel: the Official Website link and news-item links used only `esc()` on their `href`, which escapes HTML special characters but not the URL scheme — a `javascript:`/`data:` URL from a developer-supplied website field or a news item would have passed through untouched. Both now go through the same `/^https?:\/\//i` allowlist `accountsBar.js`/`app.js` already apply to profile URLs (`safeHref` in `panel.js`).
- `POST /api/game-details/stream`: unlike every sibling data-fetching route, this SSE batch endpoint had no rate limit and no cap on how many games one request could list — a single request could queue unbounded upstream Steam/HLTB/SteamSpy/ProtonDB calls and unbounded `db.sqlite` cache writes. It now shares `detailsLimit`'s per-minute budget and rejects a request above the new `STREAM_MAX_GAMES` cap (default 5000).
- `lib/steam.js`: the shared upstream-call semaphores (`storeLimit`/`spyLimit`/`protonLimit`) had no maximum queue depth — `createSemaphore` now takes a `maxQueue` (20000) as a coarse safety valve against unbounded queue growth, on top of the request-level bound above.
