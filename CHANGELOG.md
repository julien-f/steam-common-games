# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/).

## [Unreleased]

### Security

- Side panel (`public/panel.js`): a game's store `short_description` was interpolated directly into `panelBody.innerHTML` with no escaping (every other field in the same template went through `esc()`), and the panel opens for any appid with no ownership check — a malicious/compromised Steam listing's description could run arbitrary script in the app's origin the moment its panel opened. `esc()` alone wasn't the right fix since the field can legitimately contain literal HTML entities (e.g. "Baldur's Gate... Dungeons &amp; Dragons") that `esc()` would double-escape into visible `&amp;` text. It's now decoded via an inert `DOMParser` document (no scripts run, no resources load) and inserted with `textContent` instead.
- Side panel: the Official Website link and news-item links used only `esc()` on their `href`, which escapes HTML special characters but not the URL scheme — a `javascript:`/`data:` URL from a developer-supplied website field or a news item would have passed through untouched. Both now go through the same `/^https?:\/\//i` allowlist `accountsBar.js`/`app.js` already apply to profile URLs (`safeHref` in `panel.js`).
- `POST /api/game-details/stream`: unlike every sibling data-fetching route, this SSE batch endpoint had no rate limit and no cap on how many games one request could list — a single request could queue unbounded upstream Steam/HLTB/SteamSpy/ProtonDB calls and unbounded `db.sqlite` cache writes. It now shares `detailsLimit`'s per-minute budget and rejects a request above the new `STREAM_MAX_GAMES` cap (default 5000).
- `lib/steam.js`: the shared upstream-call semaphores (`storeLimit`/`spyLimit`/`protonLimit`) had no maximum queue depth — `createSemaphore` now takes a `maxQueue` (20000) as a coarse safety valve against unbounded queue growth, on top of the request-level bound above.

### Fixed

- `getSteamTags` (`lib/steam.js`): the cache key for a game's tags is now `tagids:{appid}` instead of reusing the old SteamSpy-era `tags:{appid}` key. That key's stored shape changed from a `{tagname: voteCount}` object (SteamSpy) to a `tagid[]` array (Steam's own tag ids, see the tags source swap above); a pre-existing `tags:` entry from before this change was read back by the new code as-is and crashed on `tagIds.slice is not a function` the first time an already-cached appid's tags were requested. An initial fix treated any non-array cached value as a miss, which handled that crash but missed a quieter case: a game with zero SteamSpy votes had cached a bare `[]` under the old key, indistinguishable by shape alone from a legitimate empty result under the new format — those games stayed permanently stuck showing no tags even once Steam's own data had some. Moving to a distinct key prefix sidesteps the ambiguity entirely; old `tags:` entries are never read again and age out on their own via the existing 60-day meta TTL sweep.
- Side panel (`public/panel.js`, shared by both pages): the News and Achievements sections used to render nothing at all when their fetch failed, looking identical to "this game genuinely has no news/achievements" instead of a failure worth noticing. Both now show an explicit "Couldn't load …" message when there's no data to fall back on (a failed *refresh* that still has stale data from an earlier successful load keeps showing that stale data instead, rather than replacing it with an error).
- Side panel: clicking a DLC entry's "Part of *Base Game*" link right back to the base game you just came from (or vice versa) used to push a duplicate consecutive entry onto the DLC-navigation history stack (`panelHistory`) instead of just going back — `navigateToGame` now collapses that case by popping the stack instead of growing it.
- Side panel (`public/panel.js`, shared by both pages): expanding a base game's DLC card no longer holds the whole card on its loading skeleton until *every* DLC entry has resolved — a franchise with a large DLC catalog (e.g. Stellaris, 30+ entries) could take a long time to show anything at all, since one slow/rate-limited entry blocked the rest from appearing even though most had already loaded. `loadDlc` now fills a `game.dlcPartial` slot as each entry resolves and re-renders immediately, so already-loaded entries appear right away with a "Loading N more…" line for what's still pending; a force-refresh seeds those slots from the previous complete list so the card doesn't visibly shrink back to empty while refreshing.
- Side panel (`public/panel.js`, shared by both pages): expanding or collapsing an HLTB/News/Achievements card (`collapsibleCard()`) no longer yanks the whole panel's scroll position back to the top. `renderPanelBody` rebuilds `#panel-hero` from scratch on every re-render, and `buildPanelHero()` unconditionally `scrollIntoView()`s the active filmstrip item — appropriate when actually opening the panel or paging the hero, but it fired just as eagerly on a re-render that had nothing to do with the hero, scrolling the reader back up to it. The panel body's scroll position is now snapshotted before re-rendering and restored after.
- Comparison page (`public/app.js`): a standalone "look up any game" lookup (no player loaded, or a game nobody in the comparison owns) now shows the Achievements section too, matching what the Library Explorer already did for its own no-player case — the section was silently never wired up on this page at all (`showAchievements` was never set on `initPanel`), so it just never appeared regardless of whether a game had achievements. A loaded comparison-group game still shows nothing here, same as before: unlike the Library Explorer's single player, a comparison group has no one well-defined account to fetch unlock progress for (a game can belong to several slots/Families at once), so per-account progress on this page remains a separate, not-yet-tackled piece of work — this fix only covers the list-only, no-progress case standalone lookups already support server-side (`steamids` is optional on `GET /api/achievements/:appid`).
- `getAppDetails` (`lib/steam.js`): a game's tag cloud / Categories & Genres columns could show the exact same pill twice — Steam's own store API sometimes lists two distinct category/genre ids that share an identical label (e.g. app 3357650 has separate ids for "DualShock Controller Support" and separate ids for "DualSense Controller Support", each pair rendering the same text). Since only the label is ever displayed, never the id, `genres`/`categories` are now deduped by description at the source rather than in every place that renders them.

### Changed

- `getSteamTags` (`lib/steam.js`) now requests up to 30 tags per game (was 20) and shows all of them — the 10-tag display cap inherited unchanged from the old SteamSpy-based code is gone.
- Game tags (`lib/steam.js`) now come from Steam's own store tag data instead of SteamSpy — `getSteamSpyTags` is replaced by `getSteamTags`, which calls the undocumented `IStoreBrowseService/GetItems` (per-app `tagids`, weight-ordered) and `ajaxgetstoretags` (tagid → name, fetched once and cached long-term as `tagnames:all`) endpoints. This matches what the store page itself, SteamDB, and IsThereAnyDeal show, and fixes games SteamSpy had sparse or no tag data for (e.g. niche/recent titles) showing no tags at all in the side panel despite having plenty on Steam. SteamSpy is no longer used anywhere in the app.
- Bumped `@vates/data-table-vanilla` from 0.8.0 to 0.9.0.
- Side panel (`public/panel.js`, shared by both pages): the game description now renders right under the glance grid, ahead of the tag cloud, instead of after it — it's the "what this game is" text and previously got buried under a wall of tag/genre/category chips. It, along with the tag cloud, now sits in the same bordered `.panel-card` box HLTB/News/Achievements already used, instead of being bare unboxed `<div>`s — the whole panel body now reads as one consistent stack of cards rather than two different visual systems glued together.
- Side panel: the Owners section (who in the loaded slot/library owns this game) now renders right after the description, ahead of the HLTB/News/Achievements collapsibles, instead of dead last below all three — on the comparison page in particular, "who owns this" is often the actual reason the panel was opened, and it used to be buried under sections most people never expand. The sticky sub-nav's button order already matched this (Owners listed first); only the actual section order changes to match it.
- Side panel: the Owners section now moved one step further, to right after the tag cloud instead of right after the description — grouping the two "what this game is" blocks (description, then tags/genres/categories/dev-publisher) together ahead of the "who has it" comparison-specific data, rather than splitting them apart. Also now sits in the same bordered `.panel-card` box every other content section uses (it was the one section still rendering as a bare unboxed `<div>`, inconsistent with the description/tag-cloud/HLTB/News/Achievements cards around it).
- Side panel: a DLC entry's "release date · DLC for *Base Game*" line is now one line instead of two stacked ones — this, combined with the "← Back to *Game*" line a DLC-navigation hop also adds above the title, used to make the sticky header (which stays pinned while the rest of the panel scrolls) noticeably tall for exactly that case.
- Side panel: the DLC card's expanded list is now sorted newest-released first, with not-yet-released entries surfaced above everything else — previously it rendered in whatever order Steam's own `meta.dlc` appid list happened to return, which isn't chronological. Not paginated — a base game with a very large catalog (e.g. Stellaris, Sims 4) still shows every resolved entry, just in a more useful order.
- Side panel: the sticky sub-nav (Overview/Owners/HLTB/News/Achievements) now highlights whichever section is actually scrolled into view (`updateSubnavScrollSpy` in `public/panel.js`), instead of being a static row of jump-links with no sense of "where am I" once a panel is long enough to scroll.
- Side panel: the Steam Workshop/Official Website icon-links are now tucked behind a single "⋯ More" toggle instead of each always showing its own icon — with both present (plus the always-there Store/ITAD/copy-link/refresh), the row ran to 6-7 icon buttons, wide enough to squeeze the title into a two-line wrap on a narrow panel (most visible on a DLC entry, which also carries a "← Back" line and a "release date · DLC for X" line above/beside the title). The row's width is now fixed regardless of how many of these a given game happens to have; the "⋯" button itself is only rendered at all when there's at least one to show.
- Side panel: dropped the standalone 📰 News icon-link that used to sit in the header as a fallback for whenever the News card had nothing to show — the card's own ↗ icon (once it renders) already covers the case that matters (linking to the exact same Steam news hub), and a game with confirmed zero official posts isn't worth a dedicated icon just to go check whether unrelated syndicated press showed up on the raw hub instead.

### Added

- Side panel: an All/Unlocked/Locked filter for the expanded Achievements list, so a game with a large achievement count (100+) doesn't force scrolling through everything just to find what's left to unlock. Only shown once real progress is loaded (filtering by achieved status is meaningless with nobody loaded, where nothing is ever marked achieved). The list is now also sorted once per fetch and cached rather than re-sorted on every render — any unrelated toggle elsewhere in the panel re-renders the whole body, which used to re-sort the full achievement list every time for no reason.
- Side panel: a 🔗 icon-link next to Store/IsThereAnyDeal copies a link straight back to this game (`?game=<appid>` on the current page, briefly flashing ✓ on success) — deliberately just the appid, not the full current URL with whatever `u=`/filters/sort/tab/view happen to be set from the search that led here, since sharing "check out this game" almost never means "reproduce my exact search too".

- Side panel (`public/panel.js`, shared by both pages): a new "DLC" card lists a base game's downloadable content — collapsed by default, same as HLTB/News/Achievements. The collapsed header's count comes straight from the base game's own store metadata (`meta.dlc`, a bare appid list Steam's `appdetails` response already includes for free); the full list — each entry's name and capsule image — is only resolved once the card is actually expanded. Each DLC appid is resolved through the exact same `GET /api/game-details/:appid` (and its existing `detailsLimit` rate limiter/cache/circuit-breaker) every other single-game lookup already uses, rather than a bespoke batch endpoint — a DLC appid isn't fundamentally different from any other appid the app looks up, so it isn't given its own rate-limit policy or an arbitrary cap on how many resolve at once; a franchise with a very large DLC catalog is subject to the same per-minute budget as any other burst of game lookups, same as rapidly opening that many panels by hand would be. A DLC entry that fails to resolve (delisted, or rate-limited under a large burst) is silently dropped from the list rather than shown as an error — the rest is still worth showing. Each entry is a real link (`<a href>`, so ctrl/cmd/shift-click and middle-click open it in a new tab the normal way) that, on a plain click, opens that DLC in the same panel instead — and the panel now remembers where you came from: a "← *Game Name*" button appears above the title while a DLC-navigation trail is in progress, popping back through however many hops were taken (DLC → DLC → …), reusing the exact same "open this appid" mechanism as the "look up any game" search box. An ordinary panel open (a table/row click, a search-box pick, prev/next/random) starts a fresh trail rather than inheriting whatever was there before. The card's expanded/collapsed state (like HLTB/News/Achievements) is remembered per appid for the rest of the session — navigating to a game whose DLC card was left expanded from an earlier visit (e.g. reached again via a DLC link or the "← Back" button) now correctly kicks off the fetch itself rather than rendering the card already open with nothing loaded and no click left to trigger it.
- Side panel: a game that is itself DLC now shows a "DLC for *Base Game*" link right under the title, the reverse of the DLC card above — same real-link/intercepted-click in-panel navigation (renamed from `navigateToDlc` to the more general `navigateToGame`, since it now backs both directions of this relationship), same "← Back" support. Backed by a new `fullgame` field on `extractAppDetails` (`lib/steam.js`) — Steam's `appdetails` response for a DLC app already includes `{appid, name}` pointing at its base game, for free on the same response, so no new upstream call. The base game's name is exposed alongside its appid purely to avoid a title flash while the link is up but not yet clicked — same trade-off already made for DLC entries and the "look up any game" search box; the real name is still always re-resolved from the base game's own metadata once you actually open it.
- Side panel: two new icon-links alongside the existing Steam Store/IsThereAnyDeal/News icons — a 🛠️ Steam Workshop link (shown whenever `meta.categories` includes "Steam Workshop", already-fetched data reused rather than a new call) and a 🌐 Official Website link (a new `website` field on `extractAppDetails`, present for plenty of games and absent for others, same free appdetails response).
- Library Explorer: the game detail side panel now has an "Achievements" section showing each game's full achievement list (name, description, icon) with unlocked/locked state and an overall N / total (%) count, for whichever account(s) are currently loaded. A merged Steam Family slot unions progress the same way owned games are unioned elsewhere — an achievement counts as unlocked for the group if any member has it. The section is collapsed by default and remembers whether you expanded it per game for the rest of the session, so a 40-100 item list doesn't dominate the panel for every game that has one. The summary and the list live in one bordered card (matching the glance grid's bold, color-coded-percentage chip look via the same `scoreColor` used for ratings) instead of a floating header above a separate stack of individually-boxed items — the list, once expanded, sits below a divider inside that same card, and its rows are separated by thin dividers rather than each being its own box. A ↗ icon next to the header links out to that account's own Steam achievements page. An unlocked achievement's card shows its unlock date on hover. A hidden achievement not yet unlocked shows "Hidden achievement" (name/description withheld, same as Steam's own profile) until clicked, which reveals it in place. Each achievement also shows its community-wide unlock percentage (e.g. "4.2%") — visible even while an achievement is still spoiler-hidden, since knowing how rare it is doesn't give away what it actually is. The list itself (names/descriptions/icons/rarity) is store metadata, not tied to any account, so it's shown even with no player loaded (e.g. a standalone "look up any game" lookup) — `steamids` on the endpoint is optional; the header shows "— · N total" instead of a percentage, and the expanded list reads "Load a player above to see who's unlocked what" instead of implying 0% progress. A new `playerCount` field on the response distinguishes "no player was asked about" from a player whose progress is genuinely unavailable (`private:true`, unchanged). New endpoint `GET /api/achievements/:appid?steamids=...` (steamids optional), backed by three new `lib/steam.js` functions: `getGameSchema` (achievement names/icons — store metadata, cached like rating/HLTB/tags), `getPlayerAchievements` (one account's unlock state per game — player progress, cached like owned games), and `getGlobalAchievementPercentages` (community-wide rarity per achievement, cached like the schema; a transient failure here degrades to "no rarity data" rather than breaking the rest of the panel). Comparison page unaffected — its groups have no single well-defined player to fetch progress for.
- Side panel redesign (`public/panel.js`, shared by both pages): a "glance strip" — a fixed 2×2 grid of SteamDB, Metacritic, HLTB, and Linux/Deck (ProtonDB) chips right under the title, each chip built from one shared template (a value, then a one-line caption) and each chip *is* the link to its source. This replaces the old Score/Linux-Steam-Deck/HLTB sections plus a separate "Links" list that duplicated the same four sources a second time. Title/release date/glance strip now stay visible (`position: sticky`) while the rest of the panel scrolls underneath. Tags/genres/categories/developer-publisher are merged into one pill cloud (`tagCloud()`) distinguished by a small colored dot + legend instead of four near-identical "uppercase title + pill row" sections. The nav bar (prev/next/random) is now pinned to the bottom of the panel on both desktop and mobile — previously it sat between the hero and the body, so reaching it on desktop meant scrolling back up past the hero every time.
- Side panel: the How Long To Beat breakdown and News sections now use the same collapsed-by-default "chip + expand-in-place" card the Achievements section already had (`collapsibleCard()` in `public/panel.js`, a small helper shared by all three) instead of always rendering their full content — a game with tags, HLTB, news, and achievements data no longer forces a long scroll just to see what's below the glance strip. Neither the HLTB nor the News chip has a headline number — HLTB has no single figure that isn't either an arbitrary pick among Main/Extra/Completionist or a plain repeat of the glance strip's own "All PlayStyles" chip just above, so it's a plain text teaser naming which categories the breakdown has instead (auto-expanding when `all` itself is missing, since then the breakdown is the only HLTB data the panel has at all); News dropped a "3 recent posts" count once it became clear the number never varies (the panel always shows every fetched headline, so a count added nothing you couldn't already see one click away). News' caption spells out "more on Steam" explicitly instead of leaving that to the header's ↗ icon's title tooltip alone, and now shows every headline the server fetched rather than truncating client-side further — a limit that existed only because the section used to always render inline and a longer list ate into the panel's visible height, which collapsing it by default made moot. `extractNews`' own cap (`lib/steam.js`) is raised from 5 to 20 to match — the upstream request already fetches `count=20`, so returning all of them (instead of throwing most away after already paying for the fetch) costs nothing extra; the panel comfortably shows the full 20 in its scrollable body once expanded. A new sticky sub-nav row (Overview / Owners / HLTB / News / Achievements, whichever are present) sits under the title and jumps straight to a section — shown only once there are at least two sections worth jumping to, so a game with nothing below the glance strip doesn't get a lone useless button.
- Side panel: the Achievements card's outbound ↗ link, previously silently dead (the server response never actually included the `steamUrl` field the frontend was already reading), now links to Steam's public per-game achievements page (`steamcommunity.com/stats/<appid>/achievements/`, no login/account needed) whenever no specific account is loaded (e.g. a standalone "look up any game" lookup) — a loaded account's own achievements page (set client-side in `public/library.js`) still takes precedence when one's available.
- Comparison page: the side panel's "Owned by" list (`buildOwnersHtml`, `public/app.js`) is now ordered by last played, most recent first (ties broken alphabetically), and each owner gets a playtime meter — a single-hue bar sized relative to the top playtime among that game's owners — as a secondary cue alongside the existing hours-played number, which stays the primary, always-visible value.

- Library Explorer: a new "Last Played" column showing the most recent time anyone in the loaded slot launched each game, sourced from `rtime_last_played` on Steam's `GetOwnedGames` response (already fetched for every game, just unused until now — no new upstream call). For a merged Steam Family slot this is the max across every account in the slot, not any one account's own timestamp. Shown as a plain date (e.g. "2026-07-01"), same convention as the Released/Added columns; blank means owned but never launched by anyone in the slot, and the column is dropped entirely from the Wishlist tab (wishlist games aren't owned, so there's nothing to have played). The comparison page's side panel "Owned by" tags gained the same per-account info (`· last played 2026-07-01`) next to existing playtime.
- Library Explorer: the Released column now colors an unreleased game's date/placeholder amber (reusing `scoreColor`'s existing mid-tier amber), so scanning the wishlist for what's still coming makes released vs. unreleased visible at a glance instead of requiring a close read of each date string. Backed by a new `comingSoon` field on `extractAppDetails` (`lib/steam.js`) carrying Steam's own `coming_soon` flag through to the client, rather than re-deriving release status by parsing the (sometimes unparseable, e.g. "Coming soon") date string.
- Side panel (`public/panel.js`, shared by both pages): a new "News" section shows up to 3 recent headlines (title, date, feed label) for the open game, each linking straight to the full post, plus a "More news →" link to that game's full Steam news hub. A new 📰 icon link next to the existing Steam Store/IsThereAnyDeal icons links to the news hub too, independent of whether any headlines loaded. `GetNewsForApp`'s raw response mixes the developer/publisher's own Community Announcements posts with syndicated third-party press coverage in whatever language that outlet publishes in, with no regard for the requester's locale — for some games that press can outnumber official posts 10:1 or more, dominating the most recent items entirely with untranslated foreign-language articles, and none of it actually matches what the store page's own News tab shows. Fixed with an undocumented `feeds=steam_community_announcements` query param that filters server-side to official posts only (verified directly against the live API) — `extractNews` (`lib/steam.js`) also keeps a `feedname` filter as cheap insurance in case that param is ever dropped or inconsistent for some app. Backed by a new `getGameNews` (`lib/steam.js`, wrapping the documented, key-less `ISteamNews/GetNewsForApp` endpoint) and a new dedicated `GET /api/game-news/:appid` route — deliberately its own endpoint rather than folded into `fetchGameDetails`/the SSE stream, since news has no table column and nothing to sort/filter on, so fetching it for every game in a whole loaded library/comparison would be pure waste for the (common) case of most panels never being opened. It's fetched lazily instead, once per game, only when that game's panel actually opens (`loadNews` in `panel.js`, same on-demand shape achievements already use), and refetched by the panel's "↻ Refresh" button alongside everything else. Cached under a new `news:` prefix with its own TTL (`NEWS_CACHE_TTL_MINUTES`, default 6 hours) — shorter than the 60-day store-metadata tier, since news/patch notes change far more often than a game's genres or screenshots.
- Cross-page navigation: index.html's header now has a "Library Explorer →" link (mirroring library.html's existing "← Comparison tool" back-link, both now sharing one `.header-nav-link` style in `style.css` instead of a page-scoped one-off). Each link is contextual — index.html's points at `/library.html?u=<ids>` for the single player/Family currently loaded (falling back to the bare link for a multi-player comparison, which the Library Explorer has no notion of), and library.html's points at `/?u=<ids>` for whoever's currently loaded there.
- Both pages now keep the browser tab title in sync with what's actually open: an open game's name takes over the title entirely (e.g. "Half-Life 2 — Steam Common Games" / "Half-Life 2 — Library Explorer"); with no panel open it falls back to the loaded player/comparison context (e.g. "alice, bob — Steam Common Games" or "alice's Wishlist — Library Explorer"); with nothing loaded at all, the original static title. Makes finding a specific game/search back through browser history or tab-search actually work, instead of every tab reading the same generic title.
- Library Explorer: the side panel now has the same "Owned by" section the comparison page already had (`buildLibraryOwnersHtml` in `public/library.js`, same template as `app.js`'s `buildOwnersHtml`) — per-account playtime and last-played, most recently played first, with a playtime meter. Shown even for a single loaded account (not just merged Steam Families) for consistency between the two pages; for a Family slot it surfaces the per-member breakdown the table itself flattens into one summed playtime / max last-played column. Backed by the same per-account `playtime`/`lastPlayed` maps `/api/common-games` already returns (previously only used to compute those flattened table numbers, then discarded) — works automatically for a standalone "look up any game" lookup too, since those maps cover the loaded account's entire owned library, not just whichever games are currently visible as table rows. Empty (and correctly hidden) on the Wishlist tab, since wishlist items aren't owned by anyone.
- `public/urlState.js` gained `reorderUrlParams`, a canonical query-param order (`u`, `tab`, `sort`, `game`, `shot`, `name`, filter dims, `view`, `wview`) shared by every URL-writing function on both pages — the same logical state now always serializes to the same URL string regardless of what order its pieces happened to be set/mutated in.
- Library Explorer now supports browser back/forward (previously the URL changed on load/tab-switch/panel-open but nothing listened for `popstate`, so Back did nothing). Also collapsed what used to be 2-3 separate `pushState` calls per Load-button click / tab switch / recent-search click (clearing `game`/`shot`, then setting `u`, then `tab` — each its own history entry) into a single push per genuine new load, with everything else (panel open/close, lightbox, an account refresh, restoring from a URL/back-forward navigation) using `replaceState` instead.

### Changed

- Site-wide contrast pass: `--text2` (`#4c6b8a`), used for most secondary/caption text (section titles, glance-chip captions, HLTB labels, news meta, achievement descriptions, owner/tag legends, footer links, etc.), measured well under WCAG AA against its actual backgrounds — 2.68:1 against `--bg0` and a failing 1.75:1 against `--bg1` (`--bg1` is the side panel's own background, so most panel captions were the worst-hit case). Every real-text use of `--text2` now uses `--text1` (`#8f98a0`) instead — 5.09:1 against `--bg0`, 3.32:1 against `--bg1` — while the handful of genuinely decorative/exempt uses (input placeholders, a disabled button's label, the offline-status dot's fill) keep the original muted `--text2`, since WCAG doesn't require those to meet text contrast and dimming them further than real content is intentional.
- Side panel (`public/style.css`): the collapsible HLTB/News/Achievements card headers no longer share the exact flat background/chevron look of the (non-interactive) glance grid chips right above them — both reused the same `panel-glance-num`/`panel-glance-val` chip template, so a static data point (e.g. the SteamDB score) and a click-to-expand control looked like the same kind of element. The card background stays `--bg0` (the same fill the glance chips already use, with proven ~1.5:1 contrast against the panel's own `--bg1`, rather than `--bg1` itself, which measures ~1:1 against the panel and made the cards nearly invisible but for their border), plus a 3px accent-colored left stripe and a chevron that's accent-colored at rest, not just on hover — so "this expands" reads as a control at a glance, without losing visibility.
- Side panel (`public/panel.js`, shared by both pages): the tag/genre/category/developer-publisher cloud now renders right after the glance grid instead of at the very bottom of the panel, below the (collapsed) HLTB/News/Achievements cards and the owner list. That identity info — what kind of game this is — is something most people want within the first screenful, especially when opening an unfamiliar title from the comparison page; the description (marketing blurb) now follows it instead of preceding it.
- Side panel: the title row's 📰 icon-link (out to the game's Steam news hub) is now only shown when the News card itself isn't rendered — once the News card exists, its own ↗ link already points at that exact same URL, so showing both was a plain duplicate. The icon still appears as a fallback for a game with no fetched headlines (no News card to carry a link at all). The HLTB and News cards also gained a leading icon (⏱️/📰, the same 📰 retired from the title row) in the numeral's slot — both cards had no number to show there (see `collapsibleCard`'s `numHtml` doc), which left them reading as plain text next to Achievements' bold colored percentage instead of as one visual family of cards.
- Side panel: the game description now reads at the same primary-text weight as the title and tag names (`--text0`, 13px) instead of the muted secondary-caption treatment (`--text1`, 12px) it shared with things like the HLTB labels and tag legend around it — it's prose meant to be read, not metadata, and was blending into both neighbors at that weight.
- Library Explorer: the Wishlist tab's "Wishlist Rank" column is now hidden by default (still available via the column picker) — Steam's wishlist ordering isn't something most users track or find meaningful at a glance.
- Library Explorer: the "Last Played" column is now hidden by default too (still available via the column picker). Steam's `GetOwnedGames` only returns real `rtime_last_played` data for the account whose own API key is querying it — every other account comes back with it silently absent, indistinguishable from "owned but never launched." Most searches here involve at least one non-key-owner account, so showing it by default risked reading as real data when it's often just an unavailable field. The column header now also gets a tooltip warning specifically when every currently loaded game shows no value at all — the actual tell that the whole column is unavailable for this account, rather than that nobody's touched their library.
- Both pages now write the shareable `?u=` URL and the localStorage recent-searches entry from the server-resolved Steam64 ID(s), not the raw typed input. Previously a vanity name (or a raw ID) was written verbatim as soon as the search was submitted, so the same player could produce differently-spelled URLs/recents depending on what was typed, and a vanity name that its owner later changed would leave a stale, no-longer-resolvable string behind. The write is now deferred until the search's fetch actually resolves the IDs (`public/app.js`'s `findCommonGames`, `public/library.js`'s `loadLibrary`/`loadWishlist`) rather than happening optimistically beforehand — simpler than a write-then-correct scheme, at the cost of the URL/recents no longer updating instantly while a search is still in flight, and not updating at all if it fails. `game`/`shot` deep-link params still clear immediately on a genuine new search, since they don't depend on anything the server resolves.

### Fixed

- Side panel glance strip (`glanceGrid`, `public/panel.js`): the SteamDB, Metacritic, and Linux/Deck (ProtonDB) chips no longer disappear when that source has no data for a game (no reviews, no critic score, no ProtonDB reports) — they now render a "—" placeholder with a "no rating"/"no score"/"no reports" caption instead, matching the fallback the HLTB chip already had. - Side panel: the hero image/filmstrip and glance strip no longer permanently occupy space above the scrollable body — on short/mobile screens they (plus the sticky title bar) could eat most or all of the visible panel before any real content (description, HLTB breakdown, owners, tags) came into view, with no way to scroll them out of the way. The glance grid's leftover margins (inherited from when it sat inside `.panel-header-sticky`) also made the gap above it nearly 3x the gap below — now symmetric.

- Library Explorer wishlist: the Released column's range filter/slider and date-tree dropdown no longer treat "Coming soon"/"TBA" placeholders as real dates. `endOfReleasePeriod` (the column's `parseDate`, also driving the framework's range-filter bounds and date-tree grouping — not just sorting) used to anchor those placeholders at a sentinel timestamp in the year 9999 so they'd sort deterministically after every real date; that same fake timestamp leaked into the other consumers of `parseDate`, dragging the whole column's computed max to year 9999 (squashing every real release date into a sliver of the range slider), letting a "released after X" filter wrongly match games with no known release date, and growing a nonsensical "9999" branch in the date-tree. The sentinel logic moved into a new sort-only helper, `releaseSortTimestamp` (used solely by the `compareDateMissingLast` sort comparator); `endOfReleasePeriod`/`parseDate` now treats those placeholders as unparseable (`NaN`), same as any other unrecognized string, so the range filter, slider bounds, and date-tree all correctly treat "unreleased" as "no known date."

### Changed

- The `[game-details]` upstream-failure warnings logged by `fetchGameDetails` (`server.js`) now include the appid — with several games fetched in parallel via `/api/game-details/stream`, a bare `ProtonDB error 403` gave no way to tell a single game's failure apart from every game in the batch failing the same way. The ProtonDB error message itself also now carries the appid plus a short response-body snippet, since that endpoint is called with no headers at all (unlike HLTB's spoofed UA/Referer) and a 403 there is as likely to be a blanket bot-block as a per-game issue. Those same warn lines now also print `err.cause` when present — Node's `fetch` throws a generic `fetch failed` `TypeError` for any network-level failure (DNS, connection reset, timeout, ...) and buries the actual reason there, so without it a whole batch of failures looked identical with no signal about the real cause.

### Fixed

- Side panel: a broken hero image (e.g. a video whose poster/thumbnail URL 404s upstream on Steam's own CDN — the video itself, played via the lightbox, can still work fine) no longer hides the entire hero. `setupHeroImg` (`public/panel.js`) used to respond to the `<img>` failing to load by hiding `.panel-hero-main` outright, which also took down the prev/next nav and, for a video, the play-button overlay and click target — the whole hero pane vanished instead of just the broken thumbnail. It now only marks the image itself broken (`.panel-hero-img--broken`) and leaves the rest of the hero usable. The filmstrip thumbnails got the same treatment, plus a fallback: a broken screenshot *thumb* now retries with the full-res image behind it (more likely to still be alive than the small thumbnail variant) before giving up.
- Side panel: on touch devices, dragging right over the hero filmstrip to scroll it toward earlier thumbnails no longer gets hijacked by the swipe-to-close gesture. `initPanelSwipe` (`public/panel.js`) tracked touches starting anywhere in the panel and `preventDefault()`'d any rightward horizontal drag to animate the close, which blocked the filmstrip's own native scroll for that same direction; it now excludes touches starting on `.panel-filmstrip`, matching the exclusion `initHeroSwipe` already had for its own hero-image-stepping swipe.
- ProtonDB requests (`getProtonDbStatus`, `lib/steam.js`) had no concurrency limiter, unlike Steam's store fetches or SteamSpy — a library/comparison load fetching details for dozens of games at once fired that many unthrottled connections at `protondb.com` simultaneously, which surfaced as bursts of network-level `fetch failed` errors (connection resets/DNS contention) across most or all of the games in the batch. Now capped at 3 concurrent requests, same as SteamSpy.

- An unreleased game with an announced release date (e.g. "Oct 14, 2026") no longer shows a blank Released date in the wishlist/side panel. `getAppDetails` (`lib/steam.js`) was nulling out the date whenever Steam's `coming_soon` flag was true, conflating "not out yet" with "no known date" — it now always passes through whatever date string Steam provides.
- Library Explorer: sorting/filtering by Released no longer misorders games with a coarse or fuzzy date ("2026", "Fall 2026", "Q4 2026", "2026 or later") — `new Date()` anchors those at the *start* of the period it can parse (e.g. "2026" → Jan 1), which could sort a still-unreleased game before ones that already shipped earlier that same year. A new `endOfReleasePeriod` helper anchors coarse dates at the *end* of their stated period instead (the latest point consistent with what Steam told us), and is now wired into both the Released column's sort `compare` and its `parseDate` (so the date filter tree/range picker agree with the sort order too, which they didn't before since `parseDate` wasn't set at all).
- Library Explorer: refined that same Released ordering further — a bare year and Q4 of that year used to tie exactly (both anchor at Dec 31), so `endOfReleasePeriod` now nudges the less-specific bare year 1ms later (e.g. `Q3 2026 < Q4 2026 < 2026 < 2028`). "Coming soon" and "To be announced"/"TBA" are also no longer unparseable placeholders dumped in an unordered bucket at the very end — they now get real sentinel positions after every dated/coarse entry, in that order (Coming soon carries at least some signal that TBA doesn't).
