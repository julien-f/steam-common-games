# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the app

```bash
echo "STEAM_API_KEY=your_key_here" > .env   # first time only — only required setting
npm install                                  # first time only
npm start                                    # or: npm run dev  (restarts on file changes)
```

The server binds to `http://127.0.0.1:3000` by default. `default.env` (committed to the repo) holds all settings with their defaults and documentation. Create `.env` (gitignored) with only the values you want to override — `STEAM_API_KEY` is the only required one. The server exits immediately at startup with a clear error message if it is missing.

Run the test suite with `npm test` (Node's built-in test runner against `test/*.test.js`, with `DB_FILE=` so it uses an in-memory database). There is no linter or formatter configured — match the existing style in whatever file/module you're editing rather than reformatting it.

## Architecture

- **`server.js`** — Express setup and route handlers only.
- **`lib/cache.js`** — Persistent cache (`getCached`, `setCache`), disk I/O, process exit hooks.
- **`lib/config.js`** — TTL constants (`LIBRARY_CACHE_TTL_MS`, `RESOLVE_CACHE_TTL_MS`, `RATING_CACHE_TTL_MS`, `META_CACHE_TTL_MS`, `SEARCH_CACHE_TTL_MS`, `BUNDLES_CACHE_TTL_MS`) shared across modules.
- **`lib/dedup.js`** — In-flight request deduplicator (`createDedup`): concurrent calls for the same key share one promise. Its in-flight map, and `lib/steam.js`'s per-host rate-limiting semaphores (`storeLimit`/`tagLimit`/`protonLimit`), are process-local state — correct for this app's current single-process deployment, but would need rethinking (e.g. a shared store) before ever running multiple instances/workers, since each would get its own independent map/semaphore and silently multiply real upstream request volume rather than erroring.
- **`lib/steam.js`** — Steam API calls (`resolveSteamId`, `getOwnedGames`, `getWishlist`, `getPlayerSummaries`, `getGameRating`, `getAppDetails`, `getSteamTags`, `getGameDemo`, `searchStoreGames`, `getGameNews`).
- **`lib/hltb.js`** — HLTB auth + search (`getHLTB`), plus exported `stringSimilarity` and `levenshtein` for unit testing.
- **`lib/groupGames.js`** — Groups slot libraries by exact ownership set (`groupByOwnership`).
- **`lib/itad.js`** — IsThereAnyDeal API calls (`getSteamShopId`, `getBundles`, `resolveSteamAppIds`) backing the Bundles page. See its own section below.
- **`public/index.html`** — Single-page frontend shell (vanilla JS, no framework).
- **`public/app.js`** — Main frontend JS: search flow, SSE streaming, rendering, filtering/sorting, URL state, and the page-specific parts of the side panel (owner list, tag-click filtering, prev/next/random nav bar) built on top of `panel.js`. Also wires up the accounts bar and recent-searches row from `accountsBar.js` (see below) — the accounts bar is grouped by slot (`renderAccountChipsGrouped`), each slot rendered in its own bordered box (`.slot-accounts` in `style.css`) rather than flowing inline with the next slot's chips, labelled `Player N` once there's more than one slot to tell apart (a comparison can involve several separate slots) and/or `N accounts merged` whenever a slot itself unions more than one account (a Steam Family) — without the box + merge count, a family merge (one slot, several accounts) and a plain multi-player comparison (one account per slot) rendered as the same flat, unlabelled-or-thinly-labelled row of chips. A recent-search entry stores the whole normalized slot array so clicking it rebuilds every slot/family input row via `addPlayerSlot`. `updateTitle()` keeps `document.title` in sync: an open game's name takes over the title entirely; otherwise it falls back to the loaded slot names, then the bare app name with nothing loaded. `updateLibraryExplorerLink()` keeps the site nav's Library Explorer link (see `public/nav.js` above) pointed at `/library.html?u=<ids>` for the single player/Family currently loaded, falling back to the bare link for a multi-player comparison (which the Library Explorer has no notion of).

Renders the hero carousel, score/HLTB/news/tags/links body, and handles swipe gestures; used by both `app.js` and `library.js`. Page-specific bits (owner list, tag-click filtering, nav bar) are supplied via `options` or layered on by the host page wrapping `panelOpen`/`panelClose`. `panelClose()` itself is called from more places than just host code — the backdrop click, × button, and swipe-to-close are all bound straight to it — so `options.onClose` is the one hook guaranteed to run on every close path, not just whichever one a host happens to wrap; both `app.js` and `library.js` use it to clear `?game=`/`&shot=` from the URL (and, on the comparison page, to reset its own `activeGame`/row-highlight state) regardless of how the panel closed. `panelClose({ preserveUrl: true })` skips that URL clearing for a caller that's about to reopen the same game once a refresh/restore completes (see `findCommonGames` in `app.js`) — the URL still needs its `game`/`shot` params intact for `restorePanelFromUrl()` to read afterward. A "News" section (`newsHtml`) shows every headline in `g.news` (title, plain date, feed label; up to 20, `extractNews`' own cap in `lib/steam.js`), each linking to the full post, collapsed behind a chip by default (`collapsibleCard()`, shared with the HLTB breakdown and Achievements sections — see below) whose ↗ icon links out to the game's Steam news hub for anything beyond what was fetched. `g.news` is already filtered server-side (`extractNews`) to the developer/publisher's own `steam_community_announcements` feed — the raw `GetNewsForApp` endpoint also aggregates syndicated third-party press in whatever language that outlet publishes in, unrelated to the requester's locale, which for some games outnumbers official posts entirely and doesn't match what the store page's News tab shows. There's no standalone 📰 icon-link in the header — only the News card's own ↗ icon (once it renders) links out to the hub; a game with confirmed zero official posts (no card at all) isn't worth a dedicated header icon just to go check whether unrelated syndicated press showed up there instead. Unlike rating/HLTB/tags/ProtonDB (which live on `g.details` and are prefetched for every game via `fetchGameDetails`/the SSE stream — see "Ratings"/"HLTB" and the Request flow below), news has no table column and nothing to sort/filter on, so it's kept off `g.details` entirely and fetched lazily by `panel.js` itself (`loadNews`), once per game, only when that game's panel actually opens — the same on-demand shape achievements already use, backed by its own `GET /api/game-news/:appid` route rather than folded into `fetchGameDetails`. `g.news`/`g.newsLoading` persist on the game/row object, so reopening a game already seen this session doesn't refetch; the panel's "↻ Refresh" button force-refreshes it alongside everything else (`handlePanelRefresh`). A "Price" card (`priceHtml`) is deliberately light — a single always-open card, not a collapsible section: the current Best Deal (same 🔥 all-time-low/★ 1-year-low/☆ 3-month-low color+badge+tooltip as the Bundles/Wishlist table cell's `renderBestDeal` (`public/gameColumns.js`), both built on the shared `dealRecordTier` — see `public/utils.js`'s own bullet above and the Best Deal column's bullet below; `panel.js` can't `import` `renderBestDeal` itself the way `bundles.js`/`library.js` do, since it's a plain script and `gameColumns.js` is an ES module — see that file's own header comment — so this card keeps its own small copy of the surrounding render code, built on the one piece that really matters being shared), its Discount when there is one, and the shop name — plus an "IsThereAnyDeal ↗" link in the card title for the fuller picture (historical lows, every other shop) this card leaves out on purpose. When there's a deal to buy, the *whole line* below the title (not just the shop name) is itself the outbound buy link (ITAD's own per-deal affiliate/redirect `url`, passed through unmodified — same rule as the Bundles page's "Get this bundle" link) — a large, easy target rather than one small "Fanatical ↗" word, since going to buy is the entire point of the card; falls back to a plain unlinked line when ITAD didn't return a url for that deal. No numbers beyond Best Deal/Discount, no bundle tier price, no subnav entry — earlier drafts of this card carried all of that and read as too heavy for what's meant to be a quick glance. Entirely passive, unlike news/achievements/DLC above: it renders whatever `bestDealPrice`/`bestDealCut`/`bestDealShop`/`bestDealUrl`/`lowAll`/`lowY1`/`lowM3`/`priceCurrency` the *host page* already put on the row object (see `loadWishlistPrices` in `library.js`/`loadPrices` in `bundles.js`, both under their own sections below) rather than fetching anything itself, so it's simply absent on the comparison page and standalone lookups, which never set those fields (`g.bestDealPrice === undefined`). Because the mutation happens outside `panel.js`, both of those functions re-render an already-open panel right after mutating a row (`isPanelOpen() && getPanelGame() === row → renderPanelBody(row)`, the same idiom the ratings/HLTB stream and achievements loader already use elsewhere in those files) — without it, a panel opened before its price batch resolved would never pick the numbers up once they landed.

### Request flow

1. Frontend POSTs `{ slots: [["alice", "bob_family"], ["charlie"]] }` to `/api/common-games`. Each slot is a logical player — multiple accounts in a slot have their libraries unioned before comparison (Steam Family simulation). Legacy `{ users: [...] }` is also accepted and treated as single-account slots.
2. Server resolves every identifier to a Steam64 ID, deduplicates within each slot, fetches all libraries in one parallel pass, unions libraries per slot, groups games by exact set of slot owners, returns `{ groups, slots }`.
3. Frontend renders groups immediately (one table per owner set, from most owners to fewest), then POSTs the full game list to `POST /api/game-details/stream` (SSE endpoint) to load rating, HLTB, store metadata, and tags progressively in a single connection. The legacy `GET /api/game-details/:appid` endpoint still exists for direct API consumers.

### Ratings — Wilson score vs. Weighted Rating

The comparison page's own table cell (and the "Wilson Score" column in the Library Explorer) show the **Wilson score lower bound** at 95% confidence, computed server-side in `getGameRating`/`computeRating` from Steam's own review counts (`store.steampowered.com/appreviews/:appid`). Do not replace it with a simple positive/total ratio — that's exactly the naive approach the Wilson bound is meant to avoid, since it lets a game with 2 positive reviews outrank one with 50,000 mostly-positive reviews. (SteamDB itself used to use this same formula but has since switched to a different one — see below — so don't assume parity with what SteamDB currently shows.)

Client-side, from the same `rating.positive`/`.total` numbers already delivered to the frontend (no extra backend calls), `computeSteamdbRating(positive, total)` in `public/utils.js` computes a formula adapted from SteamDB's current one instead: `p − (p − 0.5) × 2^(−k × log₁₀(n + 1))` where `p = positive/total`, `n = total reviews`, and `k` is `STEAMDB_RATING_SHRINK_STRENGTH`. A Bayesian shrinkage toward a neutral 50% prior that fades as review volume grows. SteamDB's own published formula is `k = 1` (their worked example: 90% positive over 100 reviews lands at 80%); this app runs hotter, at `k = 2`, so it converges to the raw ratio faster (the same 90%/100-review example lands at ~87-88% here) — a deliberate app-specific tuning choice, not a claim about what SteamDB itself currently shows. Whatever `k` is, the result is mathematically guaranteed to stay between 50 and `p`, moving monotonically closer to `p` as `n` grows — it can never overshoot past `p`. SteamDB moved to this general shape from the Wilson interval specifically because it's easier to explain to users; see [steamdb.info-issues#793](https://github.com/SteamDatabase/steamdb.info-issues/issues/793). It returns the **raw, unrounded** value — round only for display; the Library Explorer's Weighted Rating column sorts on the unrounded number so otherwise-tied displayed integers still order deterministically, and isn't groupable (grouping keys off the raw value, which would otherwise split into a near-useless one-row-per-group table). The internal function/field/URL-param name (`computeSteamdbRating`, the `steamdbRating` row key, `?sort=steamdbRating`) is left as-is rather than renamed alongside the label — renaming it would silently break any already-shared library URL with that in its `sort`/`view` param, for a purely internal identifier no user ever sees.

This one function backs two different, intentionally-asymmetric surfaces:

- **Library Explorer table** — "Weighted Rating" is the default-visible, default-sorted score column; "Wilson Score" and "Steam %" (the raw, unadjusted ratio) both exist too, hidden by default.
- **Game detail side panel** (`public/panel.js`, shared by both pages) — shows only the Weighted Rating (labeled just "Weighted", linking to the game's Steam reviews, since the number/caption is this app's own weighted rating, not SteamDB's) plus a compact reviews line (e.g. "99% positive of 465k reviews"), no Wilson score and no Steam review-summary text tier (e.g. "Very Positive"). This means the comparison page's own table cell (Wilson score) and its side panel (Weighted Rating) intentionally show two different numbers for the same game — expected, not a bug.

### Production Tier — a heuristic, not Steam-provided data

Steam's API has no field for a game's budget or studio size, so the Library Explorer's "Production Tier (est.)" column (hidden by default) is a best-effort AAA/AA/Indie guess, computed client-side by `computeProductionTier` in `public/utils.js` from three signals already delivered to the frontend for every row: `meta.isFree`/`meta.priceInitial` (the undiscounted launch price in cents, USD — new fields on `extractAppDetails` in `lib/steam.js`, backed by the same appdetails response already fetched for everything else about the game; `getAppDetails`'s upstream fetch now pins `cc=us` specifically so this price is always USD regardless of the server's own geolocation), `rating.total` (review count, a reach proxy) and whether a Metacritic entry exists at all (professional press coverage tends to skip most indie releases). Deliberately **no publisher/developer allowlist** — that would be the single strongest signal (works before any reviews accumulate, survives sales, survives free-to-play) but requires externally maintained, ever-drifting knowledge Steam's API doesn't provide (legal-entity name variants, acquisitions, studio spin-offs); the heuristic stays entirely self-updating from Steam's own data instead, at the cost of accuracy in exactly the cases only a publisher list would catch.

Decision order: DLC/expansion appids (`meta.fullgame` set) and Steam's other non-game content types (`meta.type` being `dlc`/`demo`/`music`/`video`/`series`/`episode`/`mod`/`hardware`/`advertising` — see the Library Explorer's own "Type" column below) return `null` outright rather than being scored on their own price — a cheap DLC attached to a AAA base game would otherwise misclassify as Indie, and no parent-game lookup is attempted to avoid an extra fetch just for this. Free-to-play games have no price signal at all, so they're judged on review volume alone against a deliberately high bar (200k+) — the only lever available. Priced games ≥$50 are "AAA"; $20–$50 is the AA/premium-indie overlap zone, requiring either 20k+ reviews or a Metacritic entry to clear "AA" rather than fall to "Indie"; below $20 is always "Indie" regardless of review count (this is where breakout indie hits with huge review counts — Vampire Survivors, Stardew Valley, Terraria — correctly stay classified as Indie rather than reading as AAA). Known, accepted misclassifications with no data-side fix: cheap rereleases/remasters of old AAA IP, prestige-priced niche sim/strategy games from small studios, and veteran-founded small studios shipping a low-budget but polished game. This is why the column label spells out "(est.)" rather than presenting the value as fact.

### HLTB — no npm package

The `howlongtobeat` npm package was removed (it pulled in a vulnerable `axios`). HLTB is called directly with a two-step auth flow:

1. `GET https://howlongtobeat.com/api/search/site/init?t={ms}` → returns `{ token, hpKey, hpVal }`
2. `POST https://howlongtobeat.com/api/search/site` with `X-Auth-Token`, `X-Hp-Key`, `X-Hp-Val` headers and `{ [hpKey]: hpVal, ...payload }` in the body

(Previously `api/bleed/init` and `api/bleed` — HLTB renamed these endpoints; the `howlongtobeat-ts` npm package's source is what surfaced the new paths when the old ones started 404ing.)

The token is cached in memory for 5 minutes (not on disk — it's session-bound). A 401/403 from the search endpoint clears the cache so the next call re-fetches. Match quality is checked via Levenshtein similarity; results below 0.35 are discarded.

`pickBestMatch` extracts four times from the matched entry's raw fields (all in seconds, converted to hours rounded to the nearest half hour — the same granularity HLTB's own site displays, e.g. "2½ Hours" — rather than a whole hour, which would silently discard that precision): `main` (`comp_main`), `extra` (`comp_plus`), `completionist` (`comp_100`), and `all` (`comp_all`) — HLTB's "All PlayStyles" figure. `all` is **not** an average of the other three — it's the average of every individual completion-time submission pooled together regardless of category, weighted by how many people submitted each one (`comp_all_count` equals `comp_main_count + comp_plus_count + comp_100_count`). Since far more players report a Main Story time than a Completionist one, it usually lands much closer to Main Story than to the simple midpoint of all three. It's the default-displayed HLTB column in the Library Explorer (`hltbAll`, "All (h)") and shown first (leftmost) in the side panel's How Long To Beat section as "All PlayStyles", precisely because it's a single representative number rather than one specific playstyle.

If HLTB breaks again, recent npm packages (e.g. `howlongtobeat-ts`) tend to reverse-engineer the new flow quickly and are a good first place to look.

**Compliance note:** `/api/search/site` is an undocumented, internal HLTB endpoint reached with spoofed browser `User-Agent`/`Referer` headers — this is not a published public API and isn't guaranteed to be sanctioned by HLTB's terms of service. Usage here is low-volume and non-commercial, but treat it as liable to break or be blocked without notice, and don't scale up request volume without revisiting this.

### Wishlist — undocumented endpoint

`getWishlist` calls `https://api.steampowered.com/IWishlistService/GetWishlist/v1/?steamid={id}`, which is not listed in Valve's published Web API docs (same unofficial-endpoint situation as HLTB above, though no spoofed headers are needed here — it works with a plain request). A private wishlist, a private profile, and a genuinely empty wishlist are all indistinguishable: each returns `200 OK` with `{"response":{}}` (no `items` key). The app treats a missing `items` key as an empty wishlist rather than surfacing an error, since there's no way to tell those cases apart.

### Tags & demo link — Steam's own store browse data, not SteamSpy

`getSteamTags` (`lib/steam.js`) fetches the same user tags shown on a game's own Steam store page (and, downstream of that, SteamDB and IsThereAnyDeal) rather than SteamSpy's separate crowd-voted dataset, which this used to pull from and which can be sparse or empty for a game Steam itself has plenty of tag data for — especially anything niche or too recent for SteamSpy's own community to have caught up on. Two undocumented, key-less endpoints (same trust tier as the other endpoints covered by this compliance note) stand in for it:

- `https://api.steampowered.com/IStoreBrowseService/GetItems/v1/?input_json={"ids":[{"appid":N}],"context":{"language":"english","country_code":"US"},"data_request":{"include_tag_count":30}}` returns that one app's whole "store browse item" — `tagids` (already ordered by relevance weight descending, the same order the store page itself displays them in — all returned tagids are shown, no further display cap on top of this) plus other fields riding along on the same response for free. `getGameDemo` reads one of those: `related_items.demo_appid`, the appid of the game's free demo if it has one, surfaced in the side panel as a standalone "🎮 Try the Free Demo" banner (`public/panel.js`'s `demoBannerHtml`) right under the sticky header — deliberately not folded into the "⋯ More" icon menu alongside Website/Workshop, since a demo is a call to action worth surfacing without an extra click, unlike those two which are just supplementary info. The **whole raw item** is cached (`browse:{appid}`, not just the extracted tagids) — the usual "cache raw, extract at read time" approach used everywhere else in this file (see the cache-table intro above) — specifically so that adding another field this same call already returns, like the demo link, never needs a new upstream request, just a new extractor over the already-cached response. `getSteamTags` and `getGameDemo` share one upstream fetch per appid this way, via the same cache entry plus the usual in-flight dedup.
- `https://store.steampowered.com/actions/ajaxgetstoretags?l=english` maps every tagid to its human-readable name — a single, near-static ~430-entry list, not per-game, so it's fetched once and cached long-term (`tagnames:all`, same 60-day `META_CACHE_TTL_MINUTES` group as `browse:` — see the cache table above) rather than repeated for every game lookup.

The `browse:` cache key is the third one used for this data — `tags:` (SteamSpy's `{tagname: voteCount}` object) then briefly `tagids:` (a bare `tagid[]`) came before it. Each format change got a new key rather than reusing the old one: a shape check alone can't safely tell an old value apart from a new one when both can legitimately be the same JS type (e.g. a game with zero SteamSpy votes cached a bare `[]`, indistinguishable from an empty `tagid[]` result). Retired-key entries are simply never read again and age out on their own via the existing TTL sweep.

### Looking up an arbitrary game

Both pages have a "look up any game" search box (`public/gameSearch.js`) for previewing a game in the shared side panel regardless of whether anyone in the current search owns or has wishlisted it — see the "Ratings" and "HLTB" sections above for what that panel shows. `GET /api/game-details/:appid` has no ownership check at all (it already has to work for wishlist items, which aren't "owned" either), so the only missing piece was turning a typed name into an appid.

Opening a looked-up game writes `?game=<appid>` to the URL on both pages (and, within it, `&shot=<idx>` for an open lightbox screenshot/video) — a copied link reopens the same standalone lookup once the page loads, falling back to fetching the appid directly if it isn't part of whatever's currently loaded (or nothing is loaded at all). `public/gameSearch.js` also keeps a "recently looked up" row of games (distinct from `accountsBar.js`'s per-page "Recent:" *player*-search row) backed by one `localStorage` list shared by both pages, since a looked-up game means the same thing regardless of which page found it.

`GET /api/game-details/:appid` never accepts or trusts a client-supplied name — it always resolves the game's name itself from store metadata (`getAppDetails(appid)`), the same appid-keyed source used for everything else about the game, and searches HLTB using that resolved name. A name picked from the search dropdown (or carried in `library.js`'s standalone-lookup object) exists purely client-side, to avoid a title flash in the panel while the fetch is in flight — it's never sent to the server or written to the URL. The cost is that HLTB search always waits for store metadata to resolve first, rather than starting in parallel using an already-known name (e.g. an owned game's name from Steam's library API) — a deliberate trade against treating any client-provided string as ground truth on a public, key-less, ownership-free endpoint.

`GET /api/search-games?q=<term>` (`searchStoreGames` in `lib/steam.js`) wraps `store.steampowered.com/api/storesearch/?term=...&l=english&cc=US` — the same undocumented endpoint Steam's own store search box uses, no key or auth required. Same trust tier as the HLTB/wishlist endpoints documented elsewhere in this file: not a published API, not guaranteed to be sanctioned by Steam's terms, liable to break or be blocked without notice. Usage here is low-volume (client-side debounced, and each distinct term only costs one upstream call — repeats hit the `search:` cache tier) and non-commercial; don't scale up request volume without revisiting this note. A bare appid or a pasted store URL (`store.steampowered.com/app/<id>/...`) typed into the box bypasses this endpoint entirely and goes straight to `/api/game-details`.

### Bundles — IsThereAnyDeal API

The Bundles page (`public/bundles.html`/`bundles.js`) browses current Steam game bundles via the [IsThereAnyDeal API](https://docs.isthereanydeal.com/) (`lib/itad.js`) — a free, key-gated API, distinct trust tier from the undocumented Steam/HLTB endpoints covered elsewhere in this file (published, if sparse, OpenAPI docs). Entirely optional: gated behind `ITAD_API_KEY` (`.env`), which is not required for the rest of the app to run. `server.js`'s `isItadConfigured()` checks it per-request; `GET /api/bundles`/`POST /api/bundles/resolve`/`POST /api/prices` return 503 when unset, and the page itself shows a plain "not configured" message instead of the browse UI (`GET /api/health`'s `itadConfigured` field drives that check). The same ITAD integration also backs the Library Explorer's Wishlist price columns — see its own section below; `POST /api/prices` is shared by both pages (this section covers it from the Bundles side first).

The bundle list itself is height-capped and scrollable (`.bundle-list`, `max-height`) rather than growing to however many bundles are loaded, and auto-collapses to a one-line "Show list" toggle once a bundle is actually opened (`setListCollapsed`) — otherwise a long list pushes the real content (the opened bundle's game table) far down the page. Changing region/sort/"include expired" re-expands it, since that's a browsing action again.

- **`GET /bundles/v1`** (wrapped by `getBundles` / `GET /api/bundles`) lists current bundles, paginated (`offset`/`limit`, max 50/page), with a `country` param that drives both currency and (per ITAD, presumably regional storefront) pricing. There is no single-bundle-fetch endpoint upstream, so `?bundle=<id>` deep linking (same idea as `?game=`/`?u=` elsewhere) is backed by a bounded server-side search instead: `findBundleById` (`lib/itad.js` / `GET /api/bundles/:id`) pages through `GET /bundles/v1` — active bundles first (`expired=false`), then expired — up to `BUNDLE_SEARCH_MAX_PAGES` (6) pages of 50 each per expired-state, and 404s rather than searching indefinitely if the id never turns up (very old/deleted bundle, or a bad id). Each page it fetches reuses `getBundles`' own per-page cache, so a second deep link into a bundle on an already-searched page costs no extra upstream call. `openBundleById` (`bundles.js`) always goes straight to this route on page load rather than checking whatever's already in the browsed list first — the list may be a different sort/page, or not loaded yet at all, and the two run concurrently rather than sequentially. Opening a bundle (deep-linked or picked from the list) always writes `?bundle=<id>` via `replaceState` (not pushed — this page has no `popstate` listener, unlike `library.js`/`app.js`); a 404 clears it back out so a refresh doesn't repeat the same failed search.
- Each bundle's `tiers[]` lists the games unlocked at that price tier; a game can appear in more than one tier (a cheap tier's games are still included in every pricier tier above it) — `flattenBundleGames` (`public/bundles.js`) dedupes by ITAD game id, keeping the cheapest tier's price, since ITAD's tiers are observed to always be price-ascending.
- Bundle games carry no Steam appid directly — only an ITAD-internal id (uuid), slug, and title. Resolving to Steam is a separate step: `resolveSteamAppIds` (`lib/itad.js`) first resolves ITAD's numeric shop id for Steam via `GET /service/shops/v1` (cached under `itad-shop:steam`, effectively permanent), then batches the bundle's game ids through `POST /lookup/shop/{shopId}/id/v1` (`POST /api/bundles/resolve` on this app's side) — **not** the more RPC-shaped `/lookup/{shopId}/gid/v1` path the sibling lookup endpoints' naming might suggest; the real path follows ITAD's own `/lookup/{lookup-what}/{by-what}/` convention and was confirmed against the live API, not just the docs. The response namespaces each shop id as `"app/<id>"` (a store page) or `"sub/<id>"` (a package/bundle sub, not a single game page) — only an `"app/"` entry resolves to something `GET /api/game-details/:appid` can look up; a game listed only as a `"sub"` resolves to `null`, same as no Steam listing at all. Each ITAD game id's resolution is cached individually (`itad-appid:{gid}`) so a game seen in one bundle is never re-resolved for another.
- Resolved games feed straight into the same `POST /api/game-details/stream` pipeline the Library Explorer uses — the Bundles page's game table shares almost its entire column set with the Library Explorer via `public/gameColumns.js` (`CORE_COLUMNS`/`PRICE_COLUMNS` — see its own file-listing bullet above for what's shared and why), same shared side panel. The only columns this page still defines for itself are genuinely bundle-specific (Tier Price, Add-on — see below); ownership-only columns (Played/Last Played) simply never enter the shared `CORE_COLUMNS` at all, so there's nothing to exclude here the way an earlier, fully-duplicated version of this table needed to. Unresolved games (no Steam listing) render in a separate plain list instead of the table — nothing to sort/filter/group on beyond what ITAD already gives (title, type, tier price, boxart).
- The panel's prev/next/random nav bar (`#panel-nav`, ↑/↓/R — same shared markup/keys/CSS as `library.js`'s own), hero ArrowLeft/Right stepping, and `?game=<appid>`/`&shot=<idx>` deep linking now all work here too, mirroring `library.js`'s `renderPanelNav`/`getGameList`/`setPanelParam`/`setLightboxParam`/`restorePanelFromUrl` (see the "Looking up an arbitrary game" section above for the general shape; this page has no `gameSearch.js` lookup box, so the list a game navigates is always the currently open bundle's own resolved rows, via a `visibleRows()`/`getGameList()` pair added alongside the pre-existing `visibleRowsForTable()`). `openGame` (used by `onRowClick`, the nav buttons, and DLC/base-game navigation alike) is the one place that opens the panel, so nav bar + `?game=` + achievement loading always stay in sync regardless of how a game was opened. Opening a *different* bundle (list click, ‹/› nav, a fresh `?bundle=` deep link) always closes whatever panel is open and clears `?game=` first — its nav position belonged to the bundle being left — **except** a region change reopening the *same* bundle in place (`openBundle(bundle, { preserveGameParam: true })`), which keeps the open game across the re-price.
  - `restorePanelFromUrl(restoreShot)` is checked **twice** per bundle open (`openBundle`), same two-call shape `library.js`'s own `loadLibrary`/`loadWishlist` use and for the same reason: an *early* attempt right after `rowMap` is populated — before the ratings/HLTB/tags stream itself starts — opens a `?game=` that's part of this bundle immediately as a real, progressively-filling row (rather than waiting for every game in the bundle to finish loading first, or falling back to a lesser standalone view); a *second* attempt once the stream completes actually opens `&shot=`'s lightbox, since that needs real media data the early attempt's still-`loading` row doesn't have yet. `restoreShot` is threaded through as an explicit param (captured once, up front, in `init()`) rather than re-read from `location.search` on the second call, for the same reason `library.js` does this — opening the panel calls `setPanelParam()`, which deletes `shot` from the live URL. The per-event stream loop (`streamGameDetails`) also calls `renderPanelNav(row)` (not just `renderPanelBody(row)`) whenever the *currently open* game's own data streams in — without it, a game opened via the early attempt (list still empty — nothing's streamed in yet) would show a permanently stuck "0 / 0" nav position and a stale, empty prev/next button list, since nothing else re-renders the nav bar as the rest of the bundle streams in around it. A game that isn't part of the bundle (or no bundle was linked at all) falls back to a standalone lookup, same as DLC navigation to a game outside the bundle already did.
  - Fixed as part of this: Escape previously did nothing while the lightbox was open on this page — it only ever guarded *against* closing the panel behind an open lightbox, never actually closed the lightbox itself (`app.js`'s/`library.js`'s own Escape handlers always had that branch; this page's copy was missing it). Rather than fix bundles.js's copy in isolation, the lightbox-close-then-panel-close logic all three pages need is now one shared `panelHandleEscape()` in `panel.js`, called from each page's own Escape branch (after whatever page-specific higher-priority check it has, e.g. the keyboard-shortcuts modal on `app.js`/`library.js`) instead of three hand-rolled copies that can silently drift apart the way this one did.
- **`POST /games/prices/v3`** (wrapped by `getPrices`/`extractPriceInfo` in `lib/itad.js`, `POST /api/prices` on this app's side) supplies the pricing columns — batched separately from `resolveSteamAppIds` above since it needs `country` (prices are region-specific; appid resolution isn't) and returns, per ITAD game id, `historyLow.{all,y1,m3}` (the lowest price seen across every shop ITAD tracks — not Steam-specific; "have I ever seen this cheaper anywhere" is the more useful question than a Steam-only low) plus a `deals[]` array with each shop's current `price`/`regular`/`cut`/`url` (ITAD's own affiliate/redirect link for that specific deal). `extractPriceInfo` reads this array twice: once for the `deals[]` entry whose `shop.id` matches the Steam shop id (from `getSteamShopId`), returning its `regular` (Steam's own non-discounted price), and once scanning every entry for the lowest `price.amount` regardless of shop (`bestDeal: {price, shop, url}` — `url` exists purely so the side panel's Price card, see `panel.js`'s own bullet above, can link straight to the shop; passed through unmodified, same as every other ITAD-sourced link/price in this app) — every entry in one response is already in the same requested `country`'s currency, so they're directly comparable with no conversion needed. Both this call and `resolveSteamAppIds`'s lookup run for a bundle's games concurrently with the `game-details/stream` fetch (`Promise.all` in `openBundle`) — pricing has nothing to do with ratings/HLTB/tags, so there's no reason to sequence them. Cached per `(gid, country)` (`itad-price:{country}:{gid}`), unlike the appid resolution above which only needs to be resolved once ever — a price is meaningfully different per region, not just a currency relabeling. Best Deal and Discount are visible by default (answers "is this bundle actually a good deal, and where's it cheapest right now" at a glance); Steam Full Price (named that way, not the shorter "Steam Price", specifically to make clear it's the non-discounted list price), All-Time Low, Best Deal Shop, and 1yr Low/3mo Low are hidden by default, same "secondary number" convention as Wilson Score/Steam %/Achievements elsewhere in this column set — Steam Full Price and All-Time Low specifically because Best Deal + Discount together already answer "is this a good deal, and by how much" for the common case, not because the exact numbers stopped being useful. A bundle tier's own price (`tierPrice`/`tierCurrency` on each row) can be `null` for a free/pay-what-you-want-or-more tier.
  - **Discount is its own column (`bestDealCut`), not a percentage folded into the Best Deal cell — and it's computed against Steam Full Price, not taken from ITAD's own per-deal `cut` field.** `cut` (an integer percentage ITAD does return per deal, e.g. `70` for 70% off) is that shop's own discount off *its own* regular price — a number shops set independently and don't compute consistently with each other, so it means something different from row to row (whatever that particular shop happens to list). `discountPct(bestDealAmt, steamRegularAmt)` (`public/gameColumns.js`, shared by both pages — see its own file-listing bullet above) computes `1 - bestDeal/steamRegular` instead, so every row's Discount answers the same question against the one stable, Valve-set anchor this app already treats as the reference price throughout (the same reasoning that keeps Steam Full Price around as its own column at all). Safe to compute without clamping: Best Deal is defined as the cheapest price across *every* shop including Steam, so `bestDealAmt <= steamRegularAmt` always holds. `extractPriceInfo` (`lib/itad.js`) deliberately does *not* surface `cut` at all, for exactly this reason. `renderCut` renders `0` (the best deal genuinely isn't any cheaper than Steam) the same as "—" — a flat "0%" would read as noise next to every other row's real discount, and nothing else in this column set treats a confirmed zero differently from "nothing to show" either.
  - **`POST /api/prices` is one shared route for both Bundles and the Library Explorer's Wishlist tab**, not two near-identical ones — the actual pricing operation (resolve to an ITAD gid if needed, then `getPrices`/`extractPriceInfo`) is identical either way; only the identifier space the caller already has differs. Bundles passes `gids` (it already has ITAD gids off a bundle's own `tiers[].games[].id`); the Wishlist tab passes `appids` instead (a wishlist row only has a Steam appid) and the route resolves those to gids internally first via `resolveItadIds` (`lib/itad.js`) — the reverse direction of `resolveSteamAppIds` above, via `POST /lookup/id/shop/{shopId}/v1` (confirmed against the live API: takes `["app/<appid>", ...]`, returns `{"app/<appid>": "<uuid>"|null, ...}`, keyed by exactly what was sent). That reverse resolution isn't exposed as its own route the way `/api/bundles/resolve`'s gid→appid mapping is — nothing needs the raw gid itself, unlike Bundles' own "which of these games have no Steam listing at all" list. Each appid's resolution is cached individually (`itad-gid:{appid}`, same `cache_bundles` tier as `itad-appid:` — see the Database section below), same "confirmed miss cached the same as a real mapping" treatment as `resolveSteamAppIds`. Exactly one of `gids`/`appids` must be provided; the route 400s on both-or-neither. See the Library Explorer's own section below for the Wishlist-side details (row shape, region picker, the `visibleRowsForTable`/`markRowChanged` fix this feature needed there).
  - **`tierCurrency` and `priceCurrency` are deliberately two separate fields on a row, not one shared `currency`.** An earlier version had one shared field, populated first from whichever value arrived first and never overwritten — this was a real bug, confirmed live: a bundle's own tier price can come back from ITAD in USD only regardless of requested `country` (same "this shop doesn't offer this region's currency" situation as bundle-level pricing generally — see the region-selection bullet below), while that *same* bundle's games' Steam/other-shop prices, a separate upstream call, correctly come back in the requested currency. With one shared field, whichever request resolved first "won" and silently mislabeled the other's amounts with the wrong currency symbol (right number, wrong label — easy to miss). `tierCurrency` (from the bundle's own tier data) backs only the Tier Price column; `priceCurrency` (from `loadPrices`, always set unconditionally from that response — never conditionally backfilled) backs the other five price columns. `formatMoney(v, currency)` (`public/utils.js` — see its own file-listing bullet above for why it lives there rather than in `gameColumns.js` alongside the rest of this logic) is the shared low-level formatter both `renderPrice` (`gameColumns.js`) and `renderTierPrice` (`bundles.js`, bundle-specific) call with the correct field for their own column, rather than each reimplementing `Intl.NumberFormat` against a shared field.
  - `renderBestDeal` (`public/gameColumns.js`, shared by both pages — one definition, not a duplicated pair) deliberately does NOT put the shop name in the cell's own text (an earlier version did, as "$11.24 · Fanatical") — instead the price is colored/badged when it's at or below a historical low, via the shared `dealRecordTier(price, row)` (`public/utils.js` — see its own bullet above): bright teal + bold + 🔥 for an all-time low, green + ★ for a 1-year low, amber + ☆ for a 3-month low, each checked only when no rarer tier already matched. `<=`, not `<` — the current deal genuinely can BE the historical low itself (it's what set it), not only ever beat it. The shop name still exists (a native `title` tooltip on the price, and its own hidden-by-default `bestDealShop` column for grouping/filtering) — dropped from the cell text specifically to leave room for the low-price indicator, judged the more actionable of the two at a glance. The tooltip itself is deliberately terse — just the shop name (`"Fanatical"`), plus `dealRecordTier`'s own `tooltipLabel` (`" — all-time low"`/`" — 1-year low"`/`" — 3-month low"`) appended when it qualifies — with no "cheapest current price" restatement, since that's already what the Best Deal column itself means; an earlier draft spelled that out in every tooltip and it read as redundant once actually seen hovering over a column already labeled "Best Deal". `panel.js`'s `priceHtml` (the side panel's Price card, a plain script that can't `import` from `gameColumns.js` — see that file's own header comment) still keeps its own copy of this same tier-to-badge logic, built on the same shared `dealRecordTier` — a 3-month-low tier was once added only to `computePriceStatus`/`PRICE_STATUS_TIERS` before anyone remembered to add it to `renderBestDeal`/`panel.js`, which is exactly the divergence pulling the tier logic itself into `dealRecordTier` now prevents, even where the surrounding render code still can't be the literal same function.
  - **Every price column (Tier Price, Steam Full Price, Best Deal, All-Time/1yr/3mo Low) and Discount are `groupable: true`, bucketed rather than grouped by exact value** — a raw price/percentage is near-unique per row, which would otherwise produce one group per row (the same problem `bucketNumericRange`/`bucketLogRange` solve for `hltbAll`/`reviewsTotal` elsewhere in this file). Discount uses a plain fixed 25-point step (`bucketNumericRange(25)`/`formatNumericRange(25, '%')`) — a percentage is already bounded 0-100 with no long tail, so an even step is enough. The five/six price columns instead bucket against `PRICE_TIERS` (`[0, 5, 15, 30, 50, 75, 100]`), a hand-rolled staircase matching Steam's own common price points ($4.99/$14.99/$29.99/$49.99/$74.99) — neither a fixed linear step (too coarse or too fine depending on where you set it) nor the log-scale `bucketLogRange` grid (geometric, so it can't land on both "$50" and "$75" as distinct boundaries) reproduces those specific breakpoints. A real `$0` gets its own "Free" bucket, same "real zero is its own group" treatment `halfDecadeBucket` gives a real `0` review count. No currency symbol in the bucket label itself (`formatPriceTier`, e.g. `"5–15"` not `"$5–$15"`) — the selected region's currency isn't fixed to USD (see `tierCurrency`/`priceCurrency` above), and hardcoding "$" would mislabel every other currency's amounts. Tier Price's missing-bucket label is "Varies" (`formatMissingGroup(formatPriceTier, 'Varies')`) rather than the generic "—" the other price columns' missing bucket uses, matching `renderTierPrice`'s own "Varies ≠ no data" distinction. `PRICE_TIERS`/`priceTierBucket`/`formatPriceTier` live in `public/gameColumns.js`, shared by both pages (bundles.js's own `TIER_PRICE_COLUMN` reuses them too, for the one price column that isn't itself in the shared cluster).
  - **A hidden-by-default `priceStatus` column** (`computePriceStatus`, `public/gameColumns.js` — `PRICE_STATUS_COLUMN` is a single shared column object both pages insert into their own column list, not two copies) categorizes a row's current deal as `All-Time Low` / `1yr Low` / `3mo Low` (all three via the shared `dealRecordTier` — see `public/utils.js`'s own bullet above) / `On Sale` (a real discount that isn't, yet, any kind of historical low — the catch-all for a row that doesn't fit any of the other tiers) / `Not Discounted` (a confirmed `bestDealCut === 0`) / `—` (no price data at all, or `bestDealCut` itself unknown) — computed as a `value()` function, so it needs no new fetch or stored row field and stays correct across a refresh with no extra `markRowChanged` bookkeeping. Exists specifically so "which games are at their all-time low right now" (or any of the other tiers) is a direct filter/group instead of only ever eyeballed off the Best Deal cell's badge, which the column set's other price/discount columns individually can't answer either (Discount's own bucketed grouping only answers "how big a discount", not "is this a record").
    - **`PRICE_STATUS_TIERS`** (`gameColumns.js`) is the single ordered worst-to-best list backing both the column's sort and its visual treatment, so the two can't drift apart the way two separately-maintained arrays could — and, since its three record entries spread `color`/`icon`/`bold` straight off `DEAL_RECORD_TIERS` (`public/utils.js`, reversed to worst-to-best and prefixed with the `Not Discounted`/`On Sale` non-record labels) rather than restating them, it also can't drift from the Best Deal cell's own badge. `PRICE_STATUS_ORDER` (feeding `comparePriceStatus`, same "ordered array + `indexOf`" shape as `PRODUCTION_TIER_ORDER`/`PROTON_TIER_ORDER`) is just `PRICE_STATUS_TIERS.map(t => t.label)`, and `renderPriceStatus` looks a value's `color`/`icon`/`bold` up in the same list. `defaultSortDir: 'desc'` on the column shows All-Time Low rows first on a fresh click.
    - **`renderPriceStatus` reuses `renderBestDeal`'s own color/icon treatment verbatim** for the two tiers it already covers — bright teal + bold + 🔥 for All-Time Low, green + ★ for 1yr Low (`scoreColor(90)`/`scoreColor(70)`, the same "excellent"/"good" tiers) — extended one step further for 3mo Low: a real record, just over a shorter window, so it gets `scoreColor`'s next tier down (amber, `scoreColor(55)`) and an outline star (☆) instead of 1yr Low's filled one, reading as "still a record, just a lesser one" rather than an unrelated icon. On Sale and Not Discounted stay plain text — not being a record isn't a bad thing worth flagging, so nothing there competes for attention with the three genuine record tiers. `render` (not just `format`) also drives group headers for this column per the table library's own contract, so a grouped view shows the same colored/badged label as the cell would.
- The "‹"/"›" buttons next to the bundle title (`renderBundleNav` in `bundles.js`) step to the previous/next entry in the currently-loaded `bundles` array — not the full remote list, no auto-"Load more", no wraparound at either end. `activeBundleId`'s position is looked up fresh on every click/render rather than cached, so it stays correct as `bundles` itself changes (a new sort/country/"Include expired" reset, or "Load more" appending a page) — `renderBundleNav()` is called after both `openBundle` and `loadBundles` for exactly that reason. A bundle that isn't part of the loaded list at all (`indexOf` returns -1 — e.g. a `?bundle=` deep link to one the currently loaded page/sort/filter doesn't include) disables both buttons rather than guessing a position.
- The game table's view (visible columns, sort, grouping, filters) auto-persists locally via `prefs.js` (`bundlesTableView`) — one shared key rather than per-bundle, meant to be "how I like this table set up" carrying over from whichever bundle was open last to the next one, not per-bundle. Applied *after* `table.setViewState({ sorts: DEFAULT_SORT })` at table construction (`restoreTableView`, same ordering the old `syncViewToUrl` used) so the persisted view overrides the default sort when one exists, but the default still applies on a genuinely first-ever visit. Same "share on demand, not live-synced" model as the Library Explorer's own table views (see that section above) — a "🔗 Share view" button copies a link with the current view snapshotted into `?bv=`, never writing it to the page's own address bar (see that section's comment on why a link left in a live URL goes stale the moment the table changes again); `restoreTableView` consumes an incoming `bv` param once (applies it, seeds the stored default, strips it from the URL) since this page rebuilds its table on every bundle open (list click, ‹/›, a region-reopen), not just on a genuine page load. `resetTableView(table, TABLE_VIEW_PREF_KEY, TABLE_VIEW_PARAM)` (the page's "Reset view" button) clears both the stored pref and the live view back to construction defaults, and the `bv` param if present; `DEFAULT_SORT` is reapplied afterward the same way library.js's own reset button does, since blanking the view state clears sorts to none too and there's no construction-time option to make it preserve a non-empty default. (This used to persist via `@vates/data-table-vanilla`'s own `persistViewToLocalStorage`/`syncViewToUrl`/`resetView` helpers under a standalone `bundles:table-view` localStorage key — dropped in favor of `prefs.js` once table views needed to be one more thing a future per-key server sync could reach; the package's helpers have no way to route through a shared preference store instead of raw `localStorage`/the URL directly, so this page keeps its own small copy of that logic now, same as `library.js`'s.)
- Region selection is a small curated dropdown of major Steam pricing regions, not the full ISO 3166-1 list — ITAD's `country` param accepts any 2-letter code, but a bare 250-country dropdown is worse UX for a feature that only exists to compare prices at a glance. `COUNTRY_OPTIONS`/`TIMEZONE_COUNTRY`/`detectCountry`/`AUTO_COUNTRY`/`getStoredRegion`/`setStoredRegion`/`resolveRegion`/`initRegionSelect`/`REGION_CHANGED_EVENT` all live in shared `public/region.js` (a plain script, loaded on all four pages before `nav.js`, same convention as `esc()`/`reorderUrlParams` from `utils.js`/`urlState.js`) rather than duplicated per page. The actual `<select>` is only ever populated once, by `nav.js`'s own popover (see its bullet above) — Bundles and the Wishlist tab just read `getStoredRegion()`/react to `REGION_CHANGED_EVENT`, they don't call `initRegionSelect` themselves.
  - **One shared preference (`prefs.js`'s `'region'` key), picked from the nav bar's own ⚙ Preferences popover (`public/nav.js`) — not per-page, and not a URL param.** Bundles and the Wishlist tab used to each have their own inline `<select>`; both were removed once the nav popover existed as one global place to manage it, and now show only a read-only readout of the resolved region plus a "(⚙ Preferences to change)" hint. It's "what currency do I want to see prices in", a single user preference, unlike e.g. `bundlesTableView` (genuinely page-specific display state, and itself now also just a `prefs.js` key rather than its own standalone one — see the Bundles section above). Deliberately not shareable via URL either (an earlier version wrote it to `?country=`, mirroring `sort`/the old `view` param) — region says more about the viewer than about which bundle/wishlist they're looking at, so a shared link shouldn't override whatever the *recipient's* own region preference is.
  - **The dropdown's first entry is always `AUTO_COUNTRY` ("auto"), labeled "Auto-detect (⟨whatever it currently resolves to⟩)"** (`initRegionSelect`) — e.g. "Auto-detect (Europe / Germany (EUR))" — so picking it isn't a leap of faith, and it's the default when nothing has ever been explicitly chosen (`getStoredRegion`, falling back to `AUTO_COUNTRY` when storage is empty/unavailable/holds an unrecognized value). `resolveRegion(selected)` is the one place `detectCountry()` gets consulted for a *live* value — every actual upstream call resolves the picker's current value through it, so "Auto-detect" always tracks the current OS/browser signals rather than freezing whatever they resolved to at picker-population time. Picking a real region instead overrides auto-detection until switched back.
  - `detectCountry` itself is unchanged: tries the OS timezone first (`Intl.DateTimeFormat().resolvedOptions().timeZone`, via a curated `TIMEZONE_COUNTRY` map including a Eurozone-to-`DE` mapping) before falling back to `Intl.Locale(navigator.language).maximize().region` — language reflects a UI preference, not physical location, and very commonly stays "en-US" (or another English variant) regardless of where the user actually is (confirmed live: a machine with `LANG=en_US.UTF-8` but an OS timezone of `Europe/Paris`, which the language-only heuristic resolved straight to `US`).
  - The Eurozone entry's label leads with "Europe" (`Europe / Germany (EUR)`, not `Germany / EU (EUR)`) — `DE` is just the ISO code Steam/ITAD happen to key Eurozone pricing off, an implementation detail nobody picking a region cares about; the concept being selected is "Europe", not specifically Germany.
  - **Not every bundle actually follows it** — the currency on a tier/game price is whatever ITAD's upstream shop itself charges in, passed straight through; most shops (Humble, GreenManGaming, most Fanatical bundles) do switch currency per region, but some (verified live: a shop ITAD lists as "Digiphile", and at least one specific Fanatical bundle) only ever price in USD regardless of `country` — this is genuine upstream behavior, not a bug to "fix" by converting currencies client-side, and the page has a note next to the region picker explaining it.
- A bundle tier's `price` can be `null` even when the tier lists real games — this is **not** the same as free. In practice this is Fanatical's "Build Your Own ⟨N⟩ Bundle" pick-and-mix format: one tier, a pool of 15-30 games, price scales with however many you pick rather than being a fixed property of the bundle. A genuinely free/pay-what-you-want-or-more tier would carry an explicit `{amount: 0, ...}` price object instead (truthy, so it's grouped with priced tiers, not with the `null` case) — never observed in practice as of writing, but the correct thing to special-case if ITAD ever sends one. `cheapestTierPrice`/`fmtBundleListPrice` (bundle list) and `renderTierPrice`/the `tierPrice` column's own `format` (game table) both render `null` as "Varies"/"Price varies", reserving "Free" for an actual `amount === 0`. The `tierPrice` column also needs `compare: compareNumMissingLast` for this same reason — without it, `null` coerces to `0` under the column's default numeric comparator, which would sort every "Build Your Own" bundle's games as the single cheapest thing in the table under the default ascending Tier Price sort.
- An opened bundle shows two outbound links (`renderDetailLinks` in `bundles.js`): "View on IsThereAnyDeal ↗" (the bundle's `details` field, ITAD's own page for it) and "Get this bundle ↗" (`url`, the real shop/affiliate purchase link exactly as ITAD returned it — never rewritten or stripped of tracking params; ITAD's terms require passing prices/links through unmodified, same as the compliance note on the other third-party integrations in this file).
- Bundle listings, Steam-appid resolutions, and per-region price lookups share one cache tier (`BUNDLES_CACHE_TTL_MINUTES`, default 2 hours — see the Database section below) rather than each getting its own: a bundle can go live or expire at any time (shorter-lived than store metadata), while the appid mapping itself is closer to permanent, but it's cheap to over-invalidate the latter two in exchange for one fewer cache table.
- `BUNDLES_RATE_LIMIT_MAX` backs 4 separate `rateLimit()` instances (`bundlesListLimit`/`bundlesByIdLimit`/`bundlesResolveLimit`/`pricesLimit`), not one shared limiter — each `skip`s a request it can answer entirely from cache, by reconstructing that route's own cache key from the request and checking `getCached` directly (same "cache hits don't count" pattern `detailsLimit`/`gameSearchLimit`/`achievementsLimit` already use elsewhere in `server.js`). `pricesLimit` (named generically, not `bundlesPricesLimit` — see the shared-route bullet above) branches its `skip` on whichever of `gids`/`appids` the request actually sent, checking `itad-price:`'s cache key either way plus `itad-gid:` too for the `appids` case, since that route resolves appids to gids as its own internal step. This matters more here than it might look: simply reloading the Bundles page a handful of times re-requests the list and re-opens whatever bundle is deep-linked (`?bundle=`) every time, and without the skip, every one of those re-requests — even though none of them touch ITAD — counted against the same budget a genuinely new bundle open needs, silently 429ing it with no obvious cause. `bundlesByIdLimit` (`GET /api/bundles/:id`) is the one exception — `findBundleById`'s search walks a variable number of pages depending on where the id turns up, so there's no single cache key to check in advance; it gets a looser budget (`BUNDLES_RATE_LIMIT_MAX * 2`) instead of a skip, on the reasoning that deep links are a comparatively rare action next to list browsing, and the pages it walks are still individually cached underneath via `getBundles`.
- A failed `POST /api/prices` call (rate limited, transient upstream error) does not leave the Steam Price/All-Time Low/1yr Low/3mo Low columns stuck on `undefined` (rendered as "…", indistinguishable from "still loading") forever — `loadPrices`'s catch block (`bundles.js`) sets every resolved row's price fields to `null` (rendered "—", same as any other "no data" case) and writes a visible explanation to `#price-status`, a dedicated status line kept separate from `#detail-status` (which `streamGameDetails`'s own progress messages would otherwise overwrite). `library.js`'s own `loadWishlistPrices` does the same for the Wishlist tab's own `#price-status`.
- **`@vates/data-table-vanilla`'s `setData` only re-renders a row's cells when the object at its rowKey is a genuinely *new* reference** — mutating an existing row object in place and calling `setData` again with an array that still contains that same reference (even a brand-new outer array from `.filter()`) does not update its already-rendered cells, confirmed live by directly inspecting a row's in-memory state (correct) against its rendered DOM (stale). This bites `bundles.js` specifically because a row can become visible (via `streamGameDetails`, all fields set atomically in one `applyDetailsEvent` call) *before* `loadPrices`'s later, separate mutation of that same row's price fields — the common case once everything is cache-warm and both requests resolve near-instantly, so the ordering isn't a rare edge case.
  - The naive fix — blanket-copy every visible row on every `setData()` call — technically works but is wrong two ways: it forces a full-table re-render on every single streamed event instead of just the row that changed, and it breaks object identity for anything reading a row back from the table (`onRowClick`'s row is a fresh, different copy every render, so a row opened in the panel would silently drift from `rowMap` the next time anything else about it streamed in).
  - The actual fix is a per-appid `tableRowCache` (`bundles.js`): `visibleRowsForTable()` reuses a row's cached copy verbatim across renders until `markRowChanged(appid)` is called for it, at which point a fresh copy is made — so only the row that actually changed gets a new reference, and every other row's DOM is left alone. `rows`/`rowMap` keep the stable, mutated-in-place object identity everything else needs (the panel re-renders by reading fields straight off whatever object `panelOpen` was called with, and it must stay the same reference across a refresh) — `onRowClick` explicitly looks the canonical `rowMap` object back up by appid before opening it (rather than trusting whatever copy the table's click handler passed), so `onRefresh`'s mutation lands on the same object `rowMap` does, not a disconnected copy.
  - **Every mutation site must call `markRowChanged` right after mutating — including `streamGameDetails`'s own first-time reveal of a row, not just `loadPrices`/`onRefresh`.** This isn't optional even though a fresh reveal looks like it should be covered by `visibleRowsForTable`'s own "no cache entry yet" fallback: `loadPrices` and `streamGameDetails` run concurrently (`Promise.all` in `openBundle`), and on a cache-warm bundle `loadPrices` (one cheap batched ITAD call) routinely resolves *before* `streamGameDetails` (several real per-game Steam/HLTB calls) reveals that same row. If `loadPrices` calls `markRowChanged` first, it creates a cache entry from the row's still-`loading` snapshot; by the time `streamGameDetails` later flips it visible, the cache already "has" an entry, the fallback never fires, and the row is permanently stuck on that premature snapshot — missing ratings/HLTB/genres/etc. entirely. Confirmed live exactly this way before `streamGameDetails` was given its own `markRowChanged` call.
  - `library.js` now carries the identical fix (its own `tableRowCache`/`markRowChanged`/`visibleRowsForTable`, plus `onRowClick: row => openGame(rowMap.get(row.appid) ?? row)`) — added once the Wishlist tab's own price loading (`loadWishlistPrices`, see "Wishlist pricing" below) gave it a second async source that mutates an already-visible row, on top of the pre-existing "↻ Refresh" path (`onRefresh` in its `initPanel` call) which had the exact same latent risk but never actually hit it before, since a plain load never mutates a row again after it first becomes visible. `visibleRows()` itself is unchanged and still returns the canonical `rows`/`rowMap` objects directly — it's now explicitly documented as the one nav/random-pick/`onRowClick` callers must use instead of `visibleRowsForTable()`, precisely because those need the same reference the panel keeps displaying, not a copy that further mutations would stop reaching.

### Wishlist pricing (Library Explorer)

The Library Explorer's Wishlist tab shows the same IsThereAnyDeal-backed price columns Bundles does — Best Deal, Discount, Steam Full Price, All-Time Low, 1yr Low, 3mo Low, Price Status (with the same all-time/1yr-low 🔥/★ badge on Best Deal) — because both pages insert the literal same `PRICE_COLUMNS` array (`public/gameColumns.js`, see its own file-listing bullet above) into their own column list via `insertColumnsAfter`, right after Wishlist Rank on this page — the same relative "right before Scores & reviews" position `bundles.js` gives it, right after its own Tier Price/Add-on. There is no `library.js`-local price-column code left to drift out of sync with `bundles.js`'s own copy the way there used to be. Best Deal and Discount are visible by default (`WISHLIST_DEFAULT_VISIBLE`), same as Bundles; Steam Full Price, the narrower-window lows, the shop name, and Price Status stay hidden. Every price/discount column here is groupable with the same bucketing (`PRICE_TIERS` staircase / fixed 25-point Discount step) as Bundles, for the obvious reason that it's the exact same column objects — see that section's own bullet above (there's no Tier Price column here, so no "Varies" missing-label special case). Opening a wishlist row's side panel shows the same numbers again in its own Price section — see `panel.js`'s own bullet above for how that's wired (passive, off the exact same row fields this section sets).

- **A wishlist row only has a Steam appid, not an ITAD game id** — the reverse of a bundle's own games, which start as ITAD gids and get resolved *to* a Steam appid (`resolveSteamAppIds`, `/api/bundles/resolve`). `loadWishlistPrices` (`library.js`) instead calls the shared `POST /api/prices` with `appids` (see the shared-route bullet above), which resolves them to gids server-side first via `resolveItadIds` before running the identical price lookup — so nothing in `library.js` itself ever sees a raw ITAD gid.
- **Region readout**: a read-only label (`#wishlist-region-label`, `updateWishlistRegionLabel`) next to the tabs, showing whatever `resolveRegion(getStoredRegion())` currently resolves to — the actual picker lives in the nav bar's own ⚙ Preferences popover now (see the Bundles section's own region-selection bullet above), not on this page; a `window.addEventListener(REGION_CHANGED_EVENT, ...)` listener keeps this label and the loaded wishlist's prices (`loadWishlistPrices`) in sync with it regardless of which UI changed it. Hidden on the Library tab (no price columns there) and hidden outright when ITAD isn't configured (`itadConfiguredPromise`, a `GET /api/health` check fired once at module load and awaited wherever it matters, never rejecting — a failed health check is treated the same as "not configured"), rather than showing a readout for a feature that isn't running.
- **Changing region re-prices the currently-loaded wishlist in place** (`loadWishlistPrices(rows)`, called again from the `<select>`'s own `change` handler, which also calls `setStoredRegion`) rather than reloading the whole tab — there's no bundle-detail-view/list-collapse state to juggle the way Bundles' own region change has (see its own section above), just the one already-loaded table's price columns going back to "…" until the new country's prices land.
- **No ITAD key configured at all**: `loadWishlistPrices` fills every row's price fields with `null` (rendered "—", same as any other "no data" case) rather than attempting a request bound to 503 or leaving the columns stuck on their loading placeholder forever — same reasoning as a failed price lookup elsewhere in this file, just checked proactively instead of caught after the fact.
- **Chunked client-side into batches of `MAX_PRICE_LOOKUP_GAMES` (500, mirroring the server's own cap)**, run sequentially rather than in parallel — unlike a bundle's game list (which never exceeds the cap and so bundles.js's own `loadPrices` always sends everything in one call), a Steam wishlist can run well past it, and firing several chunks at once would just be several concurrent ITAD-backed requests for no benefit.
- Runs concurrently with `streamGameDetails` (`Promise.all` in `loadWishlist`), same "pricing has nothing to do with ratings/HLTB/tags" reasoning as Bundles' own `openBundle`.

### Database (`db.sqlite`)

`db.sqlite` is the application database, opened via the built-in `node:sqlite` module (`DatabaseSync`). It currently holds only cache tables, but is intentionally named `db.sqlite` (not `cache.db`) to accommodate non-cache data in the future. WAL mode is enabled for better concurrent write throughput. Cache entries are evicted at startup and lazily on read; every write goes directly to SQLite (no debounced flush). Set `DB_FILE=` (empty) in `.env` to use an in-memory database. Cache TTLs:

| Key prefix | TTL env var | Default | Reason |
|---|---|---|---|
| `resolve:` | `RESOLVE_CACHE_TTL_MINUTES` | 90 days | Steam ID resolution — essentially permanent |
| `rating:` | `RATING_CACHE_TTL_MINUTES` | 30 days | Steam review scores — drifts slowly |
| `hltb:`, `meta:`, `browse:`, `tagnames:` | `META_CACHE_TTL_MINUTES` | 60 days | Store metadata, HLTB, tags, demo link — rarely changes for an existing game |
| `games:`, `player:`, `wishlist:` | `LIBRARY_CACHE_TTL_MINUTES` | 6 hours | Changes when users buy games / edit their wishlist |
| `search:` | `SEARCH_CACHE_TTL_MINUTES` | 1 day | Game name → appid search results — much shorter than the other game-details tiers since new games ship regularly |
| `news:` | `NEWS_CACHE_TTL_MINUTES` | 6 hours | Recent news/announcements for a game — changes far more often than store metadata (patch notes, event posts), so it shares the library tier's cadence rather than the 60-day META one above |
| `itad-bundles:`, `itad-shop:`, `itad-appid:`, `itad-gid:`, `itad-price:` | `BUNDLES_CACHE_TTL_MINUTES` | 2 hours | IsThereAnyDeal bundle listings, the Steam shop id, appid↔gid resolutions (near-permanent in reality, but cheap to over-invalidate alongside the shorter-lived bundle/price data — see the Bundles section above), and per-region price lookups |

Run `npm run cache:clear` to wipe all cache entries without deleting the database file.

These TTLs are generous because both `getCached` and every `lib/steam.js`/`lib/hltb.js`/`lib/itad.js` fetch function accept `{ force: true }` to bypass the cache read for one call (the fetch still writes fresh data back to the cache). This backs three user-facing "↻ Refresh" affordances rather than being needed for background freshness:

- The **accounts bar's per-account "↻"** (both pages, see `public/accountsBar.js`) re-POSTs `/api/common-games`/`/api/wishlist` with `refreshIds: [steamid, ...]`, forcing fresh owned-games/player/wishlist data for just that one account rather than every account in the search. `getPlayerSummaries` takes a matching `forceIds` option so a single `GetPlayerSummaries` batch call can bypass the cache for only the listed IDs. (There used to be a coarser search-bar-level "↻ Refresh" button on both pages forcing the whole search; it was removed in favor of this once the accounts bar existed to hang a per-account control on.)
- The **side panel's Refresh button** re-fetches `GET /api/game-details/:appid?refresh=1`, forcing fresh rating/HLTB/store metadata/tags for that one game only, and in parallel `GET /api/game-news/:appid?refresh=1` for that game's news (see `handlePanelRefresh` in `panel.js`) — two separate requests since news isn't part of `fetchGameDetails` (see the panel.js bullet above). Both always count against their respective rate limiters (`DETAILS_RATE_LIMIT_MAX`/news's own limiter sharing that same budget) — the cache-hit skip is disabled for `refresh=1`, since a forced call never is a cache hit.
- The **Bundles page and Library Explorer Wishlist tab's page-level "↻ Refresh prices" button** (next to Reset view, `refreshPricesBtn` in `bundles.js`/`library.js`) re-POSTs `/api/prices?refresh=1`, forcing fresh ITAD pricing for every game currently loaded — bundles.js re-sends the open bundle's own `currentResolvedGames`, library.js re-sends the loaded wishlist's `rows`, so no re-resolution or re-streaming of ratings/HLTB/tags happens, just the one already-batched price call again. Deliberately one page-level control rather than per-game (unlike rating/HLTB/tags, which do differ enough per game to warrant the panel's own per-game refresh) — pricing is already fetched as a single batch call for the whole page, so refreshing it per-game would only add friction with no matching benefit. `force` only bypasses `itad-price:`; it deliberately does *not* force `itad-gid:`/`itad-appid:` appid↔gid resolution (see the route's own comment in `server.js`) — that mapping is closer to identity data than price data and near-permanent in practice, so forcing it on every price refresh would be an extra upstream call for nothing, same reasoning as the bullet just below about `resolve:`. `pricesLimit`'s cache-hit skip is disabled the same way for `refresh=1`.

None of the three refresh paths touch `resolve:` — a vanity-URL mapping isn't expected to change, so there's no user-facing reason to force it.

### Monitoring — GET /api/metrics

`lib/metrics.js` counts every outbound HTTP request this app makes to a third-party service (Steam, HLTB, ITAD, ProtonDB) — a plain in-memory counter, not persisted to `db.sqlite`, the same in-memory-singleton trade-off `lib/dedup.js`'s in-flight map and `lib/steam.js`'s `storeLimit`/`tagLimit`/`protonLimit` semaphores already make. `trackedFetch(group, label, url, opts)` is a drop-in replacement for a bare `fetch(url, opts)` call (same signature/return value) that every fetch call site in `lib/steam.js`, `lib/hltb.js`, and `lib/itad.js` now goes through instead of calling `fetch` directly. `GET /api/metrics` composes this with several other signals — inbound rate-limiter trips, dedup coalescing, semaphore contention, cache effectiveness — each covered in its own paragraph below, so a session reviewing this endpoint for a suspected issue has more to go on than outbound request/status counts alone.

Counts are nested two levels — `group` (the trust-tier/routing boundary: `steam-store` for `fetchStoreApi`/`storeLimit`, `steam-browse` for `fetchStoreBrowseItem`/`tagLimit`, `steam-api` for the rest of the documented+keyed `api.steampowered.com` calls, `protondb`, `hltb`, `itad`) and then `label` (the specific function making the call, e.g. `resolveItadIds` vs. `getPrices` within `itad`) — so a stall in one specific operation is visible rather than folded into one flat per-service count; e.g. ITAD resolving ids fine while price lookups fail shows up as one label's count moving and the other's staying flat, rather than both being indistinguishable under a single `itad` total. `fetchStoreApi` is called by four different `steam-store` functions (`getGameRating`, `getAppDetails`, `searchStoreGames`, `getTagNameMap`), so it takes `label` as a second parameter from each caller rather than hardcoding one.

Time buckets live at the *root* of the response, and *only* at the root — every windowed signal this endpoint exposes (outbound `groups`, `rateLimiters`, `dedupHits`, `cacheHits`) nests under `sinceRestart`/`lastHour`, not the other way around. `sinceRestart` holds lifetime totals, never trimmed; `lastHour` holds the same breakdown recomputed from a per-event `{ts, ...}` list kept alongside the lifetime counters (trimmed to the trailing hour on every write and re-filtered by timestamp on every read — so a read reflects the last hour correctly even after a long idle stretch with no new writes to trigger a trim). Earlier drafts put the window at the root for `groups` but nested `sinceRestart`/`lastHour` *inside* each named entry for `rateLimiters`/`dedupHits`/`cacheHits` instead — an inconsistency: reviewing "what happened in the last hour" meant one direct read for outbound requests but digging into every limiter/dedup-instance/cache-group name for the other three. One convention throughout fixes that: `sinceRestart`/`lastHour` are always the outermost keys, whatever's underneath (`groups`, `rateLimiters`, `dedupHits`, `cacheHits`) is always a plain `{name: ...}` or `{group: ...}` map with no bucket of its own. A single one-hour window was chosen over several (5 min/day/week were considered) — it answers "is this happening right now" without the extra bookkeeping multiple windows would need, and `sinceRestart` already covers the "since the process started" end of the range. A per-group total (summed across its labels) was tried and dropped — it added a `total`/`labels` wrapper layer under every group for something trivial to compute client-side by summing that group's labels, so each label sits directly under its group instead.

Each label entry carries `requests`, `statusCounts` (a `{ [httpStatus]: count }` map), `networkErrors` (a count of `fetch()` itself throwing — timeout, DNS, abort), and `avgLatencyMs`/`maxLatencyMs` (measured around the `fetch()` call itself, covering every outcome — a success, a non-2xx status, and a thrown network error all still take real time, so all three feed the same latency figures; only the outcome-specific counters branch on status). `statusCounts` is deliberately not collapsed into one "errors" number: plenty of non-2xx responses in this app are expected business outcomes for a given label, not failures (`getPlayerAchievements`/`getGlobalAchievementPercentages` treat 403 as "private profile"/"no stats", `getProtonDbStatus` treats 404 as "no reports yet" — see their own comments in `lib/steam.js`), and folding those into a generic error count would bury a genuine problem (e.g. a run of 429s on `steam-store`) under routine, often high-volume traffic. Read a label's `statusCounts` against what CLAUDE.md/the code already documents as expected for that specific endpoint. `networkErrors` has no such ambiguity — no endpoint treats a thrown fetch error as a valid outcome — so it does get its own counter too. `avgLatencyMs`/`maxLatencyMs` exist because a run of slow-but-200 responses (an upstream degrading before it starts actually erroring) is otherwise invisible in `statusCounts` alone — `maxLatencyMs` in particular surfaces a single bad outlier that an average would dilute away.

`GET /api/metrics` exposes `{ since, sinceRestart: { groups: { [group]: { [label]: { requests, statusCounts, networkErrors, avgLatencyMs, maxLatencyMs } } }, rateLimiters: { [name]: count }, dedupHits: { [name]: count }, cacheHits: { [group]: { hits, misses, forced } } }, lastHour: { ... same shape as sinceRestart ... }, cacheEntries: { [group]: count }, circuitBreakers: { 'steam-store': { blockedUntil, tripCount, consecutive403s } }, semaphores: { store, tag, proton: { active, queued, maxQueueSeen, rejected } } }` — no auth, same trust level as `GET /api/health`. Resets on every restart (except `cacheEntries`, read straight from `db.sqlite` — see its own paragraph below); there's no historical/persisted view beyond the trailing hour otherwise. A label/name/group with no events yet is simply absent from its map rather than present with zeroed counts. `circuitBreakers`/`semaphores`/`cacheEntries` sit outside both `sinceRestart`/`lastHour` — they're live snapshots (a current queue depth, a current block-until timestamp, a current `db.sqlite` row count), not windowed counters, so there's no "since restart" vs. "last hour" version of any of them to bucket. `circuitBreakers['steam-store'].blockedUntil` (0 when not tripped) is `fetchStoreApi`'s existing 403-storm circuit breaker (see the comment above `storeConsecutive403s` in `lib/steam.js`) surfaced directly — "is steam-store blocked right now" is a more immediately actionable signal than reconstructing it from `statusCounts` history, and it's composed into the route in `server.js` (via `getStoreCircuitBreaker`) rather than folded into `lib/metrics.js` itself, since that state is owned by `lib/steam.js`, not the request counters. `tripCount` is the lifetime complement to `blockedUntil`'s current-state-only snapshot — `blockedUntil: 0` alone can't tell "never tripped" apart from "tripped once, ages ago" from "tripping every 20 minutes", all of which look identical once the circuit has closed again. `consecutive403s` is the pre-trip state: a single 403 doesn't trip the breaker at all (it takes 2 in a row), so without it a run of isolated single 403s — each one resetting on the very next non-403 — is indistinguishable from zero 403s in `blockedUntil`/`tripCount` alone; it gives an early-warning window ("currently at 1, one more trips it") before the breaker actually opens.

**Inbound counterpart — our own rate limiters.** `rateLimiters` is the mirror image of the outbound `statusCounts`: how often server.js's own `express-rate-limit` instances actually rejected a client request, not how often a third party rejected *us*. Tracked via `recordLimiterTrip(name)` (`lib/metrics.js`), called from a `handler` every one of the 9 limiter definitions in `server.js` gets via a shared `namedRateLimit(name, opts)` wrapper (mirroring express-rate-limit's own default handler — status + message — after recording the trip) rather than repeating a `handler` on each definition. Kept separate from `groups`/`counterFor`: it's a different axis (self-imposed inbound limits vs. calls to a specific outbound service) that would otherwise make a group name like `steam-store` ambiguous between "calls we made" and "requests we rejected". Limiter names: `search`, `details`, `news`, `gameSearch`, `achievements`, `bundlesList`, `bundlesById`, `bundlesResolve`, `prices` — matching the `const ...Limit` variable names in `server.js` minus the `Limit` suffix. Only trips (a `skip()` that returned false *and* the request was over budget) are counted, not every request the limiter saw — same reasoning `detailsLimit`'s own "cache hits don't count" skip already applies to the budget itself, carried through here.

**Dedup coalescing.** `dedupHits` counts how often `lib/dedup.js`'s `createDedup()` actually coalesced a concurrent call into an already-in-flight one, per named instance — `lib/steam.js`'s is `'steam'`, `lib/itad.js`'s is `'itad'`. `createDedup(name)`'s `name` is optional and purely for this; most test call sites omit it and simply opt out of being tracked. Windowed the same `sinceRestart`/`lastHour` way as `rateLimiters` — an unusual burst of coalescing (many concurrent duplicate calls for the same key, e.g. a retry loop or a buggy polling client) is itself a "is this happening right now" signal, not just background context a lifetime total would convey just as well. `rateLimiters` and `dedupHits` share one `createNamedCounter()` helper in `lib/metrics.js` (a lifetime count + the same `recent[]`/`pushRecent` windowing machinery `trackedFetch` uses) rather than each keeping a separate, near-identical copy of that bookkeeping — its `summarizeSinceRestart()`/`summarizeLastHour()` each return a flat `{name: count}` map (not a `{name: {sinceRestart, lastHour}}` map), so `getMetrics()` can slot each straight into the root `sinceRestart`/`lastHour` bucket alongside `groups` rather than nesting a bucket inside every name.

**Semaphore contention.** `semaphores` exposes `lib/steam.js`'s `storeLimit`/`tagLimit`/`protonLimit` concurrency semaphores' own live + lifetime stats via `getSemaphoreStats()`: `active`/`queued` (current snapshot), `maxQueueSeen` (a lifetime high-water mark on queue depth, since a live snapshot alone can read as "fine" even if the queue was deep moments earlier), and `rejected` (a lifetime count of calls actually turned away by the `maxQueue` safety valve — see `createSemaphore`'s own comment on why that valve is deliberately generous, meant to stay at 0 in practice; a nonzero value means it's actually firing, which had zero visibility before this counter existed). `active`/`queued`/`maxQueueSeen` tell a slow-upstream problem apart from a self-inflicted concurrency-cap bottleneck: high `avgLatencyMs` on `steam-store` with a consistently near-zero `queued` means the upstream itself is just slow; a `queued`/`maxQueueSeen` that's regularly high means requests are piling up behind these limits instead. `createSemaphore` is exported from `lib/steam.js` purely for direct unit testing (same "exported so tests can exercise it directly" reasoning as `lib/hltb.js`'s own exported `stringSimilarity`/`levenshtein`) — real contention on `storeLimit`/`tagLimit`/`protonLimit` themselves is exercised through the real Steam/ProtonDB-backed functions built on top of them, but `rejected`'s `maxQueue`-saturation path is impractical to reach that way (`SEMAPHORE_MAX_QUEUE` is deliberately 20000-deep), so it's tested against a small throwaway semaphore instead.

**Cache effectiveness.** `cacheHits` is a per-group (`library`, `resolve`, `rating`, `meta`, `search`, `news`, `bundles`, matching the `label` on each entry in `lib/cache.js`'s `GROUPS`) `{ hits, misses, forced }` breakdown of every `getCached()` outcome, tracked via `recordCacheEvent(group, outcome)` — kept in `lib/metrics.js`, not as a local counter in `lib/cache.js` itself, so it gets the same `sinceRestart`/`lastHour` windowing every other append-only counter here gets (via its own `recent[]`/`pushRecent` bookkeeping — the three sub-outcomes per group don't fit `createNamedCounter`'s one-bare-count-per-name shape, so this stays a separate implementation rather than being forced into it, though it follows the same "return a flat `{group: {...}}` map per bucket, no bucket nested inside" convention `createNamedCounter`'s two summarize functions use). A cache hit-rate collapse is exactly the "is this happening right now" kind of signal `lastHour` exists for elsewhere in this file: a lifetime-only average would let a regression that started an hour ago sit invisibly diluted under however long the process has been running (some of these TTLs run up to 90 days), the same blind spot `lastHour` already solves for outbound requests and rate-limiter trips. Without it at all, "outbound `steam-store` requests doubled" is ambiguous between "traffic genuinely grew" and "the cache stopped doing its job" (a misconfigured TTL, an eviction bug, a route calling `{ force: true }` more than expected) — both look identical from the outbound counters alone. `forced` is its own bucket, not folded into `misses`, since a forced bypass (a user-clicked "↻ Refresh" — see the Database section below) is an intentional, expected action, not the cache failing to do its job. Named distinctly from `GET /api/health`'s own `cache` field — a different shape (a flat `{ entries }` count there vs. this per-group, windowed hit/miss/forced breakdown) that would be confusing to conflate under the same key across the two endpoints.

**Cache entry counts.** `cacheEntries` (`{ [group]: count }`, via `lib/cache.js`'s `getCacheEntryCounts()`) is a per-group row count read straight from `db.sqlite`, not an in-memory counter — unlike everything else on this endpoint, it doesn't reset on restart and always lists every group, even one `cacheHits` hasn't seen a read for yet this session. `getCacheStats()` (backing `GET /api/health`'s lighter `{ entries }` field) now derives its total from this same function rather than querying row counts a second time. Read alongside `cacheHits`, this is what tells apart "few entries, lots of misses" (a TTL too short, evicting before reuse) from "many entries, lots of misses" (a large/low-locality key space the cache structurally can't help much with) — neither is distinguishable from hit/miss counts alone.

### Server logs — proactive warnings, and avoiding per-request spam

Most of the above is pull-based (`GET /api/metrics` has to be read by someone/something); two discrete, already-tracked events also get a `console.warn` right at the moment they happen, so they show up in the logs without anyone having to go look:

- **`[circuit-breaker] steam-store tripped ...`** — logged once, in `lib/steam.js`'s `fetchStoreApi`, at the exact point `storeTripCount` increments (not per blocked request afterward — see below). Includes the ISO timestamp it's blocked until.
- **`[semaphore:<name>] queue saturated ...`** — logged every time `createSemaphore`'s `maxQueue` safety valve actually rejects a call (`store`/`tag`/`proton`, matching `getSemaphoreStats()`'s own keys). Not throttled, unlike the two below — `maxQueue` is deliberately generous (`SEMAPHORE_MAX_QUEUE`), so this is expected to fire essentially never; each occurrence is individually noteworthy rather than repetitive.

Both are `console.warn` (not `console.error`) — same tier as the pre-existing `[HLTB]` warnings in `lib/hltb.js`, a degraded-but-recoverable condition rather than a bug.

Adding the circuit-breaker warning surfaced a real redundancy in the pre-existing per-request error logging: once `steam-store`'s circuit is open, every request that touches it for the next 5 minutes throws the same "rate limited (circuit open)" error, and — before this — each one logged its own `[upstream:...]`/`[game-details]` line via `routeErrorStatus` (`server.js`) and `fetchGameDetails`'s own `logErr`. For a large batch load (rating + meta both go through `fetchStoreApi`, once per appid), that's potentially hundreds of near-identical lines repeating information the one-time trip warning already recorded. Fixed by marking that specific error `isCircuitOpen: true` at its single throw site in `fetchStoreApi`, and having both consumers skip logging (but still return the right status/null fields) when they see it — the same "expected, already-explained outcome, not new information" treatment `isClientError` already gets in `routeErrorStatus`.

A second, separate spam source: `lib/hltb.js`'s per-search `"[HLTB] search failed for ..."` warning had no backoff — unlike the auth-init failure path (already throttled via `_hltbAuthFailedAt`/`HLTB_AUTH_RETRY_MS`), a systemic HLTB outage or block *during* search (auth still valid, but the search endpoint itself rejecting everything) would log once per game in whatever library/comparison is loading. Fixed with its own throttle (`_hltbSearchWarnedAt`/`HLTB_SEARCH_WARN_THROTTLE_MS`, same 30s window, tracked separately since an auth failure and a search failure are different failure classes) — the search itself still runs and still throws normally every time; only how often the warning *prints* is throttled.

Reviewed and left as-is: `[unhandled rejection]`/`[bug:...]`/`[timeout:...]` (genuine bugs or backstops, expected to be rare — logging every occurrence is exactly right); the one-time startup errors/banner; `[HLTB] init failed` (already throttled via the same auth backoff). Deliberately *not* added: log-based warnings for cache hit-rate collapse or latency degradation — both are trend metrics with no single discriminating event to hang a log line on; reviewing `GET /api/metrics` (by hand, or by asking an agent to) is the right tool for those, not trying to get the app to self-diagnose trends via logs.

### URL / sharing

Players are encoded as `?u=` query params. A single-account player is `?u=alice`; a multi-account slot (Steam Family) is `?u=alice,bob_family` (comma-joined). Old single-account URLs are fully compatible. Members within each slot and slots themselves are sorted alphabetically so the same comparison always produces the same URL. `history.pushState` is used for explicit searches; `pushState: false` is used when restoring from URL on load or back/forward navigation to avoid polluting history. Every URL-writing function on both pages runs its params through `reorderUrlParams` (`public/urlState.js`) before writing, so the same state always produces byte-identical query strings regardless of write order. `sort` is omitted from the URL entirely when it matches the default (`score` descending) rather than always spelling out `-score`.

The Library Explorer (`public/library.js`) pushes exactly one history entry per genuine new action (Load button, recent-search click, tab switch, per-account refresh is `push: false`) instead of the 2-3 partial `updateUrlParams` pushes each of those used to fire (clearing `game`/`shot`, then setting `u`, then `tab` — each its own entry); everything else (panel open/close, lightbox step, restoring from a URL/back-forward navigation) uses `replaceState`. A `popstate` listener (`loadFromUrl`, mirroring `app.js`'s own) makes browser Back/Forward actually work on this page — previously the URL changed on every action but nothing reacted to History API navigation at all.

Table view state (`?lv=`/`?wv=` on the Library Explorer, `?bv=` on Bundles) is the one deliberate exception to "the URL reflects current state" above — see each page's own section for why it's share-on-demand only, not continuously synced.

## Working style

- Be concise: short responses, no filler, no restating what was just done.
- Suggest Claude Code plugins, skills, or agents when relevant to the task at hand.
- When asked a question, answer it — don't jump straight to implementing.
- When a request is ambiguous, ask clarifying questions **one at a time** before proceeding.
- Don't re-read a file already read in the current session unless it may have changed.
- When there are multiple valid approaches, present the options and trade-offs and wait for a choice before implementing.
- For non-trivial changes (multiple files, non-obvious design decisions, refactors), outline a brief plan and get confirmation before implementing. Trivial/obvious edits can proceed directly.
- Stay in scope: only make the changes asked for. Flag other issues noticed rather than fixing them unprompted.
- Match the existing code style and conventions in the file/project rather than imposing personal preference; don't reformat unrelated code.
- Ask before adding a new dependency; prefer what's already in use.

## Git workflow

- Make commits atomic: each commit represents one logical change.
- Write descriptive commit messages that explain the *why*, not just the *what* — a short subject line, with a body when context is needed.
- Commit directly to `main` — this is a solo repo with no PR/review process; there's no history of feature branches being merged back in, even for large multi-file changes (e.g. the whole Bundles subsystem landed as direct commits).
- Only commit or push when explicitly asked.
- Never commit secrets, credentials, API keys, or `.env` values.
- Update `CHANGELOG.md` in the same commit as the code change it documents (see "Changelog" below) — never as a separate follow-up commit.
- If a change is accidentally left out of a commit that was just made, amend that commit (`git commit --amend`) rather than adding a separate fixup commit for it.

## Development workflow

After making changes:

1. Check whether existing tests need updating, or new ones are needed, to cover the change, then run `npm test` and report actual results — not assumptions.
2. Update any affected documentation (this file, `README.md`, `CHANGELOG.md`) — see "Knowledge sharing" above for where things belong.
3. A `pre-commit` git hook (plain shell script at `.git/hooks/pre-commit`, not a package like Husky — this repo has no dependency for it) runs `npm test` automatically and blocks the commit on failure; there's still no linter/formatter configured. The hook lives under `.git/`, so it isn't version-controlled — it needs to be recreated after a fresh clone (see the snippet in this repo's own `.git/hooks/pre-commit` if you need to reproduce it elsewhere). Once step 1 above has already confirmed tests pass, don't run `npm test` again immediately before `git commit` just because a commit is about to happen — the hook already re-runs it and blocks on failure, so a run whose only purpose is "will this commit succeed" is redundant with the hook, not an extra safety margin.
