# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the app

```bash
echo "STEAM_API_KEY=your_key_here" > .env   # first time only — only required setting
npm install                                  # first time only
npm start                                    # or: npm run dev  (restarts on file changes)
```

The server binds to `http://127.0.0.1:3000` by default. `default.env` (committed to the repo) holds all settings with their defaults and documentation. Create `.env` (gitignored) with only the values you want to override — `STEAM_API_KEY` is the only required one. The server exits immediately at startup with a clear error message if it is missing.

- **`lib/cache.js`** — Persistent cache (`getCached`, `setCache`), disk I/O, process exit hooks.
- **`lib/config.js`** — TTL constants (`LIBRARY_CACHE_TTL_MS`, `RESOLVE_CACHE_TTL_MS`, `RATING_CACHE_TTL_MS`, `META_CACHE_TTL_MS`, `SEARCH_CACHE_TTL_MS`) shared across modules.
- **`lib/dedup.js`** — In-flight request deduplicator (`createDedup`): concurrent calls for the same key share one promise.
- **`lib/steam.js`** — Steam API calls (`resolveSteamId`, `getOwnedGames`, `getWishlist`, `getPlayerSummaries`, `getGameRating`, `getAppDetails`, `getSteamSpyTags`, `searchStoreGames`, `getGameNews`).
- **`lib/hltb.js`** — HLTB auth + search (`getHLTB`), plus exported `stringSimilarity` and `levenshtein` for unit testing.
- **`lib/groupGames.js`** — Groups slot libraries by exact ownership set (`groupByOwnership`).
- **`public/index.html`** — Single-page frontend shell (vanilla JS, no framework).
- **`public/app.js`** — Main frontend JS: search flow, SSE streaming, rendering, filtering/sorting, URL state, and the page-specific parts of the side panel (owner list, tag-click filtering, prev/next/random nav bar) built on top of `panel.js`. Also wires up the accounts bar and recent-searches row from `accountsBar.js` (see below) — the accounts bar is grouped by slot (`renderAccountChipsGrouped`), each slot rendered in its own bordered box (`.slot-accounts` in `style.css`) rather than flowing inline with the next slot's chips, labelled `Player N` once there's more than one slot to tell apart (a comparison can involve several separate slots) and/or `N accounts merged` whenever a slot itself unions more than one account (a Steam Family) — without the box + merge count, a family merge (one slot, several accounts) and a plain multi-player comparison (one account per slot) rendered as the same flat, unlabelled-or-thinly-labelled row of chips. A recent-search entry stores the whole normalized slot array so clicking it rebuilds every slot/family input row via `addPlayerSlot`. `updateTitle()` keeps `document.title` in sync: an open game's name takes over the title entirely; otherwise it falls back to the loaded slot names, then the bare app name with nothing loaded. `updateLibraryExplorerLink()` keeps the header's "Library Explorer →" link (`#library-explorer-link`, index.html) pointed at `/library.html?u=<ids>` for the single player/Family currently loaded, falling back to the bare link for a multi-player comparison (which the Library Explorer has no notion of).
- **`public/panel.js`** — Shared game detail side panel: `initPanel(options)`, `panelOpen(game)`, `panelClose(opts)`, `isPanelOpen()`, `getPanelGame()`, `panelStepHero(dir, { wrap })`, `pickRandomFrom(list, queueKey, currentAppid)`/`clearRandomQueue`/`clearAllRandomQueues`. Renders the hero carousel, score/HLTB/news/tags/links body, and handles swipe gestures; used by both `app.js` and `library.js`. Page-specific bits (owner list, tag-click filtering, nav bar) are supplied via `options` or layered on by the host page wrapping `panelOpen`/`panelClose`. `panelClose()` itself is called from more places than just host code — the backdrop click, × button, and swipe-to-close are all bound straight to it — so `options.onClose` is the one hook guaranteed to run on every close path, not just whichever one a host happens to wrap; both `app.js` and `library.js` use it to clear `?game=`/`&shot=` from the URL (and, on the comparison page, to reset its own `activeGame`/row-highlight state) regardless of how the panel closed. `panelClose({ preserveUrl: true })` skips that URL clearing for a caller that's about to reopen the same game once a refresh/restore completes (see `findCommonGames` in `app.js`) — the URL still needs its `game`/`shot` params intact for `restorePanelFromUrl()` to read afterward. A "News" section (`newsHtml`) shows up to 3 recent headlines from `g.news` (title, plain date, feed label), each linking to the full post, plus a "More news →" link to the game's Steam news hub; `g.news` is already filtered server-side (`extractNews` in `lib/steam.js`) to the developer/publisher's own `steam_community_announcements` feed — the raw `GetNewsForApp` endpoint also aggregates syndicated third-party press in whatever language that outlet publishes in, unrelated to the requester's locale, which for some games outnumbers official posts entirely and doesn't match what the store page's News tab shows; a 📰 icon link to that same hub sits alongside the existing Store/IsThereAnyDeal icons regardless of whether any headlines loaded yet. Unlike rating/HLTB/tags/ProtonDB (which live on `g.details` and are prefetched for every game via `fetchGameDetails`/the SSE stream — see "Ratings"/"HLTB" and the Request flow below), news has no table column and nothing to sort/filter on, so it's kept off `g.details` entirely and fetched lazily by `panel.js` itself (`loadNews`), once per game, only when that game's panel actually opens — the same on-demand shape achievements already use, backed by its own `GET /api/game-news/:appid` route rather than folded into `fetchGameDetails`. `g.news`/`g.newsLoading` persist on the game/row object, so reopening a game already seen this session doesn't refetch; the panel's "↻ Refresh" button force-refreshes it alongside everything else (`handlePanelRefresh`).
- **`public/lightbox.js`** — Screenshot/video lightbox: `initLightbox({ onParamChange })`, `openLightbox(game, idxOrShotId)`, `closeLightbox()`, `stepLightbox(dir)`, `isLightboxOpen()`. Manages its own DOM (lazy singleton), HLS playback, zoom/pan, touch/swipe, focus trap, and loading indicator. Depends on `buildMediaItems`/`resolveShotIndex` from `mediaItems.js`.
- **`public/mediaItems.js`** — Builds the ordered media item list for a game (`buildMediaItems(appid, meta)`) and resolves a shot identifier to an index (`resolveShotIndex(shots, idxOrShotId)`). Exported for Node unit tests. The hero banner (the first item) uses `meta.banner` — Steam's own `header_image` for that specific game, resolved server-side in `extractAppDetails` (`lib/steam.js`) — once metadata has loaded, guessing the conventional `.../apps/<appid>/header.jpg` CDN path only as a client-side placeholder before then. That guess doesn't exist for every game (some are only ever served from a newer asset pipeline, e.g. `shared.akamai.steamstatic.com/store_item_assets/...`), and since it never changes, a game whose guess 404s used to show a permanently broken hero image no matter how many times the panel was reopened.
- **`public/urlState.js`** — Parses the URL search string into structured state (`parseUrlState(search)`) and exports `FILTER_DIMS`. Also exports `reorderUrlParams(params)`, the canonical query-param order (`u`, `tab`, `sort`, `game`, `shot`, `name`, filter dims, `view`, `wview`) applied by every URL-writing function on both pages, so the same logical state always serializes to the same URL string regardless of what order its pieces were set/mutated in — otherwise e.g. opening a game before vs. after adding a tag filter would leave `game` in a different position. Loaded as a plain script (not a module) on both pages — `library.js` (a module) reaches `reorderUrlParams` off the resulting global, same as it does `esc()` from `utils.js`. Exported for Node unit tests.
- **`public/utils.js`** — Shared rendering utilities (`normalizeInput`, `scoreColor`, `fmtH`, `fmtPlaytime`, `foldStr`, `esc`, `renderScoreCell`, `renderMainCell`, `renderExtraCell`, `computeSteamdbRating`); exported for Node unit tests.
- **`public/accountsBar.js`** — Shared by both pages: renders the "accounts bar" of resolved-account chips (avatar, persona name linking to their Steam profile, an online/in-game status dot, a per-account count, a "🔒 Private" badge when `communityvisibilitystate !== 3`, and a per-account "↻" refresh icon) below the search form, plus a "Recent:" row of clickable avatar chips above it backed by `localStorage` (never sent to the server; capped at 10, namespaced per page since a Library Explorer search and a comparison-page search aren't interchangeable). The status dot's tooltip says "as of this search" rather than implying live presence, since `personastate`/`gameextrainfo` ride on the same library cache tier as everything else on the chip (`LIBRARY_CACHE_TTL_MINUTES`, default 6h) — a snapshot, not real-time. Each recent-search entry's `players` snapshot is always **one array per slot/group**, even for a single-group search (`addRecent(storageKey, id, groups, data)`) — `recentChipHtml` joins accounts within a group with "+" and groups with ", ", the same convention as the accounts bar's own "N accounts merged" labeling, so a recent entry for two merged Steam Families never renders identically to a plain multi-player comparison (both used to flatten to the same "A + B + C + D"). Entries written before this grouping existed have a flat `players` array rather than an array of groups; `recentChipHtml` normalizes each element (`Array.isArray(g) ? g : [g]`) so an old entry degrades to a comma-separated list instead of crashing the page on load. Depends on the global `esc()` from `utils.js`, so it's loaded after it as a plain script (not a module) on both pages.
- **`public/gameSearch.js`** — Shared by both pages: the "look up any game" search box — a debounced name search (`GET /api/search-games`, backed by `searchStoreGames` in `lib/steam.js`) rendered as a dropdown of matches, or a bare appid/store URL typed directly bypasses the search entirely. Picking a result calls the host page's `onSelect({appid, name})`, which opens the shared side panel (`panel.js`) for that game regardless of whether anyone's library/wishlist actually contains it — `GET /api/game-details/:appid` has no ownership check, so this works for any valid Steam appid. Both host pages mark the resulting game object `standalone: true`; panel-adjacent, group-shaped UI that assumes a table row or comparison group backs the open game (owners section, prev/next nav, random-pick, the group-scoped keyboard shortcuts) checks that flag (or, on the comparison page, the absence of `groupKey`) and renders nothing / no-ops instead of erroring. If the looked-up appid turns out to already be a loaded row/comparison game, both pages open that instead of a lesser standalone view. Also exports a second, independent "recent games" list (`addRecentGame`/`renderRecentGamesBar`/`bindRecentGamesBar`) — unlike `accountsBar.js`'s "Recent:" row of player searches (namespaced per page), this one is a single `localStorage` list shared by both pages, since a game looked up here means the same thing regardless of which page it was looked up from; both host pages call `addRecentGame` once the game's real name/thumbnail is resolved (never with the `App <appid>` placeholder). Depends on the global `esc()` from `utils.js`, loaded the same way as `accountsBar.js`.
- **`public/library.html`** / **`public/library.js`** — Library Explorer: browse one player's full Steam library, or their wishlist, in a sortable/filterable/groupable table (`@vates/data-table-vanilla`, an npm dependency; `server.js` serves its `dist/` files straight from `node_modules`, resolved via an import map in `library.html`). A Library/Wishlist tab toggle switches between the two; each keeps independent table view state (`?view=`/`?wview=` URL params) and random-pick history. The wishlist is read-only — Steam has no key-based way to mutate it, only session-authenticated calls as the logged-in user, which this app doesn't support. Reuses `panel.js`/`lightbox.js`/`mediaItems.js`/`utils.js` for the same row-click side panel as the comparison page, minus tag-click filtering (the owner list is present too — `buildLibraryOwnersHtml`, mirroring `app.js`'s `buildOwnersHtml` — see its own comment for why it's a separate copy rather than shared), and `accountsBar.js` (see above) for its accounts bar / recent-searches row, which only ever holds one flat group (a Library Explorer search is a single Family, not multiple slots). Also hosts the shared `gameSearch.js` "look up any game" box and its shared "recently looked up" games row (see above); on this page the deep-link `?game=<appid>` param falls back to fetching that game directly when the appid isn't among the currently loaded rows — including with no player loaded at all. The name isn't carried in the URL (see the "Looking up an arbitrary game" section below) — the panel shows a placeholder title (`App <appid>`) until the fetch resolves the real one from store metadata. `updateTitle()` mirrors `app.js`'s own: an open game's name takes over `document.title` entirely; otherwise it falls back to `<player>'s Library`/`<player>'s Wishlist`, then the static default with nothing loaded. `updateBackLink()` keeps the header's "← Comparison tool" link (`#back-to-comparison-link`) pointed at `/?u=<ids>` for whoever's currently loaded, so following it back opens that same player's library on the comparison page instead of a bare form.
- **`public/style.css`** — All page styles.

### Request flow

1. Frontend POSTs `{ slots: [["alice", "bob_family"], ["charlie"]] }` to `/api/common-games`. Each slot is a logical player — multiple accounts in a slot have their libraries unioned before comparison (Steam Family simulation). Legacy `{ users: [...] }` is also accepted and treated as single-account slots.
2. Server resolves every identifier to a Steam64 ID, deduplicates within each slot, fetches all libraries in one parallel pass, unions libraries per slot, groups games by exact set of slot owners, returns `{ groups, slots }`.
3. Frontend renders groups immediately (one table per owner set, from most owners to fewest), then POSTs the full game list to `POST /api/game-details/stream` (SSE endpoint) to load rating, HLTB, store metadata, and tags progressively in a single connection. The legacy `GET /api/game-details/:appid` endpoint still exists for direct API consumers.

### Ratings — Wilson score vs. SteamDB Rating

The comparison page's own table cell (and the "Wilson Score" column in the Library Explorer) show the **Wilson score lower bound** at 95% confidence, computed server-side in `getGameRating`/`computeRating` from Steam's own review counts (`store.steampowered.com/appreviews/:appid`). Do not replace it with a simple positive/total ratio — that's exactly the naive approach the Wilson bound is meant to avoid, since it lets a game with 2 positive reviews outrank one with 50,000 mostly-positive reviews. (SteamDB itself used to use this same formula but has since switched to a different one — see below — so don't assume parity with what SteamDB currently shows.)

Client-side, from the same `rating.positive`/`.total` numbers already delivered to the frontend (no extra backend calls), `computeSteamdbRating(positive, total)` in `public/utils.js` computes SteamDB's current formula instead: `p − (p − 0.5) × 2^(−log₁₀(n + 1))` where `p = positive/total` and `n = total reviews`. A Bayesian shrinkage toward a neutral 50% prior that fades as review volume grows (e.g. 90% positive over 100 reviews lands at 80%). SteamDB moved to this from the Wilson interval specifically because it's easier to explain to users; see [steamdb.info-issues#793](https://github.com/SteamDatabase/steamdb.info-issues/issues/793). It returns the **raw, unrounded** value — round only for display; the Library Explorer's SteamDB Rating column sorts on the unrounded number so otherwise-tied displayed integers still order deterministically, and isn't groupable (grouping keys off the raw value, which would otherwise split into a near-useless one-row-per-group table).

This one function backs two different, intentionally-asymmetric surfaces:

- **Library Explorer table** — "SteamDB Rating" is the default-visible, default-sorted score column; "Wilson Score" and "Steam %" (the raw, unadjusted ratio) both exist too, hidden by default.
- **Game detail side panel** (`public/panel.js`, shared by both pages) — shows only the SteamDB Rating (labeled just "SteamDB", linking to the game's SteamDB page — same treatment as the "Metacritic" link right below it) plus a compact reviews line (e.g. "99% positive of 465k reviews"), no Wilson score and no Steam review-summary text tier (e.g. "Very Positive"). This means the comparison page's own table cell (Wilson score) and its side panel (SteamDB Rating) intentionally show two different numbers for the same game — expected, not a bug.

### HLTB — no npm package

The `howlongtobeat` npm package was removed (it pulled in a vulnerable `axios`). HLTB is called directly with a two-step auth flow:

1. `GET https://howlongtobeat.com/api/bleed/init?t={ms}` → returns `{ token, hpKey, hpVal }`
2. `POST https://howlongtobeat.com/api/bleed` with `X-Auth-Token`, `X-Hp-Key`, `X-Hp-Val` headers and `{ [hpKey]: hpVal, ...payload }` in the body

The token is cached in memory for 5 minutes (not on disk — it's session-bound). A 401/403 from the search endpoint clears the cache so the next call re-fetches. Match quality is checked via Levenshtein similarity; results below 0.35 are discarded.

`pickBestMatch` extracts four times from the matched entry's raw fields (all in seconds, converted to rounded hours): `main` (`comp_main`), `extra` (`comp_plus`), `completionist` (`comp_100`), and `all` (`comp_all`) — HLTB's "All PlayStyles" figure. `all` is **not** an average of the other three — it's the average of every individual completion-time submission pooled together regardless of category, weighted by how many people submitted each one (`comp_all_count` equals `comp_main_count + comp_plus_count + comp_100_count`). Since far more players report a Main Story time than a Completionist one, it usually lands much closer to Main Story than to the simple midpoint of all three. It's the default-displayed HLTB column in the Library Explorer (`hltbAll`, "All (h)") and shown first (leftmost) in the side panel's How Long To Beat section as "All PlayStyles", precisely because it's a single representative number rather than one specific playstyle.

If HLTB breaks again, recent npm packages (e.g. `howlongtobeat-ts`) tend to reverse-engineer the new flow quickly and are a good first place to look.

**Compliance note:** `/api/bleed` is an undocumented, internal HLTB endpoint reached with spoofed browser `User-Agent`/`Referer` headers — this is not a published public API and isn't guaranteed to be sanctioned by HLTB's terms of service. Usage here is low-volume and non-commercial, but treat it as liable to break or be blocked without notice, and don't scale up request volume without revisiting this.

### Wishlist — undocumented endpoint

`getWishlist` calls `https://api.steampowered.com/IWishlistService/GetWishlist/v1/?steamid={id}`, which is not listed in Valve's published Web API docs (same unofficial-endpoint situation as HLTB above, though no spoofed headers are needed here — it works with a plain request). A private wishlist, a private profile, and a genuinely empty wishlist are all indistinguishable: each returns `200 OK` with `{"response":{}}` (no `items` key). The app treats a missing `items` key as an empty wishlist rather than surfacing an error, since there's no way to tell those cases apart.

### Looking up an arbitrary game

Both pages have a "look up any game" search box (`public/gameSearch.js`) for previewing a game in the shared side panel regardless of whether anyone in the current search owns or has wishlisted it — see the "Ratings" and "HLTB" sections above for what that panel shows. `GET /api/game-details/:appid` has no ownership check at all (it already has to work for wishlist items, which aren't "owned" either), so the only missing piece was turning a typed name into an appid.

Opening a looked-up game writes `?game=<appid>` to the URL on both pages (and, within it, `&shot=<idx>` for an open lightbox screenshot/video) — a copied link reopens the same standalone lookup once the page loads, falling back to fetching the appid directly if it isn't part of whatever's currently loaded (or nothing is loaded at all). `public/gameSearch.js` also keeps a "recently looked up" row of games (distinct from `accountsBar.js`'s per-page "Recent:" *player*-search row) backed by one `localStorage` list shared by both pages, since a looked-up game means the same thing regardless of which page found it.

`GET /api/game-details/:appid` never accepts or trusts a client-supplied name — it always resolves the game's name itself from store metadata (`getAppDetails(appid)`), the same appid-keyed source used for everything else about the game, and searches HLTB using that resolved name. A name picked from the search dropdown (or carried in `library.js`'s standalone-lookup object) exists purely client-side, to avoid a title flash in the panel while the fetch is in flight — it's never sent to the server or written to the URL. The cost is that HLTB search always waits for store metadata to resolve first, rather than starting in parallel using an already-known name (e.g. an owned game's name from Steam's library API) — a deliberate trade against treating any client-provided string as ground truth on a public, key-less, ownership-free endpoint.

`GET /api/search-games?q=<term>` (`searchStoreGames` in `lib/steam.js`) wraps `store.steampowered.com/api/storesearch/?term=...&l=english&cc=US` — the same undocumented endpoint Steam's own store search box uses, no key or auth required. Same trust tier as the HLTB/wishlist endpoints documented elsewhere in this file: not a published API, not guaranteed to be sanctioned by Steam's terms, liable to break or be blocked without notice. Usage here is low-volume (client-side debounced, and each distinct term only costs one upstream call — repeats hit the `search:` cache tier) and non-commercial; don't scale up request volume without revisiting this note. A bare appid or a pasted store URL (`store.steampowered.com/app/<id>/...`) typed into the box bypasses this endpoint entirely and goes straight to `/api/game-details`.

### Database (`db.sqlite`)

`db.sqlite` is the application database, opened via the built-in `node:sqlite` module (`DatabaseSync`). It currently holds only cache tables, but is intentionally named `db.sqlite` (not `cache.db`) to accommodate non-cache data in the future. WAL mode is enabled for better concurrent write throughput. Cache entries are evicted at startup and lazily on read; every write goes directly to SQLite (no debounced flush). Set `DB_FILE=` (empty) in `.env` to use an in-memory database. Cache TTLs:

| Key prefix | TTL env var | Default | Reason |
|---|---|---|---|
| `resolve:` | `RESOLVE_CACHE_TTL_MINUTES` | 90 days | Steam ID resolution — essentially permanent |
| `rating:` | `RATING_CACHE_TTL_MINUTES` | 30 days | Steam review scores — drifts slowly |
| `hltb:`, `meta:`, `tags:` | `META_CACHE_TTL_MINUTES` | 60 days | Store metadata, HLTB, tags — rarely changes for an existing game |
| `games:`, `player:`, `wishlist:` | `LIBRARY_CACHE_TTL_MINUTES` | 6 hours | Changes when users buy games / edit their wishlist |
| `search:` | `SEARCH_CACHE_TTL_MINUTES` | 1 day | Game name → appid search results — much shorter than the other game-details tiers since new games ship regularly |
| `news:` | `NEWS_CACHE_TTL_MINUTES` | 6 hours | Recent news/announcements for a game — changes far more often than store metadata (patch notes, event posts), so it shares the library tier's cadence rather than the 60-day META one above |

Run `npm run cache:clear` to wipe all cache entries without deleting the database file.

These TTLs are generous because both `getCached` and every `lib/steam.js`/`lib/hltb.js` fetch function accept `{ force: true }` to bypass the cache read for one call (the fetch still writes fresh data back to the cache). This backs two user-facing "↻ Refresh" affordances rather than being needed for background freshness:

- The **accounts bar's per-account "↻"** (both pages, see `public/accountsBar.js`) re-POSTs `/api/common-games`/`/api/wishlist` with `refreshIds: [steamid, ...]`, forcing fresh owned-games/player/wishlist data for just that one account rather than every account in the search. `getPlayerSummaries` takes a matching `forceIds` option so a single `GetPlayerSummaries` batch call can bypass the cache for only the listed IDs. (There used to be a coarser search-bar-level "↻ Refresh" button on both pages forcing the whole search; it was removed in favor of this once the accounts bar existed to hang a per-account control on.)
- The **side panel's Refresh button** re-fetches `GET /api/game-details/:appid?refresh=1`, forcing fresh rating/HLTB/store metadata/tags for that one game only, and in parallel `GET /api/game-news/:appid?refresh=1` for that game's news (see `handlePanelRefresh` in `panel.js`) — two separate requests since news isn't part of `fetchGameDetails` (see the panel.js bullet above). Both always count against their respective rate limiters (`DETAILS_RATE_LIMIT_MAX`/news's own limiter sharing that same budget) — the cache-hit skip is disabled for `refresh=1`, since a forced call never is a cache hit.

Neither refresh path touches `resolve:` — a vanity-URL mapping isn't expected to change, so there's no user-facing reason to force it.

### URL / sharing

Players are encoded as `?u=` query params. A single-account player is `?u=alice`; a multi-account slot (Steam Family) is `?u=alice,bob_family` (comma-joined). Old single-account URLs are fully compatible. Members within each slot and slots themselves are sorted alphabetically so the same comparison always produces the same URL. `history.pushState` is used for explicit searches; `pushState: false` is used when restoring from URL on load or back/forward navigation to avoid polluting history. Every URL-writing function on both pages runs its params through `reorderUrlParams` (`public/urlState.js`) before writing, so the same state always produces byte-identical query strings regardless of write order. `sort` is omitted from the URL entirely when it matches the default (`score` descending) rather than always spelling out `-score`.

The Library Explorer (`public/library.js`) pushes exactly one history entry per genuine new action (Load button, recent-search click, tab switch, per-account refresh is `push: false`) instead of the 2-3 partial `updateUrlParams` pushes each of those used to fire (clearing `game`/`shot`, then setting `u`, then `tab` — each its own entry); everything else (panel open/close, lightbox step, restoring from a URL/back-forward navigation) uses `replaceState`. A `popstate` listener (`loadFromUrl`, mirroring `app.js`'s own) makes browser Back/Forward actually work on this page — previously the URL changed on every action but nothing reacted to History API navigation at all.
