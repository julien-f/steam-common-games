# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the app

```bash
echo "STEAM_API_KEY=your_key_here" > .env   # first time only — only required setting
npm install                                  # first time only
npm start                                    # or: npm run dev  (restarts on file changes)
```

The server binds to `http://127.0.0.1:3000` by default. `default.env` (committed to the repo) holds all settings with their defaults and documentation. Create `.env` (gitignored) with only the values you want to override — `STEAM_API_KEY` is the only required one. The server exits immediately at startup with a clear error message if it is missing.

### Request flow

1. Frontend POSTs `{ slots: [["alice", "bob_family"], ["charlie"]] }` to `/api/common-games`. Each slot is a logical player — multiple accounts in a slot have their libraries unioned before comparison (Steam Family simulation). Legacy `{ users: [...] }` is also accepted and treated as single-account slots.
2. Server resolves every identifier to a Steam64 ID, deduplicates within each slot, fetches all libraries in one parallel pass, unions libraries per slot, groups games by exact set of slot owners, returns `{ groups, slots }`.
3. Frontend renders groups immediately (one table per owner set, from most owners to fewest), then POSTs the full game list to `POST /api/game-details/stream` (SSE endpoint) to load rating, HLTB, store metadata, and tags progressively in a single connection. The legacy `GET /api/game-details/:appid` endpoint still exists for direct API consumers.

### Ratings — Wilson score vs. Weighted Rating

The comparison page's own table cell (and the "Wilson Score" column in the Library Explorer) show the **Wilson score lower bound** at 95% confidence, computed server-side in `getGameRating`/`computeRating` from Steam's own review counts (`store.steampowered.com/appreviews/:appid`). Do not replace it with a simple positive/total ratio — that's exactly the naive approach the Wilson bound is meant to avoid, since it lets a game with 2 positive reviews outrank one with 50,000 mostly-positive reviews. (SteamDB itself used to use this same formula but has since switched to a different one — see below — so don't assume parity with what SteamDB currently shows.)

Client-side, from the same `rating.positive`/`.total` numbers already delivered to the frontend (no extra backend calls), `computeSteamdbRating(positive, total)` in `public/utils.js` computes a formula adapted from SteamDB's current one instead: `p − (p − 0.5) × 2^(−k × log₁₀(n + 1))` where `p = positive/total`, `n = total reviews`, and `k` is `STEAMDB_RATING_SHRINK_STRENGTH`. A Bayesian shrinkage toward a neutral 50% prior that fades as review volume grows. SteamDB's own published formula is `k = 1` (their worked example: 90% positive over 100 reviews lands at 80%); this app runs hotter, at `k = 2`, so it converges to the raw ratio faster (the same 90%/100-review example lands at ~87-88% here) — a deliberate app-specific tuning choice, not a claim about what SteamDB itself currently shows. Whatever `k` is, the result is mathematically guaranteed to stay between 50 and `p`, moving monotonically closer to `p` as `n` grows — it can never overshoot past `p`. SteamDB moved to this general shape from the Wilson interval specifically because it's easier to explain to users; see [steamdb.info-issues#793](https://github.com/SteamDatabase/steamdb.info-issues/issues/793). It returns the **raw, unrounded** value — round only for display; the Library Explorer's Weighted Rating column sorts on the unrounded number so otherwise-tied displayed integers still order deterministically, and isn't groupable (grouping keys off the raw value, which would otherwise split into a near-useless one-row-per-group table). The internal function/field/URL-param name (`computeSteamdbRating`, the `steamdbRating` row key, `?sort=steamdbRating`) is left as-is rather than renamed alongside the label — renaming it would silently break any already-shared library URL with that in its `sort`/`view` param, for a purely internal identifier no user ever sees.

This one function backs two different, intentionally-asymmetric surfaces:

- **Library Explorer table** — "Weighted Rating" is the default-visible, default-sorted score column; "Wilson Score" and "Steam %" (the raw, unadjusted ratio) both exist too, hidden by default.
- **Game detail side panel** (`public/panel.js`, shared by both pages) — shows only the Weighted Rating (labeled just "Weighted", linking to the game's Steam reviews, since the number/caption is this app's own weighted rating, not SteamDB's) plus a compact reviews line (e.g. "99% positive of 465k reviews"), no Wilson score and no Steam review-summary text tier (e.g. "Very Positive"). This means the comparison page's own table cell (Wilson score) and its side panel (Weighted Rating) intentionally show two different numbers for the same game — expected, not a bug.

### Production Tier — a heuristic, not Steam-provided data

Steam's API has no field for a game's budget or studio size, so the Library Explorer's "Production Tier (est.)" column (hidden by default) is a best-effort AAA/AA/Indie guess, computed client-side by `computeProductionTier` in `public/utils.js` from three signals already delivered to the frontend for every row: `meta.isFree`/`meta.priceInitial` (the undiscounted launch price in cents, USD — new fields on `extractAppDetails` in `lib/steam.js`, backed by the same appdetails response already fetched for everything else about the game; `getAppDetails`'s upstream fetch now pins `cc=us` specifically so this price is always USD regardless of the server's own geolocation), `rating.total` (review count, a reach proxy) and whether a Metacritic entry exists at all (professional press coverage tends to skip most indie releases). Deliberately **no publisher/developer allowlist** — that would be the single strongest signal (works before any reviews accumulate, survives sales, survives free-to-play) but requires externally maintained, ever-drifting knowledge Steam's API doesn't provide (legal-entity name variants, acquisitions, studio spin-offs); the heuristic stays entirely self-updating from Steam's own data instead, at the cost of accuracy in exactly the cases only a publisher list would catch.

Decision order: DLC/expansion appids (`meta.fullgame` set) and Steam's other non-game content types (`meta.type` being `dlc`/`demo`/`music`/`video`/`series`/`episode`/`mod`/`hardware`/`advertising` — see the Library Explorer's own "Type" column below) return `null` outright rather than being scored on their own price — a cheap DLC attached to a AAA base game would otherwise misclassify as Indie, and no parent-game lookup is attempted to avoid an extra fetch just for this. Free-to-play games have no price signal at all, so they're judged on review volume alone against a deliberately high bar (200k+) — the only lever available. Priced games ≥$50 are "AAA"; $20–$50 is the AA/premium-indie overlap zone, requiring either 20k+ reviews or a Metacritic entry to clear "AA" rather than fall to "Indie"; below $20 is always "Indie" regardless of review count (this is where breakout indie hits with huge review counts — Vampire Survivors, Stardew Valley, Terraria — correctly stay classified as Indie rather than reading as AAA). Known, accepted misclassifications with no data-side fix: cheap rereleases/remasters of old AAA IP, prestige-priced niche sim/strategy games from small studios, and veteran-founded small studios shipping a low-budget but polished game. This is why the column label spells out "(est.)" rather than presenting the value as fact.

### HLTB — no npm package

The `howlongtobeat` npm package was removed (it pulled in a vulnerable `axios`). HLTB is called directly with a two-step auth flow:

1. `GET https://howlongtobeat.com/api/search/site/init?t={ms}` → returns `{ token, hpKey, hpVal }`
2. `POST https://howlongtobeat.com/api/search/site` with `X-Auth-Token`, `X-Hp-Key`, `X-Hp-Val` headers and `{ [hpKey]: hpVal, ...payload }` in the body

(Previously `api/bleed/init` and `api/bleed` — HLTB renamed these endpoints; the `howlongtobeat-ts` npm package's source is what surfaced the new paths when the old ones started 404ing.)

The token is cached in memory for 5 minutes (not on disk — it's session-bound). A 401/403 from the search endpoint clears the cache so the next call re-fetches. Match quality is checked via Levenshtein similarity; results below 0.35 are discarded.

`pickBestMatch` extracts four times from the matched entry's raw fields (all in seconds, converted to hours rounded to the nearest half hour — the same granularity HLTB's own site displays, e.g. "2½ Hours" — rather than a whole hour, which would silently discard that precision): `main` (`comp_main`), `extra` (`comp_plus`), `completionist` (`comp_100`), and `all` (`comp_all`) — HLTB's "All PlayStyles" figure. `all` is **not** an average of the other three — it's the average of every individual completion-time submission pooled together regardless of category, weighted by how many people submitted each one (`comp_all_count` equals `comp_main_count + comp_plus_count + comp_100_count`). Since far more players report a Main Story time than a Completionist one, it usually lands much closer to Main Story than to the simple midpoint of all three. It's the default-displayed HLTB column in the Library Explorer (`hltbAll`, "All (h)") and shown first (leftmost) in the side panel's How Long To Beat section as "All PlayStyles", precisely because it's a single representative number rather than one specific playstyle.

If HLTB breaks again, recent npm packages (e.g. `howlongtobeat-ts`) tend to reverse-engineer the new flow quickly and are a good first place to look.

**Compliance note:** `/api/search/site` is an undocumented, internal HLTB endpoint reached with spoofed browser `User-Agent`/`Referer` headers — this is not a published public API and isn't guaranteed to be sanctioned by HLTB's terms of service. Usage here is low-volume and non-commercial, but treat it as liable to break or be blocked without notice, and don't scale up request volume without revisiting this.

### Wishlist — undocumented endpoint

`getWishlist` calls `https://api.steampowered.com/IWishlistService/GetWishlist/v1/?steamid={id}`, which is not listed in Valve's published Web API docs (same unofficial-endpoint situation as HLTB above, though no spoofed headers are needed here — it works with a plain request). A private wishlist, a private profile, and a genuinely empty wishlist are all indistinguishable: each returns `200 OK` with `{"response":{}}` (no `items` key). The app treats a missing `items` key as an empty wishlist rather than surfacing an error, since there's no way to tell those cases apart.

### Tags & demo link — Steam's own store browse data, not SteamSpy

`getSteamTags` (`lib/steam.js`) fetches the same user tags shown on a game's own Steam store page (and, downstream of that, SteamDB and IsThereAnyDeal) rather than SteamSpy's separate crowd-voted dataset, which this used to pull from and which can be sparse or empty for a game Steam itself has plenty of tag data for — especially anything niche or too recent for SteamSpy's own community to have caught up on. Two undocumented, key-less endpoints (same trust tier as the other endpoints covered by this compliance note) stand in for it:

- `https://api.steampowered.com/IStoreBrowseService/GetItems/v1/?input_json={"ids":[{"appid":N}],"context":{"language":"english","country_code":"US"},"data_request":{"include_tag_count":30}}` returns that one app's whole "store browse item" — `tagids` (already ordered by relevance weight descending, the same order the store page itself displays them in — all returned tagids are shown, no further display cap on top of this) plus other fields riding along on the same response for free. `getGameDemo` reads one of those: `related_items.demo_appid`, the appid of the game's free demo if it has one, surfaced in the side panel as a standalone "🎮 Try the Free Demo" banner (`public/panel.js`'s `demoBannerHtml`) right under the sticky header — deliberately not folded into the "⋯ More" icon menu alongside Website/Workshop, since a demo is a call to action worth surfacing without an extra click, unlike those two which are just supplementary info. The **whole raw item** is cached (`browse:{appid}`, not just the extracted tagids) — the usual "cache raw, extract at read time" approach used everywhere else in this file (see the cache-table intro above) — specifically so that adding another field this same call already returns, like the demo link, never needs a new upstream request, just a new extractor over the already-cached response. `getSteamTags` and `getGameDemo` share one upstream fetch per appid this way, via the same cache entry plus the usual in-flight dedup.
- `https://store.steampowered.com/actions/ajaxgetstoretags?l=english` maps every tagid to its human-readable name — a single, near-static ~430-entry list, not per-game, so it's fetched once and cached long-term (`tagnames:all`, same 60-day `META_CACHE_TTL_MINUTES` group as `browse:` — see the cache table above) rather than repeated for every game lookup.

The `browse:` cache key is the third one used for this data — `tags:` (SteamSpy's `{tagname: voteCount}` object) then briefly `tagids:` (a bare `tagid[]`) came before it. Each format change got a new key rather than reusing the old one: a shape check alone can't safely tell an old value apart from a new one when both can legitimately be the same JS type (e.g. a game with zero SteamSpy votes cached a bare `[]`, indistinguishable from an empty `tagid[]` result). Retired-key entries are simply never read again and age out on their own via the existing TTL sweep.

### Looking up an arbitrary game

Both pages have a "look up any game" search box (`public/gameSearch.js`) for previewing a game in the shared side panel regardless of whether anyone in the current search owns or has wishlisted it — see the "Ratings" and "HLTB" sections above for what that panel shows. `GET /api/game-details/:appid` has no ownership check at all (it already has to work for wishlist items, which aren't "owned" either), so the only missing piece was turning a typed name into an appid.

Opening a looked-up game writes `?game=<appid>` to the URL on both pages (and, within it, `&shot=<idx>` for an open lightbox screenshot/video) — a copied link reopens the same standalone lookup once the page loads, falling back to fetching the appid directly if it isn't part of whatever's currently loaded (or nothing is loaded at all). `public/gameSearch.js` also keeps a "recently looked up" row of games (distinct from `accountsBar.js`'s per-page "Recent:" *player*-search row) backed by one `localStorage` list shared by both pages, since a looked-up game means the same thing regardless of which page found it.

`GET /api/game-details/:appid` never accepts or trusts a client-supplied name — it always resolves the game's name itself from store metadata (`getAppDetails(appid)`), the same appid-keyed source used for everything else about the game, and searches HLTB using that resolved name. A name picked from the search dropdown (or carried in `library.js`'s standalone-lookup object) exists purely client-side, to avoid a title flash in the panel while the fetch is in flight — it's never sent to the server or written to the URL. The cost is that HLTB search always waits for store metadata to resolve first, rather than starting in parallel using an already-known name (e.g. an owned game's name from Steam's library API) — a deliberate trade against treating any client-provided string as ground truth on a public, key-less, ownership-free endpoint.

`GET /api/search-games?q=<term>` (`searchStoreGames` in `lib/steam.js`) wraps `store.steampowered.com/api/storesearch/?term=...&l=english&cc=US` — the same undocumented endpoint Steam's own store search box uses, no key or auth required. Same trust tier as the HLTB/wishlist endpoints documented elsewhere in this file: not a published API, not guaranteed to be sanctioned by Steam's terms, liable to break or be blocked without notice. Usage here is low-volume (client-side debounced, and each distinct term only costs one upstream call — repeats hit the `search:` cache tier) and non-commercial; don't scale up request volume without revisiting this note. A bare appid or a pasted store URL (`store.steampowered.com/app/<id>/...`) typed into the box bypasses this endpoint entirely and goes straight to `/api/game-details`.

### Bundles — IsThereAnyDeal API

The Bundles page (`public/bundles.html`/`bundles.js`) browses current Steam game bundles via the [IsThereAnyDeal API](https://docs.isthereanydeal.com/) (`lib/itad.js`) — a free, key-gated API, distinct trust tier from the undocumented Steam/HLTB endpoints covered elsewhere in this file (published, if sparse, OpenAPI docs). Entirely optional: gated behind `ITAD_API_KEY` (`.env`), which is not required for the rest of the app to run. `server.js`'s `isItadConfigured()` checks it per-request; `GET /api/bundles`/`POST /api/bundles/resolve`/`POST /api/prices` return 503 when unset, and the page itself shows a plain "not configured" message instead of the browse UI (`GET /api/health`'s `itadConfigured` field drives that check). The same ITAD integration also backs the Library Explorer's Wishlist price columns — see its own section below; `POST /api/prices` is shared by both pages (this section covers it from the Bundles side first).

The bundle list itself is height-capped and scrollable (`.bundle-list`, `max-height`) rather than growing to however many bundles are loaded, and auto-collapses to a one-line "Show list" toggle once a bundle is actually opened (`setListCollapsed`) — otherwise a long list pushes the real content (the opened bundle's game table) far down the page. Changing region/sort/"include expired" re-expands it, since that's a browsing action again.

- **`GET /bundles/v1`** (wrapped by `getBundles` / `GET /api/bundles`) lists current bundles, paginated (`offset`/`limit`, max 50/page), with a `country` param that drives both currency and (per ITAD, presumably regional storefront) pricing. There is no single-bundle-fetch endpoint upstream, so `?bundle=<id>` deep linking (same idea as `?game=`/`?u=` elsewhere) is backed by a bounded server-side search instead: `findBundleById` (`lib/itad.js` / `GET /api/bundles/:id`) pages through `GET /bundles/v1` — active bundles first (`expired=false`), then expired — up to `BUNDLE_SEARCH_MAX_PAGES` (6) pages of 50 each per expired-state, and 404s rather than searching indefinitely if the id never turns up (very old/deleted bundle, or a bad id). Each page it fetches reuses `getBundles`' own per-page cache, so a second deep link into a bundle on an already-searched page costs no extra upstream call. `openBundleById` (`bundles.js`) always goes straight to this route on page load rather than checking whatever's already in the browsed list first — the list may be a different sort/page, or not loaded yet at all, and the two run concurrently rather than sequentially. Opening a bundle (deep-linked or picked from the list) always writes `?bundle=<id>` via `replaceState` (not pushed — this page has no `popstate` listener, unlike `library.js`/`app.js`); a 404 clears it back out so a refresh doesn't repeat the same failed search.
- Each bundle's `tiers[]` lists the games unlocked at that price tier; a game can appear in more than one tier (a cheap tier's games are still included in every pricier tier above it) — `flattenBundleGames` (`public/bundles.js`) dedupes by ITAD game id, keeping the cheapest tier's price, since ITAD's tiers are observed to always be price-ascending.
- Bundle games carry no Steam appid directly — only an ITAD-internal id (uuid), slug, and title. Resolving to Steam is a separate step: `resolveSteamAppIds` (`lib/itad.js`) first resolves ITAD's numeric shop id for Steam via `GET /service/shops/v1` (cached under `itad-shop:steam`, effectively permanent), then batches the bundle's game ids through `POST /lookup/shop/{shopId}/id/v1` (`POST /api/bundles/resolve` on this app's side) — **not** the more RPC-shaped `/lookup/{shopId}/gid/v1` path the sibling lookup endpoints' naming might suggest; the real path follows ITAD's own `/lookup/{lookup-what}/{by-what}/` convention and was confirmed against the live API, not just the docs. The response namespaces each shop id as `"app/<id>"` (a store page) or `"sub/<id>"` (a package/bundle sub, not a single game page) — only an `"app/"` entry resolves to something `GET /api/game-details/:appid` can look up; a game listed only as a `"sub"` resolves to `null`, same as no Steam listing at all. Each ITAD game id's resolution is cached individually (`itad-appid:{gid}`) so a game seen in one bundle is never re-resolved for another.
- Resolved games feed straight into the same `POST /api/game-details/stream` pipeline the Library Explorer uses — the Bundles page's game table is a near-identical `@vates/data-table-vanilla` table (deliberately a separate copy of the column-building code, not a shared import — same "kept as a separate copy" precedent as `library.js`'s own duplicated bits relative to `panel.js`), same shared side panel, minus ownership-only columns (Played/Last Played) that have no meaning here, plus bundle/pricing-specific ones (Tier Price, Add-on, Steam Price, All-Time Low, 1yr Low, 3mo Low — see below). Unresolved games (no Steam listing) render in a separate plain list instead of the table — nothing to sort/filter/group on beyond what ITAD already gives (title, type, tier price, boxart).
- **`POST /games/prices/v3`** (wrapped by `getPrices`/`extractPriceInfo` in `lib/itad.js`, `POST /api/prices` on this app's side) supplies the pricing columns — batched separately from `resolveSteamAppIds` above since it needs `country` (prices are region-specific; appid resolution isn't) and returns, per ITAD game id, `historyLow.{all,y1,m3}` (the lowest price seen across every shop ITAD tracks — not Steam-specific; "have I ever seen this cheaper anywhere" is the more useful question than a Steam-only low) plus a `deals[]` array with each shop's current `price`/`regular`/`cut`. `extractPriceInfo` reads this array twice: once for the `deals[]` entry whose `shop.id` matches the Steam shop id (from `getSteamShopId`), returning its `regular` (Steam's own non-discounted price), and once scanning every entry for the lowest `price.amount` regardless of shop (`bestDeal: {price, shop}`) — every entry in one response is already in the same requested `country`'s currency, so they're directly comparable with no conversion needed. Both this call and `resolveSteamAppIds`'s lookup run for a bundle's games concurrently with the `game-details/stream` fetch (`Promise.all` in `openBundle`) — pricing has nothing to do with ratings/HLTB/tags, so there's no reason to sequence them. Cached per `(gid, country)` (`itad-price:{country}:{gid}`), unlike the appid resolution above which only needs to be resolved once ever — a price is meaningfully different per region, not just a currency relabeling. Best Deal and Discount are visible by default (answers "is this bundle actually a good deal, and where's it cheapest right now" at a glance); Steam Full Price (named that way, not the shorter "Steam Price", specifically to make clear it's the non-discounted list price), All-Time Low, Best Deal Shop, and 1yr Low/3mo Low are hidden by default, same "secondary number" convention as Wilson Score/Steam %/Achievements elsewhere in this column set — Steam Full Price and All-Time Low specifically because Best Deal + Discount together already answer "is this a good deal, and by how much" for the common case, not because the exact numbers stopped being useful. A bundle tier's own price (`tierPrice`/`tierCurrency` on each row) can be `null` for a free/pay-what-you-want-or-more tier.
  - **Discount is its own column (`bestDealCut`), not a percentage folded into the Best Deal cell — and it's computed against Steam Full Price, not taken from ITAD's own per-deal `cut` field.** `cut` (an integer percentage ITAD does return per deal, e.g. `70` for 70% off) is that shop's own discount off *its own* regular price — a number shops set independently and don't compute consistently with each other, so it means something different from row to row (whatever that particular shop happens to list). `discountPct(bestDealAmt, steamRegularAmt)` (`bundles.js`/`library.js`, a deliberate separate-copy pair) computes `1 - bestDeal/steamRegular` instead, so every row's Discount answers the same question against the one stable, Valve-set anchor this app already treats as the reference price throughout (the same reasoning that keeps Steam Full Price around as its own column at all). Safe to compute without clamping: Best Deal is defined as the cheapest price across *every* shop including Steam, so `bestDealAmt <= steamRegularAmt` always holds. `extractPriceInfo` (`lib/itad.js`) deliberately does *not* surface `cut` at all, for exactly this reason. `renderCut` renders `0` (the best deal genuinely isn't any cheaper than Steam) the same as "—" — a flat "0%" would read as noise next to every other row's real discount, and nothing else in this column set treats a confirmed zero differently from "nothing to show" either.
  - **`POST /api/prices` is one shared route for both Bundles and the Library Explorer's Wishlist tab**, not two near-identical ones — the actual pricing operation (resolve to an ITAD gid if needed, then `getPrices`/`extractPriceInfo`) is identical either way; only the identifier space the caller already has differs. Bundles passes `gids` (it already has ITAD gids off a bundle's own `tiers[].games[].id`); the Wishlist tab passes `appids` instead (a wishlist row only has a Steam appid) and the route resolves those to gids internally first via `resolveItadIds` (`lib/itad.js`) — the reverse direction of `resolveSteamAppIds` above, via `POST /lookup/id/shop/{shopId}/v1` (confirmed against the live API: takes `["app/<appid>", ...]`, returns `{"app/<appid>": "<uuid>"|null, ...}`, keyed by exactly what was sent). That reverse resolution isn't exposed as its own route the way `/api/bundles/resolve`'s gid→appid mapping is — nothing needs the raw gid itself, unlike Bundles' own "which of these games have no Steam listing at all" list. Each appid's resolution is cached individually (`itad-gid:{appid}`, same `cache_bundles` tier as `itad-appid:` — see the Database section below), same "confirmed miss cached the same as a real mapping" treatment as `resolveSteamAppIds`. Exactly one of `gids`/`appids` must be provided; the route 400s on both-or-neither. See the Library Explorer's own section below for the Wishlist-side details (row shape, region picker, the `visibleRowsForTable`/`markRowChanged` fix this feature needed there).
  - **`tierCurrency` and `priceCurrency` are deliberately two separate fields on a row, not one shared `currency`.** An earlier version had one shared field, populated first from whichever value arrived first and never overwritten — this was a real bug, confirmed live: a bundle's own tier price can come back from ITAD in USD only regardless of requested `country` (same "this shop doesn't offer this region's currency" situation as bundle-level pricing generally — see the region-selection bullet below), while that *same* bundle's games' Steam/other-shop prices, a separate upstream call, correctly come back in the requested currency. With one shared field, whichever request resolved first "won" and silently mislabeled the other's amounts with the wrong currency symbol (right number, wrong label — easy to miss). `tierCurrency` (from the bundle's own tier data) backs only the Tier Price column; `priceCurrency` (from `loadPrices`, always set unconditionally from that response — never conditionally backfilled) backs the other five price columns. `formatMoney(v, currency)` (`bundles.js`) is the shared low-level formatter both `renderPrice`/`renderTierPrice` call with the correct field for their own column, rather than each reimplementing `Intl.NumberFormat` against a shared field.
  - `renderBestDeal` (`bundles.js`) deliberately does NOT put the shop name in the cell's own text (an earlier version did, as "$11.24 · Fanatical") — instead the price is colored/badged when it's at or below a historical low: bright teal + bold + 🔥 for `bestDealPrice <= lowAll` (an all-time low), green + ★ for `bestDealPrice <= lowY1` (a 1-year low, checked only when the all-time-low case didn't already match), reusing `scoreColor`'s own "excellent"/"good" tier colors rather than a new palette. `<=`, not `<` — the current deal genuinely can BE the historical low itself (it's what set it), not only ever beat it. The shop name still exists (a native `title` tooltip on the price, and its own hidden-by-default `bestDealShop` column for grouping/filtering) — dropped from the cell text specifically to leave room for the low-price indicator, judged the more actionable of the two at a glance. The tooltip itself is deliberately terse — just the shop name (`"Fanatical"`), plus `" — all-time low"`/`" — 1-year low"` appended when it qualifies — with no "cheapest current price" restatement, since that's already what the Best Deal column itself means; an earlier draft spelled that out in every tooltip and it read as redundant once actually seen hovering over a column already labeled "Best Deal".
- The "‹"/"›" buttons next to the bundle title (`renderBundleNav` in `bundles.js`) step to the previous/next entry in the currently-loaded `bundles` array — not the full remote list, no auto-"Load more", no wraparound at either end. `activeBundleId`'s position is looked up fresh on every click/render rather than cached, so it stays correct as `bundles` itself changes (a new sort/country/"Include expired" reset, or "Load more" appending a page) — `renderBundleNav()` is called after both `openBundle` and `loadBundles` for exactly that reason. A bundle that isn't part of the loaded list at all (`indexOf` returns -1 — e.g. a `?bundle=` deep link to one the currently loaded page/sort/filter doesn't include) disables both buttons rather than guessing a position.
- The game table's view (visible columns, sort, grouping, filters) persists via `persistViewToLocalStorage` (`@vates/data-table-vanilla`, `bundles:table-view`) rather than a URL param the way the Library Explorer's `?view=`/`?wview=` do — there's no per-bundle URL state to hang it on (`?bundle=` identifies *which* bundle is open, not the table's own display preferences), and the preference is meant to be one shared "how I like this table set up" that carries over from whichever bundle was open last to the next one, not per-bundle. Applied *after* `table.setViewState({ sorts: DEFAULT_SORT })` at table construction (same ordering `syncViewToUrl` uses elsewhere) so a persisted view overrides the default sort when one exists, but the default still applies on a genuinely first-ever visit. `resetView(table, { storageKey: TABLE_VIEW_STORAGE_KEY })` (the page's "Reset view" button) clears both the persisted value and the live view back to construction defaults; `DEFAULT_SORT` is reapplied afterward the same way library.js's own reset button does, since `resetView` clears sorts to none and there's no construction-time option to make it preserve a non-empty default.
- Region selection is a small curated dropdown of major Steam pricing regions, not the full ISO 3166-1 list — ITAD's `country` param accepts any 2-letter code, but a bare 250-country dropdown is worse UX for a feature that only exists to compare prices at a glance. `COUNTRY_OPTIONS`/`TIMEZONE_COUNTRY`/`detectCountry`/`AUTO_COUNTRY`/`getStoredRegion`/`setStoredRegion`/`resolveRegion`/`initRegionSelect` all live in shared `public/region.js` (a plain script, loaded before both `bundles.js` and `library.js`'s module scripts, same convention as `esc()`/`reorderUrlParams` from `utils.js`/`urlState.js`) rather than duplicated in `bundles.js` alone, once the Library Explorer's Wishlist tab needed the exact same list/heuristic (see below).
  - **One shared `localStorage` preference (`steam-common-games:region`), not per-page and not a URL param.** Picking a region on either page updates both — it's "what currency do I want to see prices in", a single user preference, unlike e.g. `bundles:table-view` (genuinely page-specific display state). Deliberately not shareable via URL either (an earlier version wrote it to `?country=`, mirroring `sort`/`view`) — region says more about the viewer than about which bundle/wishlist they're looking at, so a shared link shouldn't override whatever the *recipient's* own region preference is.
  - **The dropdown's first entry is always `AUTO_COUNTRY` ("auto"), labeled "Auto-detect (⟨whatever it currently resolves to⟩)"** (`initRegionSelect`) — e.g. "Auto-detect (Europe / Germany (EUR))" — so picking it isn't a leap of faith, and it's the default when nothing has ever been explicitly chosen (`getStoredRegion`, falling back to `AUTO_COUNTRY` when storage is empty/unavailable/holds an unrecognized value). `resolveRegion(selected)` is the one place `detectCountry()` gets consulted for a *live* value — every actual upstream call resolves the picker's current value through it, so "Auto-detect" always tracks the current OS/browser signals rather than freezing whatever they resolved to at picker-population time. Picking a real region instead overrides auto-detection until switched back.
  - `detectCountry` itself is unchanged: tries the OS timezone first (`Intl.DateTimeFormat().resolvedOptions().timeZone`, via a curated `TIMEZONE_COUNTRY` map including a Eurozone-to-`DE` mapping) before falling back to `Intl.Locale(navigator.language).maximize().region` — language reflects a UI preference, not physical location, and very commonly stays "en-US" (or another English variant) regardless of where the user actually is (confirmed live: a machine with `LANG=en_US.UTF-8` but an OS timezone of `Europe/Paris`, which the language-only heuristic resolved straight to `US`).
  - The Eurozone entry's label leads with "Europe" (`Europe / Germany (EUR)`, not `Germany / EU (EUR)`) — `DE` is just the ISO code Steam/ITAD happen to key Eurozone pricing off, an implementation detail nobody picking a region cares about; the concept being selected is "Europe", not specifically Germany.
  - **Not every bundle actually follows it** — the currency on a tier/game price is whatever ITAD's upstream shop itself charges in, passed straight through; most shops (Humble, GreenManGaming, most Fanatical bundles) do switch currency per region, but some (verified live: a shop ITAD lists as "Digiphile", and at least one specific Fanatical bundle) only ever price in USD regardless of `country` — this is genuine upstream behavior, not a bug to "fix" by converting currencies client-side, and the page has a note next to the region picker explaining it.
- A bundle tier's `price` can be `null` even when the tier lists real games — this is **not** the same as free. In practice this is Fanatical's "Build Your Own ⟨N⟩ Bundle" pick-and-mix format: one tier, a pool of 15-30 games, price scales with however many you pick rather than being a fixed property of the bundle. A genuinely free/pay-what-you-want-or-more tier would carry an explicit `{amount: 0, ...}` price object instead (truthy, so it's grouped with priced tiers, not with the `null` case) — never observed in practice as of writing, but the correct thing to special-case if ITAD ever sends one. `cheapestTierPrice`/`fmtBundleListPrice` (bundle list) and `renderTierPrice`/the `tierPrice` column's own `format` (game table) both render `null` as "Varies"/"Price varies", reserving "Free" for an actual `amount === 0`. The `tierPrice` column also needs `compare: compareNumMissingLast` for this same reason — without it, `null` coerces to `0` under the column's default numeric comparator, which would sort every "Build Your Own" bundle's games as the single cheapest thing in the table under the default ascending Tier Price sort.
- An opened bundle shows two outbound links (`renderDetailLinks` in `bundles.js`): "View on IsThereAnyDeal ↗" (the bundle's `details` field, ITAD's own page for it) and "Get this bundle ↗" (`url`, the real shop/affiliate purchase link exactly as ITAD returned it — never rewritten or stripped of tracking params; ITAD's terms require passing prices/links through unmodified, same as the compliance note on the other third-party integrations in this file).
- Bundle listings, Steam-appid resolutions, and per-region price lookups share one cache tier (`BUNDLES_CACHE_TTL_MINUTES`, default 2 hours — see the Database section below) rather than each getting its own: a bundle can go live or expire at any time (shorter-lived than store metadata), while the appid mapping itself is closer to permanent, but it's cheap to over-invalidate the latter two in exchange for one fewer cache table.
- `BUNDLES_RATE_LIMIT_MAX` backs 4 separate `rateLimit()` instances (`bundlesListLimit`/`bundlesByIdLimit`/`bundlesResolveLimit`/`pricesLimit`), not one shared limiter — each `skip`s a request it can answer entirely from cache, by reconstructing that route's own cache key from the request and checking `getCached` directly (same "cache hits don't count" pattern `detailsLimit`/`gameSearchLimit`/`achievementsLimit` already use elsewhere in `server.js`). `pricesLimit` (named generically, not `bundlesPricesLimit` — see the shared-route bullet above) branches its `skip` on whichever of `gids`/`appids` the request actually sent, checking `itad-price:`'s cache key either way plus `itad-gid:` too for the `appids` case, since that route resolves appids to gids as its own internal step. This matters more here than it might look: simply reloading the Bundles page a handful of times re-requests the list and re-opens whatever bundle is deep-linked (`?bundle=`) every time, and without the skip, every one of those re-requests — even though none of them touch ITAD — counted against the same budget a genuinely new bundle open needs, silently 429ing it with no obvious cause. `bundlesByIdLimit` (`GET /api/bundles/:id`) is the one exception — `findBundleById`'s search walks a variable number of pages depending on where the id turns up, so there's no single cache key to check in advance; it gets a looser budget (`BUNDLES_RATE_LIMIT_MAX * 2`) instead of a skip, on the reasoning that deep links are a comparatively rare action next to list browsing, and the pages it walks are still individually cached underneath via `getBundles`.
- A failed `POST /api/prices` call (rate limited, transient upstream error) does not leave the Steam Price/All-Time Low/1yr Low/3mo Low columns stuck on `undefined` (rendered as "…", indistinguishable from "still loading") forever — `loadPrices`'s catch block (`bundles.js`) sets every resolved row's price fields to `null` (rendered "—", same as any other "no data" case) and writes a visible explanation to `#price-status`, a dedicated status line kept separate from `#detail-status` (which `streamGameDetails`'s own progress messages would otherwise overwrite). `library.js`'s own `loadWishlistPrices` does the same for the Wishlist tab's own `#price-status`.
- **`@vates/data-table-vanilla`'s `setData` only re-renders a row's cells when the object at its rowKey is a genuinely *new* reference** — mutating an existing row object in place and calling `setData` again with an array that still contains that same reference (even a brand-new outer array from `.filter()`) does not update its already-rendered cells, confirmed live by directly inspecting a row's in-memory state (correct) against its rendered DOM (stale). This bites `bundles.js` specifically because a row can become visible (via `streamGameDetails`, all fields set atomically in one `applyDetailsEvent` call) *before* `loadPrices`'s later, separate mutation of that same row's price fields — the common case once everything is cache-warm and both requests resolve near-instantly, so the ordering isn't a rare edge case.
  - The naive fix — blanket-copy every visible row on every `setData()` call — technically works but is wrong two ways: it forces a full-table re-render on every single streamed event instead of just the row that changed, and it breaks object identity for anything reading a row back from the table (`onRowClick`'s row is a fresh, different copy every render, so a row opened in the panel would silently drift from `rowMap` the next time anything else about it streamed in).
  - The actual fix is a per-appid `tableRowCache` (`bundles.js`): `visibleRowsForTable()` reuses a row's cached copy verbatim across renders until `markRowChanged(appid)` is called for it, at which point a fresh copy is made — so only the row that actually changed gets a new reference, and every other row's DOM is left alone. `rows`/`rowMap` keep the stable, mutated-in-place object identity everything else needs (the panel re-renders by reading fields straight off whatever object `panelOpen` was called with, and it must stay the same reference across a refresh) — `onRowClick` explicitly looks the canonical `rowMap` object back up by appid before opening it (rather than trusting whatever copy the table's click handler passed), so `onRefresh`'s mutation lands on the same object `rowMap` does, not a disconnected copy.
  - **Every mutation site must call `markRowChanged` right after mutating — including `streamGameDetails`'s own first-time reveal of a row, not just `loadPrices`/`onRefresh`.** This isn't optional even though a fresh reveal looks like it should be covered by `visibleRowsForTable`'s own "no cache entry yet" fallback: `loadPrices` and `streamGameDetails` run concurrently (`Promise.all` in `openBundle`), and on a cache-warm bundle `loadPrices` (one cheap batched ITAD call) routinely resolves *before* `streamGameDetails` (several real per-game Steam/HLTB calls) reveals that same row. If `loadPrices` calls `markRowChanged` first, it creates a cache entry from the row's still-`loading` snapshot; by the time `streamGameDetails` later flips it visible, the cache already "has" an entry, the fallback never fires, and the row is permanently stuck on that premature snapshot — missing ratings/HLTB/genres/etc. entirely. Confirmed live exactly this way before `streamGameDetails` was given its own `markRowChanged` call.
  - `library.js` now carries the identical fix (its own `tableRowCache`/`markRowChanged`/`visibleRowsForTable`, plus `onRowClick: row => openGame(rowMap.get(row.appid) ?? row)`) — added once the Wishlist tab's own price loading (`loadWishlistPrices`, see "Wishlist pricing" below) gave it a second async source that mutates an already-visible row, on top of the pre-existing "↻ Refresh" path (`onRefresh` in its `initPanel` call) which had the exact same latent risk but never actually hit it before, since a plain load never mutates a row again after it first becomes visible. `visibleRows()` itself is unchanged and still returns the canonical `rows`/`rowMap` objects directly — it's now explicitly documented as the one nav/random-pick/`onRowClick` callers must use instead of `visibleRowsForTable()`, precisely because those need the same reference the panel keeps displaying, not a copy that further mutations would stop reaching.

### Wishlist pricing (Library Explorer)

The Library Explorer's Wishlist tab shows the same IsThereAnyDeal-backed price columns Bundles does — Best Deal, Discount, Steam Full Price, All-Time Low, 1yr Low, 3mo Low (with the same all-time/1yr-low 🔥/★ badge on Best Deal) — via `WISHLIST_PRICE_COLUMNS` in `library.js`, a deliberate separate copy of `formatMoney`/`renderPrice`/`renderBestDeal`/`renderCut`/the column definitions rather than a shared import, same "kept as a separate copy" precedent as this file's other bits relative to `bundles.js`/`panel.js`. Inserted right after Wishlist Rank (via the existing `insertColumnsAfter` helper), the same relative "right before Scores & reviews" position `bundles.js` gives its own price columns. Best Deal and Discount are visible by default (`WISHLIST_DEFAULT_VISIBLE`), same as Bundles; Steam Full Price, the narrower-window lows, and the shop name stay hidden.

- **A wishlist row only has a Steam appid, not an ITAD game id** — the reverse of a bundle's own games, which start as ITAD gids and get resolved *to* a Steam appid (`resolveSteamAppIds`, `/api/bundles/resolve`). `loadWishlistPrices` (`library.js`) instead calls the shared `POST /api/prices` with `appids` (see the shared-route bullet above), which resolves them to gids server-side first via `resolveItadIds` before running the identical price lookup — so nothing in `library.js` itself ever sees a raw ITAD gid.
- **Region picker**: a small `<select>` (`#country-select`, `#wishlist-region-label`) next to the tabs, populated and restored by the shared `initRegionSelect` (`public/region.js` — see the Bundles section's own region-selection bullet above for the "Auto-detect" entry/`localStorage` persistence this backs, shared with the Bundles page). Hidden on the Library tab (no price columns there) and hidden outright when ITAD isn't configured (`itadConfiguredPromise`, a `GET /api/health` check fired once at module load and awaited wherever it matters, never rejecting — a failed health check is treated the same as "not configured"), rather than showing a picker for a feature that isn't running.
- **Changing region re-prices the currently-loaded wishlist in place** (`loadWishlistPrices(rows)`, called again from the `<select>`'s own `change` handler, which also calls `setStoredRegion`) rather than reloading the whole tab — there's no bundle-detail-view/list-collapse state to juggle the way Bundles' own region change has (see its own section above), just the one already-loaded table's price columns going back to "…" until the new country's prices land.
- **No ITAD key configured at all**: `loadWishlistPrices` fills every row's price fields with `null` (rendered "—", same as any other "no data" case) rather than attempting a request bound to 503 or leaving the columns stuck on their loading placeholder forever — same reasoning as a failed price lookup elsewhere in this file, just checked proactively instead of caught after the fact.
- **Chunked client-side into batches of `MAX_PRICE_LOOKUP_GAMES` (500, mirroring the server's own cap)**, run sequentially rather than in parallel — unlike a bundle's game list (which never exceeds the cap and so bundles.js's own `loadPrices` always sends everything in one call), a Steam wishlist can run well past it, and firing several chunks at once would just be several concurrent ITAD-backed requests for no benefit.
- Runs concurrently with `streamGameDetails` (`Promise.all` in `loadWishlist`), same "pricing has nothing to do with ratings/HLTB/tags" reasoning as Bundles' own `openBundle`.

### Database (`db.sqlite`)

`db.sqlite` is the application database, opened via the built-in `node:sqlite` module (`DatabaseSync`). It currently holds only cache tables, but is intentionally named `db.sqlite` (not `cache.db`) to accommodate non-cache data in the future. WAL mode is enabled for better concurrent write throughput. Cache entries are evicted at startup and lazily on read; every write goes directly to SQLite (no debounced flush). Set `DB_FILE=` (empty) in `.env` to use an in-memory database. Cache TTLs:

| Key prefix | TTL env var | Default | Reason |
|---|---|---|---|
| `resolve:` | `RESOLVE_CACHE_TTL_MINUTES` | 90 days | Steam ID resolution — essentially permanent |
| `rating:` | `RATING_CACHE_TTL_MINUTES` | 30 days | Steam review scores — drifts slowly |
| `hltb:`, `meta:`, `browse:`, `tagnames:` | `META_CACHE_TTL_MINUTES` | 60 days | Store metadata, HLTB, tags, demo link — rarely changes for an existing game |
| `games:`, `player:`, `wishlist:` | `LIBRARY_CACHE_TTL_MINUTES` | 6 hours | Changes when users buy games / edit their wishlist |
| `search:` | `SEARCH_CACHE_TTL_MINUTES` | 1 day | Game name → appid search results — much shorter than the other game-details tiers since new games ship regularly |
| `news:` | `NEWS_CACHE_TTL_MINUTES` | 6 hours | Recent news/announcements for a game — changes far more often than store metadata (patch notes, event posts), so it shares the library tier's cadence rather than the 60-day META one above |
| `itad-bundles:`, `itad-shop:`, `itad-appid:`, `itad-gid:`, `itad-price:` | `BUNDLES_CACHE_TTL_MINUTES` | 2 hours | IsThereAnyDeal bundle listings, the Steam shop id, appid↔gid resolutions (near-permanent in reality, but cheap to over-invalidate alongside the shorter-lived bundle/price data — see the Bundles section above), and per-region price lookups |

Run `npm run cache:clear` to wipe all cache entries without deleting the database file.

These TTLs are generous because both `getCached` and every `lib/steam.js`/`lib/hltb.js` fetch function accept `{ force: true }` to bypass the cache read for one call (the fetch still writes fresh data back to the cache). This backs two user-facing "↻ Refresh" affordances rather than being needed for background freshness:

- The **accounts bar's per-account "↻"** (both pages, see `public/accountsBar.js`) re-POSTs `/api/common-games`/`/api/wishlist` with `refreshIds: [steamid, ...]`, forcing fresh owned-games/player/wishlist data for just that one account rather than every account in the search. `getPlayerSummaries` takes a matching `forceIds` option so a single `GetPlayerSummaries` batch call can bypass the cache for only the listed IDs. (There used to be a coarser search-bar-level "↻ Refresh" button on both pages forcing the whole search; it was removed in favor of this once the accounts bar existed to hang a per-account control on.)
- The **side panel's Refresh button** re-fetches `GET /api/game-details/:appid?refresh=1`, forcing fresh rating/HLTB/store metadata/tags for that one game only, and in parallel `GET /api/game-news/:appid?refresh=1` for that game's news (see `handlePanelRefresh` in `panel.js`) — two separate requests since news isn't part of `fetchGameDetails` (see the panel.js bullet above). Both always count against their respective rate limiters (`DETAILS_RATE_LIMIT_MAX`/news's own limiter sharing that same budget) — the cache-hit skip is disabled for `refresh=1`, since a forced call never is a cache hit.

Neither refresh path touches `resolve:` — a vanity-URL mapping isn't expected to change, so there's no user-facing reason to force it.

### URL / sharing

Players are encoded as `?u=` query params. A single-account player is `?u=alice`; a multi-account slot (Steam Family) is `?u=alice,bob_family` (comma-joined). Old single-account URLs are fully compatible. Members within each slot and slots themselves are sorted alphabetically so the same comparison always produces the same URL. `history.pushState` is used for explicit searches; `pushState: false` is used when restoring from URL on load or back/forward navigation to avoid polluting history. Every URL-writing function on both pages runs its params through `reorderUrlParams` (`public/urlState.js`) before writing, so the same state always produces byte-identical query strings regardless of write order. `sort` is omitted from the URL entirely when it matches the default (`score` descending) rather than always spelling out `-score`.

The Library Explorer (`public/library.js`) pushes exactly one history entry per genuine new action (Load button, recent-search click, tab switch, per-account refresh is `push: false`) instead of the 2-3 partial `updateUrlParams` pushes each of those used to fire (clearing `game`/`shot`, then setting `u`, then `tab` — each its own entry); everything else (panel open/close, lightbox step, restoring from a URL/back-forward navigation) uses `replaceState`. A `popstate` listener (`loadFromUrl`, mirroring `app.js`'s own) makes browser Back/Forward actually work on this page — previously the URL changed on every action but nothing reacted to History API navigation at all.
