# Frontend

A Solid.js single-page app in `public/`, TypeScript throughout, bundled by Vite. One HTML entry (`index.html` → `AppRoot.tsx`), `@solidjs/router` for navigation, and a persistent shell that survives every route change.

The data model it renders — accounts, lists, combines, the localStorage schema — is [lists-and-accounts.md](lists-and-accounts.md). This file is the machinery: routes, modules, reactivity, the table, the panel, URL state.

## Routes

| Path | What it is |
|---|---|
| `/` | Home — account picker/header, the folder/list tree, combine setup |
| `/lists/owned` | Owned games for the effective current account |
| `/lists/wishlist` | That account's wishlist |
| `/lists/bundle/:bundleId` | One bundle's games |
| `/lists/:listId` | A user list (manual or dynamic) |
| `/bundles` | Browse/discover bundles — a table of bundles, not of games |
| `/game/:appid?` | "Recently Looked Up", and the canonical link for one game |
| `/about` | Static about page |

Path for "which list", query params for state within it (`?u=`, `?game=`/`&shot=`, view-sharing params). `/lists/owned`, `/lists/wishlist` and `/lists/bundle/:bundleId` are registered before the generic `/lists/:listId`; `@solidjs/router` ranks by segment specificity regardless of declaration order, so the ordering documents intent rather than being load-bearing. The production catch-all that makes these real paths work on a cold visit is in [architecture.md](architecture.md).

`/game/:appid?` is **both** the Recently Looked Up list's own address and the canonical single-game link — not two routes. `ListRoute` renders it as kind `recent`, with `params.appid` acting as an initial focus rather than a lesser standalone view.

**Looking up a game never navigates away from a route that has a list context of its own** — the nav-bar search box and a panel's DLC/base-game links open in place (a real row if the appid is already loaded, a standalone panel via `?game=` otherwise). Only a route with no such context (Home, `/bundles`, `/about`) navigates, to `/game/:appid`. See `AppShell.tsx`'s `openGameGlobally`.

## Module map

**Shell and routes**

- `AppRoot.tsx` — mounts `<Router>` with `AppShell` as its `root`.
- `AppShell.tsx` — the persistent shell: nav bar, ⚙ Preferences popover, global game search, the shared panel + lightbox (mounted once, not per route), and the `?u=` resolve effect for the whole app.
- `AccountChip.tsx` — nav-bar chip saying whose lists are on screen, with Owned/Wishlist links (inline on a wide viewport, in its popover on a narrow one) and a recent-account switcher. Deliberately thinner than Home's account section — a nav affordance, not a second copy of it.
- `ListRoute.tsx` — the generic list viewer (table + docked panel) behind every `/lists/*` and `/game/*` route; owns per-kind loading, columns, price loading, and the hero card's contents.
- `HomeRoute.tsx` — account picker/header plus the folder/list tree and combine form.
- `BundlesBrowseRoute.tsx` — `/bundles`, the bundle picker as a real table.
- `AboutRoute.tsx`, `ShortcutsModal.tsx`, `ListHero.tsx` — static about page; the `?` shortcuts dialog (rendered once by the shell); the hero card every list route opens with.

**Account and list model** (all pure/plain modules over `prefs.ts`, no Solid reactivity of their own — see [lists-and-accounts.md](lists-and-accounts.md))

- `accountsStore.ts` — `myAccount`/`currentAccount`/`recentAccounts` CRUD, `getEffectiveCurrentAccount()`, and the `ACCOUNT_CHANGED_EVENT` broadcast every consumer re-reads on.
- `accountOverride.ts` — the `?u=` half: parse, resolve, hand to `accountsStore` as an override that is never adopted into the stored preference.
- `accountData.ts` — owned/wishlist/overview fetches for a resolved account.
- `listsStore.ts` — folder/list CRUD, soft-delete, and the two structural-cycle guards (a dynamic list can't depend on itself transitively; a folder can't move into its own descendant).
- `listResolve.ts` — resolves a `ListRef`/`GameList` to appids, with every impure dependency injected so it and its tests never touch the network or localStorage.
- `combine.ts` — the pure union/intersect/subtract/group-by-membership engine over resolved sets.
- `listLabels.ts` — how an op and a source read on screen, shared by the hero card, Home's combine form, and the tree.
- `myOwnership.ts` — one cached pair of owned/wishlisted appid sets for the effective account, behind both the panel's badge and the search dropdown's markers.
- `recentGames.ts` — the recently-looked-up list backing `/game`.
- `bundleData.ts` / `bundleRows.ts` / `bundleBrowseStore.ts` — bundle fetch/flatten/resolve; the flat row shape `/bundles` sorts over; the last-browsed list `/lists/bundle/:bundleId`'s ‹/› nav steps through.

**Table, panel, and shared plumbing**

- `gameColumns.ts` — every game-table column definition and its render/format/compare/bucket helpers (see below).
- `rowStore.ts` — `createRowStore`: the appid→index bookkeeping and the `getRow`/`mutateRow` pair over a route's Solid store array.
- `streamBatcher.ts` — batches a high-frequency mutation stream into one `batch()` per flush.
- `staleGuard.ts` — generation counters for "a newer load superseded this one".
- `priceLoading.ts` — the `POST /api/prices` call and the row-field mapping/fallbacks around it.
- `panel.tsx` / `panelData.ts` / `panelNav.ts` / `panelHistory.ts` / `panelKeyboard.ts` / `ownerList.ts` / `achievementsRequest.ts` — the side panel and its per-game data, prev/next nav, DLC trail rule, keyboard handler, and the pure halves of the "Owned by"/achievements cards.
- `lightbox.tsx` / `mediaItems.ts` / `lightboxTime.ts` — screenshot/video lightbox, its ordered media list, and the one pure formatter its test needs.
- `gameSearch.ts` — the combobox/debounce UI for "look up any game" (the shell owns where results go).
- `urlState.ts` — param parsing, canonical param order, and the `?game=`/`&shot=`/`?u=` writers.
- `prefs.ts` / `prefsPopover.ts` / `region.ts` / `navPopover.ts` — the localStorage preference blob; the ⚙ panel's contents; the region preference and its detection; `<details>` popover open/close/positioning.
- `tableViewPrefs.ts` — restore/persist/share/reset a table view.
- `clipboard.ts` / `CopyButton.tsx` — the one copy-then-confirm helper behind every copy button (`copyWithFeedback` for the panel's/tables' plain DOM buttons, `<CopyButton>` for JSX call sites), with a `window.prompt` fallback where the Clipboard API isn't available (it needs a secure context, and can be permission-denied).
- `pageTitle.ts` — the two-layer `document.title` (route context, overridden by an open game).
- `types.ts` — `Game`, `ReadonlyGame`, and the account/list interfaces; the single source of truth for row shape.
- `utils.ts` — shared formatting/scoring helpers (`scoreColor`, `formatMoney`, `computeSteamdbRating`, `dealRecordTier`, …).
- `style.css` — all styles.

## Reactivity

Everything the frontend renders is driven by Solid's own reactivity — there is no "please re-render" call anywhere in the app, and reintroducing one is the mistake this section exists to prevent.

Three kinds of state, three mechanisms:

- **A game/row's data** lives in a Solid **store** owned by the route that loaded it (`createStore<Game[]>` in `ListRoute.tsx`, reached through `rowStore.ts`). Writes go through `rowStore.mutateRow(appid, fn)` — `produce(fn)`, so the callback gets a draft that supports plain `draft.field = x` assignment — and the store notifies per field, so a field written as the details stream lands patches only the cells and panel lines that read *that field*. `standaloneRows` (a small `createStore<Record<number, Game>>` in the same file) does the same job for a game opened as a standalone aside rather than as one of the list's own rows (a nav-bar lookup, a DLC/base-game hop): its details arrive asynchronously too, so it needs a store just as much as a table row does.
- **The side panel's own UI state** (which game is open, hero index, which collapsibles are expanded, …) is plain signals in `panel.tsx`, set directly by its own click handlers.
- **Everything the panel fetches for itself** (news, achievements, "Owned by", ownership status, price, DLC) is a `createResource` keyed on whichever game is open, created in one explicit module-level `createRoot` (the panel is a singleton whose data outlives every render of it, so that's its owner). The fetching and session-caching is `panelData.ts`; the resource is only the wiring. A resource gives four things the hand-rolled version each had to carry itself: `.loading` instead of an `xLoading` flag on the row, the value instead of a field on the row, automatic discard of a superseded response instead of an `if (panelGame() === game)` guard, and — being a signal — re-rendering with no notify call. `refetch()` is the panel's ↻; each fetcher reads `info.refetching` as "force" (bypass both the session cache and the server's TTL).

Every resource **source** resolves to a *primitive* (an appid, or an `appid:account` string), never an object literal: `createResource` memoizes its source with `===`, so an object would refetch every time the source merely recomputed — e.g. the DLC source re-runs whenever any collapsible anywhere is toggled, and must not turn that into a fetch.

What this replaced, and why it matters: game rows used to be **plain mutable objects plus a manual notify**. `panel.tsx`'s loaders wrote their results onto the row (`game.news = data.news`), which meant the panel could never be handed a store row (Solid rejects a direct write on a proxy), so `rowStore.ts` kept a second, deliberately plain **clone** of every row for it — and since a plain object's writes are invisible to Solid, ~30 call sites across `panel.tsx` and `ListRoute.tsx` had to call an exported `renderPanelBody(game)` that bumped a `revision` counter signal. `revision` was read in one coarse tracked block wrapping the whole panel body, so **every** notify tore the entire body down and rebuilt it: measured live, ~6 full teardowns per panel open (five async loaders, most bumping on start and finish), each discarding hover state, keyboard focus, and the scroll-spy's imperatively-assigned `active` class. The user-visible symptom that led here was the subnav's "Overview" button blinking several times per open. After the conversion the same open rebuilds the subnav **once** and patches ~30 nodes.

Three rules keep it that way:

1. **One reactive source of truth per row; the only write path is its store's setter.** Enforced by the type system: readers take `ReadonlyGame` (`types.ts`), so `game.field = x` outside a `produce` draft is a typecheck failure rather than a silent no-op. `Readonly` is deliberately shallow — it stops `g.details = …`, not `g.details.rating = …`, and `details` is only ever replaced wholesale.
2. **Async state belongs in `createResource`, not in booleans on a domain object.** `news`/`newsLoading`/`newsError`, `achievements`/`achievementsLoading`/`achievementsAccountId`, `priceLoading`, `dlc`/`dlcLoading`/`dlcPartial` and `owners` are all gone from the `Game` shape for this reason. (`inLibrary`/`onWishlist` stay — they're the *table's* copy, stamped onto rows for the ✓/☆ name-cell markers; the panel reads its own `ownership` resource instead, so a standalone lookup that was never a row still gets a badge. Both go through `myOwnership.ts`'s one cached pair of sets, so they can't disagree.)
3. **Never capture a reactive read into a plain `const` in a component body** — read signals and store fields inside JSX or a `createMemo`. This is what `npm run lint`'s `solid/reactivity` rule checks, and it's why the panel is now a set of small components (`PanelSubnav`, `HltbSection`, `RefreshButton`, …) rather than one 250-line body of derived `const`s: a component function runs once and is not a reactive scope. The one deliberate exception, with an `eslint-disable-next-line` and a comment saying why, is `PanelRest`'s `const g = props.game` — the row *object* is stable for the mount (`PanelBody` renders it under a `keyed` `<Show>`, so a different game means a new component), and capturing a store row is not the same as capturing a field of it.

Still deliberately imperative, and fine as such: the subnav scroll-spy measures section positions and toggles a class (re-run from a `createEffect` when the set of buttons changes), `panelNav.ts` renders the prev/next/random bar into `#panel-nav`, and `lightbox.tsx` manages its own DOM.


## Rows, streaming, and stale loads

- **Row data is a real Solid store (`createStore`), owned by the route that loaded it, not a plain mutated-in-place array.** This replaced an earlier `@vates/data-table-vanilla`-era bug (`setData()` only re-rendering a row when the object at its rowKey was a genuinely new reference) and the `public/rowCache.ts` reference-copy workaround built for it — both retired once every page's table ran on a real store instead. A bare `createStore` isn't a drop-in fix on its own, though: Solid's dev mode actively blocks a direct `row.field = x` assignment against a store proxy. The actual mechanism:
  - Every mutation site goes through `rowStore.ts`'s `mutateRow(appid, fn)`, which applies `fn` via `produce(fn)` (`solid-js/store`) against the store — `produce` hands its callback a draft that *does* support direct property assignment, diffing it against the real store on return. This is why the existing mutate-in-place helpers (`applyDetailsEvent`, `priceLoading.ts`'s `applyPriceInfo`/`nullMissingPriceFields`/`nullAllPriceFields`) needed no signature change at all — `mutateRow` just wraps a call to them in `produce()`.
  - Because each array element is itself a store-proxied object, the table's own per-cell rendering re-renders exactly the cell that changed with no need to swap in a new object reference — confirmed by reading `@vates/data-table-solid`'s source: each `<td>` is a small reactive insertion that reads `row[column.key]` directly, the same JSX-level tracking Solid gives any store-property read. 
  - **Superseded — see Reactivity above.** `panel.tsx` used to be unable to take a store-proxied row at all: its own lazy loaders mutated whatever `Game` object they were handed via plain `game.field = x` writes, so every page kept a second, deliberately plain `panelRows` clone of each row for it, and a `revision` counter signal (bumped by an exported `renderPanelBody(game)`) stood in for the reactivity those plain writes couldn't provide. Those loaders are `createResource`s now, nothing outside a store writes to a row, and all three of `panelRows`/`revision`/`renderPanelBody` are gone.
  - A caller handed a game that isn't one of the route's own store-backed rows (a DLC/base-game link, or a standalone lookup) sees `mutateRow` return `undefined`; it writes to `standaloneRows` instead — see Reactivity above. This used to fall back to mutating the plain object directly.
  - **`getRow`/`mutateRow` and the `rowIndex` map behind them are one shared factory, `createRowStore` in `public/rowStore.ts`** — three pages each carried an identical copy of this bookkeeping before it was extracted. (Its `panelRows` half is gone — see Reactivity above.)
  - **A streaming/high-frequency `mutateRow` caller must batch, or `@vates/data-table-solid`'s live `tableData()` reactivity fully re-sorts/re-filters/re-paginates once per *event* instead of once per *flush*.** Confirmed live: a ~1150-game library took **~33 seconds of continuous, unresponsive main-thread work** to finish streaming before this was fixed, and ~6-7 seconds after — reproduced identically on the pre-Solid-migration-pilot commit too, so this had been silently broken since the table's own Solid conversion (the pre-Solid `@vates/data-table-vanilla` table got this same amortization for free via an explicit, timer-gated `table.setData()` call, which the conversion dropped once there was no more `setData()` call left for that timer to gate — not introduced by any of the row-store/stale-guard work above). Two distinct shapes of this bug, two different fixes:
    - **Spread over time** (the SSE `/api/game-details/stream` loop, one event per `await reader.read()` tick — `ListRoute.tsx`'s `streamGameDetails`) — needs `public/streamBatcher.ts`'s `createStreamBatcher`: queues events and applies them inside one `batch()` per ~150ms flush instead of immediately per event, restoring the cadence `scheduleFlush()`'s timer already ran at (its `onFlush` option covers whatever else — `updateLastPlayedTooltip`/`updateStatus` — used to piggyback on that same timer). Each queued event carries the generation (`loadGuard`, `staleGuard.ts`) it belongs to and is dropped rather than applied if stale by flush time, since two overlapping loads could otherwise interleave their events into the one shared queue.
    - **One synchronous burst** (a price-lookup response processed in a single loop with no `await` between iterations — `loadWishlistPrices`/`loadBundlePrices`) — just needs the existing loop wrapped in a bare `batch()`; there's no "spread over time" aspect to debounce, so the timer-based batcher would be overkill.
    - Deliberately **not** folded into `rowStore.ts`'s `mutateRow` itself — `mutateRow` also backs one-off calls (a single achievements load, a DLC toggle, a "↻ Refresh" click) that need to apply immediately, not wait out a flush window: batching is opt-in, on the specific high-frequency call sites, not on the shared mutation path everything else also depends on.

## The game table

Every list of games — owned, wishlist, bundle, recent, user — renders through the same `@vates/data-table-solid` table over the same shared column set (`public/gameColumns.ts`), with `ListRoute.tsx` layering per-kind columns on via `insertColumnsAfter`:

- **owned** — Played (h), Last Played, after the HLTB cluster.
- **wishlist** — Wishlist Rank, then `PRICE_COLUMNS`, plus Added.
- **bundle** — ownership status, Tier Price, Add-on, then `PRICE_COLUMNS`.
- **recent** — ownership status only; **user** — plain `CORE_COLUMNS`.

Default sort is Weighted Rating descending, except a bundle (cheapest tier first, then rating). `/bundles` is a table too, but of bundle rows rather than `Game` rows, so it has its own small column set — reusing `gameColumns.ts`'s generic bucket/compare helpers so a price/date/count column there groups and sorts like its counterpart in a game table.

`gameColumns.ts` holds the definitions and their render/format/compare/bucket helpers: `CORE_COLUMNS` (identity, scores, HLTB, dates, classification, compatibility, extras — every column every kind shows) and `PRICE_COLUMNS` (Steam Full Price, Best Deal, Discount, Price Status, Best Deal Shop, the three historical lows — wishlist and bundle kinds only, since an owned game has nothing to buy), plus `insertColumnsAfter` and the supporting helpers (`fmt`, `renderScoreNum`, `renderBestDeal`, `renderPrice`, `renderCut`, `discountPct`, `computePriceStatus`, `PRICE_STATUS_TIERS`, `PRICE_TIERS`/`priceTierBucket`/`formatPriceTier`, `TYPE_LABELS`, `protonDbValue`, `renderProtonBadge`, date/log-bucket helpers, etc.). It imports `scoreColor`/`dealRecordTier`/`DEAL_RECORD_TIERS`/`formatMoney` from `utils.ts` directly rather than reading them off the global scope (that used to be a bare-global read back when `utils.ts` was a plain script and this file the sole ES-module exception to it; see CLAUDE.md's git history). Its compare/bucket helpers still need real imports from `@vates/data-table-core` (`compareMissingLast`, `bucketNumericRange`, etc.) — a genuine direct dependency of the app's own code, kept as an explicit `package.json` entry rather than relying on it being hoisted in as a transitive dependency of `@vates/data-table-solid`. Column *definitions* have zero per-kind variation once the per-kind columns are factored out via `insertColumnsAfter`; those (Tier Price/Add-on's render code, the wishlist and owned column objects) stay local to `ListRoute.tsx`.
  Most columns also carry a `category` (`ColumnDefBase.category`, `@vates/data-table-core` >= 0.13) matching this file's own section headers — `Scores & Reviews`, `How Long To Beat`, `Play Time & Dates` (releaseDate here, joined by the per-kind Played/Last Played/Added columns), `Classification` (also the Add-on column), `Compatibility`, `Extras`, and `Pricing` (all of `PRICE_COLUMNS` plus Tier Price) — so the Columns/Sort/Group dropdowns' otherwise-flat 25+-column lists (and the Filter dropdown's left pane) collapse into per-category submenus instead. Identity (`capsule`/`name`) and single-page columns with no sibling to group with (Wishlist Rank) stay uncategorized — a submenu isn't worth it for one or two columns, and both of those are default-visible besides. The pre-redesign pages used to import `processData`/`searchData` from `@vates/data-table-core/internal` for their own `getGameList` (prev/next-nav ordering) — that sub-path is explicitly documented as unsupported/no-semver-guarantee (see that package's own README), and reaching into it was flagged as vatesfr/data-table#22. A later release added `table.getProcessedData()` closing that gap; the app has since moved to `@vates/data-table-solid`, whose `TableState` exposes the equivalent as a `processedData()` accessor that `getGameList` calls directly — nothing imports `@vates/data-table-core/internal` anymore.

  - `renderBestDeal` (`public/gameColumns.ts`) deliberately does NOT put the shop name in the cell's own text (an earlier version did, as "$11.24 · Fanatical") — instead the price is colored/badged when it's at or below a historical low, via the shared `dealRecordTier(price, row)` (`public/utils.ts` — see its own bullet above): bright teal + bold + 🔥 for an all-time low, green + ★ for a 1-year low, amber + ☆ for a 3-month low, each checked only when no rarer tier already matched. `<=`, not `<` — the current deal genuinely can BE the historical low itself (it's what set it), not only ever beat it. The shop name still exists (a native `title` tooltip on the price, and its own hidden-by-default `bestDealShop` column for grouping/filtering) — dropped from the cell text specifically to leave room for the low-price indicator, judged the more actionable of the two at a glance. The tooltip itself is deliberately terse — just the shop name (`"Fanatical"`), plus `dealRecordTier`'s own `tooltipLabel` (`" — all-time low"`/`" — 1-year low"`/`" — 3-month low"`) appended when it qualifies — with no "cheapest current price" restatement, since that's already what the Best Deal column itself means; an earlier draft spelled that out in every tooltip and it read as redundant once actually seen hovering over a column already labeled "Best Deal". `panel.tsx`'s `priceHtml` (the side panel's Price card — it doesn't import `renderBestDeal` from `gameColumns.ts` even though both are ES modules now, since that file pulls in `@vates/data-table-core`, meaningless for a plain side panel) still keeps its own copy of this same tier-to-badge logic, built on the same shared `dealRecordTier` — a 3-month-low tier was once added only to `computePriceStatus`/`PRICE_STATUS_TIERS` before anyone remembered to add it to `renderBestDeal`/`panel.tsx`, which is exactly the divergence pulling the tier logic itself into `dealRecordTier` now prevents, even where the surrounding render code still can't be the literal same function.
  - **Every price column (Tier Price, Steam Full Price, Best Deal, All-Time/1yr/3mo Low) and Discount are `groupable: true`, bucketed rather than grouped by exact value** — a raw price/percentage is near-unique per row, which would otherwise produce one group per row (the same problem `bucketNumericRange`/`bucketLogRange` solve for `hltbAll`/`reviewsTotal` elsewhere in this file). Discount uses a plain fixed 25-point step (`bucketNumericRange(25)`/`formatNumericRange(25, '%')`) — a percentage is already bounded 0-100 with no long tail, so an even step is enough. The five/six price columns instead bucket against `PRICE_TIERS` (`[0, 5, 15, 30, 50, 75, 100]`), a hand-rolled staircase matching Steam's own common price points ($4.99/$14.99/$29.99/$49.99/$74.99) — neither a fixed linear step (too coarse or too fine depending on where you set it) nor the log-scale `bucketLogRange` grid (geometric, so it can't land on both "$50" and "$75" as distinct boundaries) reproduces those specific breakpoints. A real `$0` gets its own "Free" bucket, same "real zero is its own group" treatment `halfDecadeBucket` gives a real `0` review count. No currency symbol in the bucket label itself (`formatPriceTier`, e.g. `"5–15"` not `"$5–$15"`) — the selected region's currency isn't fixed to USD (see `tierCurrency`/`priceCurrency` above), and hardcoding "$" would mislabel every other currency's amounts. Tier Price's missing-bucket label is "Varies" (`formatMissingGroup(formatPriceTier, 'Varies')`) rather than the generic "—" the other price columns' missing bucket uses, matching `renderTierPrice`'s own "Varies ≠ no data" distinction. `PRICE_TIERS`/`priceTierBucket`/`formatPriceTier` live in `public/gameColumns.ts`; `ListRoute.tsx`'s own `TIER_PRICE_COLUMN` reuses them for the one price column that isn't in the shared cluster.
  - **A hidden-by-default `priceStatus` column** (`computePriceStatus`, `public/gameColumns.ts` — `PRICE_STATUS_COLUMN` is one shared column object) categorizes a row's current deal as `All-Time Low` / `1yr Low` / `3mo Low` (all three via the shared `dealRecordTier` — see `public/utils.ts`'s own bullet above) / `On Sale` (a real discount that isn't, yet, any kind of historical low — the catch-all for a row that doesn't fit any of the other tiers) / `Not Discounted` (a confirmed `bestDealCut === 0`) / `—` (no price data at all, or `bestDealCut` itself unknown) — computed as a `value()` function, so it needs no new fetch or stored row field and stays correct across a refresh with no extra `markRowChanged` bookkeeping. Exists specifically so "which games are at their all-time low right now" (or any of the other tiers) is a direct filter/group instead of only ever eyeballed off the Best Deal cell's badge, which the column set's other price/discount columns individually can't answer either (Discount's own bucketed grouping only answers "how big a discount", not "is this a record").
    - **`PRICE_STATUS_TIERS`** (`gameColumns.ts`) is the single ordered worst-to-best list backing both the column's sort and its visual treatment, so the two can't drift apart the way two separately-maintained arrays could — and, since its three record entries spread `color`/`icon`/`bold` straight off `DEAL_RECORD_TIERS` (`public/utils.ts`, reversed to worst-to-best and prefixed with the `Not Discounted`/`On Sale` non-record labels) rather than restating them, it also can't drift from the Best Deal cell's own badge. `PRICE_STATUS_ORDER` (feeding `comparePriceStatus`, same "ordered array + `indexOf`" shape as `PRODUCTION_TIER_ORDER`/`PROTON_TIER_ORDER`) is just `PRICE_STATUS_TIERS.map(t => t.label)`, and `renderPriceStatus` looks a value's `color`/`icon`/`bold` up in the same list. `defaultSortDir: 'desc'` on the column shows All-Time Low rows first on a fresh click.
    - **`renderPriceStatus` reuses `renderBestDeal`'s own color/icon treatment verbatim** for the two tiers it already covers — bright teal + bold + 🔥 for All-Time Low, green + ★ for 1yr Low (`scoreColor(90)`/`scoreColor(70)`, the same "excellent"/"good" tiers) — extended one step further for 3mo Low: a real record, just over a shorter window, so it gets `scoreColor`'s next tier down (amber, `scoreColor(55)`) and an outline star (☆) instead of 1yr Low's filled one, reading as "still a record, just a lesser one" rather than an unrelated icon. On Sale and Not Discounted stay plain text — not being a record isn't a bad thing worth flagging, so nothing there competes for attention with the three genuine record tiers. `render` (not just `format`) also drives group headers for this column per the table library's own contract, so a grouped view shows the same colored/badged label as the cell would.

A table's view (visible columns, sort, grouping, filters) auto-persists locally as it changes — one `prefs.ts` key per system kind (`ownedListView`/`wishlistListView`/`bundleListView`/`recentListView`, the bundle one shared across all bundles rather than per-bundle), while a user list stores its own `tableView` on the list itself and so resets around `resetTableView` rather than through it. It is applied *after* `table.setViewState({ sorts: DEFAULT_SORT })` at construction, so a persisted view overrides the default sort where one exists but the default still applies on a first-ever visit.

It is deliberately **not** written to the URL as it changes: "🔗 Share view" snapshots the current view into `?tv=` on a copied link only (one shared param name — only one table is ever on screen per route), and never calls `history.replaceState`. A link left in the page's own address bar goes stale the moment the user makes one more change to the table, silently showing a URL that no longer matches the screen. An incoming `tv` param wins over the stored default but only once: `restoreTableView` applies it, seeds it as the new stored default and strips it from the live URL — a table is rebuilt far more often than "page load" (a new account, a tab switch, another bundle), and without consuming it a shared link would clobber later edits every time.

## Each list kind, in practice

Every route opens with a **hero card** (`ListHero.tsx`) carrying the list's name as the page `<h1>`, an optional lead, kind/shop/account chips, the route's own actions, and that list's facts as labelled tiles — all off fetches the route already makes. The card is deliberately dumb: no data, no per-kind branching, callers pass already-formatted values, so "what does a wishlist show" stays answerable in `ListRoute.tsx` alone. Its dates are locale-formatted while the tables' are ISO — a card is prose read one at a time, a column is scanned down a page against its own sort.

- **owned / wishlist** — name the account they show (avatar, profile link, Family merge count) with Games/Updated/Prices tiles. They treat a `?u=` link as authoritative: while it resolves, and if it fails, the stored account is deliberately not loaded in its place.
- **bundle** — Ends (with a countdown), Games, Tiers as price chips, Published, Prices, plus ITAD's editorial note; ‹/› steps through whatever `/bundles` last showed, in the order it showed it (`bundleBrowseStore.ts`). Games with **no Steam listing** (courses, asset packs, shop-exclusive keys) render below the table as a collapsed "N more in this bundle, not on Steam" section, and the status line reads "3 of 13 games matched to a Steam listing" — the route used to drop them, so a table holding only what resolved was passing itself off as the whole bundle.
- **recent** — says it's local browser history; `params.appid` focuses one game without making it a different kind of view.
- **user** — its manual-or-op chip with Games/Folder/Sources/Edited. A dynamic list states its formula in the card: each source named (`listLabels.ts`), linked to its own address, carrying what it contributed (`Alice — Owned 343 ∪ Alice — Wishlist 115 = 457`), with a dangling source flagged in place rather than silently omitted. `group-by-membership` renders one real table **per group** (generalizing the old Comparison page's "one table per owner set, most owners first"); every other op flattens to one table.

Per-group tables skip view persistence (one list has room for one stored `tableView`, and splitting that across however many groups a combine produces isn't solved) and row selection, which is only wired up on the single-table path.

`/bundles` is itself one of these tables, over bundle rows rather than games: a cover, title, shop, game count, cheapest tier price, published/ends dates, plus hidden tier-count and active/expired columns, newest first. ITAD has no bundle-level image, so the cover is a 2×2 grid of four of the bundle's own games' `banner145` assets (already in the list response, no extra request), alongside a per-shop color chip (hue hashed from the shop name, so a shop ITAD adds later needs no code change) and a colored countdown on anything ending within the week. Sorting/filtering/grouping are the table's own over the whole loaded set; only "include expired" still round-trips to the server, since that reaches ITAD's much larger archive rather than the ~30-40 active bundles a default load pulls in full.

## Global search and the account chip

The "look up any game" box is a single nav-bar-level search in the shell, not one per route. Focusing it while **empty** shows recently looked-up games in the same dropdown under a heading, with a sticky "See all recently looked up →" row leading to `/game` — the convention every store and browser search bar already uses. They're `GameSearchResult`-shaped like any match, so the roving ArrowUp/Down selection, the ownership markers and `onSelect` all apply unchanged; the heading and "see all" row are `role="presentation"`, outside the listbox's option semantics. `gameSearch.ts` takes the list and the "see all" destination as options rather than importing `recentGames.ts` — it stays the combobox it was carved down to.

`AccountChip.tsx` says who the app is showing, re-read on `ACCOUNT_CHANGED_EVENT` so a `?u=` link resolving after mount updates it in place, with a 🔗 marker when a link's account is showing rather than the stored one. Both nav popovers (this and ⚙ Preferences) share `navPopover.ts`: `<details>` has no built-in outside-click/Escape close, and the panel is positioned in JS because `.site-nav`'s flex-wrap moves its triggers with viewport width — confirmed live on a real Galaxy S10 (Firefox) as the panel running off-screen, which ruled out a CSS-only anchor. The popover also carries **copyable Steam identifiers** — `accountsStore.ts`'s `accountIdentifiers` (the stored custom-URL name, else the steam64 id), read from the slot's own data since this chip fetches nothing: one for the current account, and one per member beside each recents row (outside its switch button, which can't nest one).

## The side panel

`panel.tsx` is a single instance mounted by `AppShell.tsx`, not one per route — `ListRoute.tsx` is its only caller now, and only ever opens/closes it (`panelOpen(game)`/`panelClose()`/`isPanelOpen()`/`getPanelGame()`/`panelStepHero()`/`panelHandleEscape()`). `PanelOptions` survives from when three separate pages each configured their own instance; only `onNavigateGame` is passed today, and `onTagClick`/`isTagActive`/`enableTagFilters` are dead weight left in place rather than ripped out by a pass that was out of scope to do it (panel tags are plain text as a result).

**Docked, not modal.** A list route renders as two live columns, table and panel, both interactive; there is no backdrop, no focus trap, and no click-outside-to-close — the × or Escape closes it. Clicking another row swaps the content in place. A narrow viewport falls back to a full-screen overlay, the one exception. Opening moves keyboard focus into the panel (its heading/close button) so screen readers announce it, but Tab flows freely back out to the table afterward. Opening and closing only ever `replaceState` — Back never steps through panel opens.

**Sections**, in order: hero carousel (`PanelHero`, swipeable, feeding `lightbox.tsx`), a demo banner when the game has a free demo, ownership badge, the glance grid (Weighted Rating, HLTB, reviews, ProtonDB…), How Long To Beat, Achievements, "Owned by", News, Price, DLC/base-game links, tags, and the ⋯ More links. The collapsible ones share `CollapsibleCard`; a subnav scroll-spy tracks position (still deliberately imperative — it measures and toggles a class).

- **News** — every headline in the game's own `steam_community_announcements` feed (up to 20, `extractNews`' cap), each linking to the post, collapsed behind a chip whose ↗ goes to the Steam news hub. Server-side filtering to that one feed matters: raw `GetNewsForApp` also aggregates syndicated third-party press in whatever language the outlet publishes in, which for some games outnumbers official posts entirely and doesn't match the store page's News tab. There's no separate 📰 header icon — a game with zero official posts renders no card, and a dedicated icon just to go check for unrelated syndicated press isn't worth it.
- **Price** — deliberately light: one always-open card with the current Best Deal (same 🔥/★/☆ record badge as the table cell, both built on `utils.ts`'s shared `dealRecordTier`), its Discount, the shop name, and an "IsThereAnyDeal ↗" link in the title for the historical detail the card leaves out. When there's a deal to buy, the *whole line* below the title is the outbound link (ITAD's own per-deal `url`, passed through unmodified) rather than one small shop name — going to buy is the point of the card. It keeps its own copy of the badge render code rather than importing `renderBestDeal`, which would drag `@vates/data-table-core` into a plain side panel.
- **Prev/next/random nav** (`panelNav.ts`, ↑/↓/R) steps the route's own processed row order; `panelKeyboard.ts` binds the page-level shortcuts (Escape, `?`, `/`, hero stepping, random, list stepping) once.
- **The DLC trail** — "← Back to ⟨game⟩" — is `panelHistory.ts`'s `nextHopHistory` rule (pop rather than push when the target is already on top, so bouncing between a base game and its DLC doesn't grow duplicates); the trail itself is a signal in `panel.tsx`, preserved across a hop through `/game/:appid` by its own `pendingHopAppid` latch.
- **↻ Refresh** refetches every panel resource for the open game with `refetching` set, which each fetcher reads as "bypass both the session cache and the server's TTL".

`lightbox.tsx` owns its own DOM (lazy singleton): HLS playback, zoom/pan, touch/swipe, focus trap, loading indicator, `?shot=` deep links. `mediaItems.ts` builds the ordered media list and resolves a shot id to an index; the hero uses `meta.banner` (Steam's own `header_image`, resolved server-side) once metadata loads, guessing the conventional CDN path only as a placeholder before then — that guess 404s permanently for games served from newer asset pipelines.

## URL & sharing

- `?u=` — which account to show. Parsed and resolved once for the whole app by `AppShell.tsx`, read everywhere via `getEffectiveCurrentAccount()`, forwarded across in-app navigation by `withAccountParam`. Full semantics in [lists-and-accounts.md](lists-and-accounts.md).
- `?game=<appid>` / `&shot=<idx>` — which game the current list has open, and which screenshot. Always `replaceState`, never pushed. `/game/:appid` is the canonical shareable address for a game itself; the panel's 🔗 copy-link deliberately omits `?u=`, so a shared game link doesn't send everyone who opens it into the sender's account.
- `?tv=` — a shared table-view snapshot, consumed once on arrival (see the table section above).
- `reorderUrlParams` (`urlState.ts`) puts every URL through one canonical param order, so the same logical state always serializes to the same string regardless of the order its pieces were set; `urlWithParams` is the single place a `URLSearchParams` becomes a URL, returning a bare path rather than a trailing `?` once the last param is deleted.

## Preferences

`prefs.ts` is one flat `{key: value}` JSON blob under a single localStorage key — one blob so the whole set is enumerable at once (a settings screen, or the initial payload a synced account would pull down), while `setPref`'s sync hook stays deliberately per-key so two preferences changing in different tabs can't race each other's writes once a server push exists.

Region is the only user-facing preference today, in the nav bar's ⚙ popover (`prefsPopover.ts` owns the contents; `AppShell.tsx` owns only the `<details>` shell, so nav stays about navigation as more preferences land there). `region.ts` holds the data and logic — a curated list of major Steam pricing regions rather than all 250 ISO codes, `detectCountry()`, and `REGION_CHANGED_EVENT`, which `setStoredRegion` dispatches on `window` on every change so price-showing routes re-price without either side knowing about the other.

- The first entry is always "Auto-detect (⟨whatever it resolves to now⟩)", and `resolveRegion` consults `detectCountry()` live on every upstream call, so auto-detect tracks current signals rather than freezing what they said at populate time.
- `detectCountry` tries the OS timezone first (`Intl.DateTimeFormat().resolvedOptions().timeZone`, via a curated map including Eurozone→`DE`) before `navigator.language` — language is a UI preference, not a location, and very commonly stays "en-US" wherever the user actually is (confirmed live: `LANG=en_US.UTF-8` on a machine in `Europe/Paris`, which the language-only heuristic resolved to `US`).
- The Eurozone label leads with "Europe", not "Germany" — `DE` is just the code Steam/ITAD key Eurozone pricing off, not the concept being picked.
- Region is deliberately not a URL param: it says more about the viewer than about what they're looking at, so a shared link shouldn't override the recipient's own preference.

## Known gaps

Carried over from the redesign's own open-questions list, all still true:

- **Folder/list tree polish** — rename/move/delete on Home use plain `window.prompt`/`window.confirm`; there's no drag-and-drop and no move-between-folders UI at all (`listsStore.ts`'s `moveFolder`/`moveList` have no caller), and no trash/restore UI for soft-deleted lists (`restoreList`/`getLists({ includeDeleted: true })` are ready for one).
- **Panel tag-click filtering** — `panel.tsx` still declares `onTagClick`/`isTagActive`/`enableTagFilters` and nothing passes them, so a tag in the panel is plain text. Rewiring means mapping a tag click onto the route's table filter state — new work, not restoration.
- **Per-account playtime in `group-by-membership` lists** — the "Owned by" card covers the current account's own members only; `listResolve.ts`'s fetchers return bare appid sets, so there's no playtime for any other account in a membership group. Teaching those fetchers to carry per-account playtime is the real fix.
- **The panel self-fetches a price for every opened game**, even on wishlist/bundle lists that already batch-price their rows (`pricesHandledByHost` is gone; nothing suppresses it). That's a duplicate — server-cached — request, but it also fills the panel sooner for a game opened before the batch lands, so it may be the better behaviour; it just isn't a decision anyone made.
- **Live reactivity to the account changing** is partial: `ACCOUNT_CHANGED_EVENT` re-runs Home's account card, `ListRoute`'s owned/wishlist load, and the ownership stamps. Anything else a route derives from the account is still read once per mount.
- **`?game=` restore-on-reload is `ListRoute`-only** — reloading `/lists/owned?game=440` reopens that game; reloading `/?game=440` doesn't, since Home/`/bundles`/`/about` register no route handler with the shell. Rarely reachable: a lookup from one of those routes goes to `/game/:appid` in the first place.
- **No cross-tab sync** — see [lists-and-accounts.md](lists-and-accounts.md).
