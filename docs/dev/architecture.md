# Architecture

An Express backend (`server.js` + `lib/*`, plain CommonJS JavaScript) serving a Solid.js single-page app (`public/*`, TypeScript, bundled by Vite). The backend is a caching proxy over Steam/HLTB/IsThereAnyDeal/ProtonDB — it holds no user data; accounts, lists and preferences all live in the browser's `localStorage`.

- [frontend.md](frontend.md) — the SPA: shell, routes, module map, reactivity rules
- [lists-and-accounts.md](lists-and-accounts.md) — the account/list data model the frontend is built around
- [integrations.md](integrations.md) — every upstream, and what's undocumented about each
- [data.md](data.md) — `db.sqlite`, cache tiers, refresh paths
- [observability.md](observability.md) — `/api/metrics`, budgets, proactive log warnings
- [decisions.md](decisions.md) — computed values (Weighted Rating, Production Tier) and why

## Running & building

```bash
echo "STEAM_API_KEY=your_key_here" > .env   # first time only — only required setting
npm install                                  # first time only
npm start                                    # or: npm run dev:backend  (restarts on file changes)
```

The server binds to `http://127.0.0.1:3000` by default. `default.env` (committed to the repo) holds all settings with their defaults and documentation. Create `.env` (gitignored) with only the values you want to override — `STEAM_API_KEY` is the only required one. The server exits immediately at startup with a clear error message if it is missing.

The frontend source in `public/` is now TypeScript, so the dev flow is two processes (see the module map below and in [frontend.md](frontend.md)):

```bash
npm run dev:frontend    # Vite dev server on :58991 — HMR, transforms the TS sources, proxies /api → :3000
npm run dev:backend     # Express backend on :3000 (restarts on file changes)
npm run dev             # both of the above at once (concurrently), Ctrl+C stops both
```

Open the app at `http://localhost:58991` (Vite), not `:3000`. The dev port is pinned (`vite.config.js`'s `server.port`/`strictPort`) rather than left to Vite's default-or-next-free fallback, since this machine runs several Vite apps at once and a same-app-different-port-between-runs would reset localStorage/cookies/auth (a different port is a different browser origin). `npm run build` (`vite build`, see `vite.config.js`) produces a real bundled/hashed production build in `dist/`; `server.js` serves that instead of `public/` automatically once it exists (`fs.existsSync(dist/index.html)`), falling back to `public/` otherwise. The old single-`npm start` flow still works against a built `dist/` (`npm run build` first) — but note a fresh clone now needs that `npm run build` before `npm start` will serve a working frontend, because `server.js`'s plain `express.static` fallback serves `public/` raw and browsers won't parse TypeScript. `dist/` is gitignored, regenerated by `npm run build`.

Run the test suite with `npm test` (Node's built-in test runner against `test/*.test.js`/`test/*.test.ts`, with `DB_FILE=` so it uses an in-memory database). The tests are still `.js` but import the `public/*.ts` modules directly — Node ≥22.13 (see `engines`) strips the types natively, no build step needed for tests. Run `npm run typecheck` (`tsc --noEmit`) to typecheck the frontend; the compiler is TypeScript 7 (the `tsgo`/Go port). Run `npm run lint` (`eslint public`) for the Solid-specific rules — see `eslint.config.mjs`, and [frontend.md](frontend.md)'s reactivity section for the rule that earns it its keep. There is no formatter configured, and no general-purpose style/complexity rules: `eslint-plugin-solid` is the whole rule set, so match the existing style in whatever file/module you're editing rather than reformatting it.


## Backend modules

- **`server.js`** — Express setup and route handlers only. Its static-file serving picks `dist/` (the `vite.config.js` build output, once `npm run build` has produced one) over serving `public/` directly — see "Running the app" above.
- **`lib/cache.js`** — Persistent cache (`getCached`, `setCache`), disk I/O, process exit hooks.
- **`lib/config.js`** — TTL constants (`LIBRARY_CACHE_TTL_MS`, `RESOLVE_CACHE_TTL_MS`, `RATING_CACHE_TTL_MS`, `META_CACHE_TTL_MS`, `SEARCH_CACHE_TTL_MS`, `BUNDLES_CACHE_TTL_MS`) shared across modules.
- **`lib/dedup.js`** — In-flight request deduplicator (`createDedup`): concurrent calls for the same key share one promise. Its in-flight map, and `lib/steam.js`'s per-host rate-limiting semaphores (`storeLimit`/`tagLimit`/`protonLimit`), are process-local state — correct for this app's current single-process deployment, but would need rethinking (e.g. a shared store) before ever running multiple instances/workers, since each would get its own independent map/semaphore and silently multiply real upstream request volume rather than erroring.
- **`lib/steam.js`** — Steam API calls (`resolveSteamId`, `getOwnedGames`, `getWishlist`, `getPlayerSummaries`, `getGameRating`, `getAppDetails`, `getSteamTags`, `getGameDemo`, `searchStoreGames`, `getGameNews`).
- **`lib/hltb.js`** — HLTB auth + search (`getHLTB`), plus exported `stringSimilarity` and `levenshtein` for unit testing.
- **`lib/groupGames.js`** — Groups slot libraries by exact ownership set (`groupByOwnership`).
- **`lib/itad.js`** — IsThereAnyDeal API calls (`getSteamShopId`, `getBundles`, `resolveSteamAppIds`) backing bundle browsing and every price column. See [integrations.md](integrations.md).
- **`eslint.config.mjs`** — Solid-specific linting over `public/**/*.{ts,tsx}` (`npm run lint`), `eslint-plugin-solid`'s `flat/typescript` rule set. `solid/reactivity` is the rule that matters here — it catches a reactive value (a signal call, a store/props member read) captured into a plain `const` in a component body, where nothing can ever re-render off it; `no-destructure` and `components-return-once` cover the two other spellings of the same mistake. `tsc` cannot see any of it: the code compiles, and renders correctly exactly once. The parser is `@babel/eslint-parser`, **not** `typescript-eslint`, which every other TS project would reach for first: this repo's typechecker is TypeScript 7 (the `tsgo`/Go port), whose npm package ships no JavaScript compiler API at all — `require('typescript').createSourceFile` is `undefined` — so `@typescript-eslint/parser` cannot parse anything here, and its own peer range (`typescript >=4.8.4 <6.1.0`) refuses to install against 7.x in the first place. Babel parses TS+JSX for the linter's purposes (syntax only; none of these rules are type-aware), needs no TypeScript, and was already in the tree as `vite-plugin-solid`'s own dependency — the three `@babel/*` devDependencies are explicit rather than relying on that hoisting, same reasoning as the `@vates/data-table-core` entry. `.mjs` rather than `.js` because `package.json` has no `"type": "module"` (the tests and `server.js` are CommonJS) and Node warns about reparsing a `.js` config that uses `import`.
- **`tsconfig.json`** — Frontend typechecker config: `strict`, `noEmit`, `module`/`moduleResolution: bundler`, `allowImportingTsExtensions`, `verbatimModuleSyntax` (type-only imports must use `import type`), `skipLibCheck`, and `paths: {"/*": ["./public/*"]}` — the latter maps the source's bare-absolute import specifiers (e.g. `import ... from '/utils.ts'`, written exactly as the browser/Vite resolve them against `root: 'public'`) onto the source tree for `tsc`, which has no notion of the web root. `include` is `public/**/*.ts`; the backend (`server.js`, `lib/*`) is intentionally out of scope and stays plain JS. Checked by `npm run typecheck` (see "Running the app").
- **`vite.config.js`** — Builds `public/`'s single HTML entry (the SPA shell) into `dist/`; four separate entry points collapsed to one when client-side routing took over navigation. Also backs the dev server (`npm run dev:frontend`): `root: 'public'` with `server.proxy` forwarding `/api` to `http://127.0.0.1:3000`, so the frontend runs on `:58991` (pinned via `server.port`/`strictPort`, to avoid this machine's several concurrent Vite apps stealing each other's port and resetting localStorage/cookies/auth across runs) against the Express backend's API. `publicDir: false` — `public/` has no passthrough static assets of its own to copy (everything in it is source HTML/TS/CSS that Vite processes as entry points/imports); the option is also disabled to sidestep the naming collision Vite's own "publicDir" convention would otherwise have with this app's frontend source directory happening to be named `public/` too.

## API routes

`server.js` holds Express setup and route handlers only; all upstream work lives in `lib/*`.

| Route | Purpose |
|---|---|
| `POST /api/common-games` | Resolve identifiers, fetch + union owned libraries per slot, group by owner set |
| `POST /api/wishlist` | One account's (or Family's) wishlist |
| `GET /api/game-details/:appid` | Rating, HLTB, store metadata, tags, ProtonDB for one game |
| `POST /api/game-details/stream` | The same, for a list of appids, streamed over SSE |
| `GET /api/game-news/:appid` | That game's own Steam announcements |
| `GET /api/achievements/:appid` | Achievement list + per-account progress |
| `GET /api/search-games` | Store search by name |
| `GET /api/bundles`, `GET /api/bundles/:id`, `POST /api/bundles/resolve` | ITAD bundle listing/lookup, ITAD gid → Steam appid |
| `POST /api/prices` | ITAD prices for a batch of gids or appids |
| `GET /api/health`, `GET /api/metrics` | Config/liveness, and the counters in [observability.md](observability.md) |

Every route is behind a named `express-rate-limit` instance that `skip`s requests it can answer from cache (see [observability.md](observability.md)'s rate-limiter paragraph, and [data.md](data.md) for the cache itself).

**SPA fallback.** Routes are real paths (`/lists/owned`, `/game/440`), not hash routes, so a cold visit or shared link must be served the app shell rather than 404ing: `server.js` ends with a catch-all (`app.get(/^\/(?!api\/)(?!.*\.[a-zA-Z0-9]+$).*/)`) sending `index.html`, placed after the API routes and static-file serving. Vite's dev server does this by default, so it only matters in production.

## Request flow

1. Frontend POSTs `{ slots: [["alice", "bob_family"], ["charlie"]] }` to `/api/common-games`. Each slot is a logical player — multiple accounts in a slot have their libraries unioned before comparison (Steam Family simulation). Legacy `{ users: [...] }` is also accepted and treated as single-account slots.
2. Server resolves every identifier to a Steam64 ID, deduplicates within each slot, fetches all libraries in one parallel pass, unions libraries per slot, groups games by exact set of slot owners, returns `{ groups, slots }`.
3. The frontend renders rows immediately (a `group-by-membership` list renders one table per owner set, most sources first), then POSTs the full game list to `POST /api/game-details/stream` (SSE endpoint) to load rating, HLTB, store metadata, and tags progressively in a single connection. The route works the list through a bounded worker pool (`STREAM_CONCURRENCY`) pulling from a shared cursor, re-checking whether the client is still connected before each appid — not one dispatch per appid up front, which made the disconnect check unreachable (nothing can have closed in the same synchronous tick) and let a single request park its whole list on `lib/steam.js`'s shared semaphore queues ahead of every other user's. The legacy `GET /api/game-details/:appid` endpoint still exists for direct API consumers.
