# Data & caching

The application database, the cache tiers over it, and the three user-facing refresh paths that bypass them. See [observability.md](observability.md) for the hit/miss counters over these tiers, and [integrations.md](integrations.md) for the upstream calls they front.

## Database (`db.sqlite`)

`db.sqlite` is the application database, opened via the built-in `node:sqlite` module (`DatabaseSync`). It currently holds only cache tables, but is intentionally named `db.sqlite` (not `cache.db`) to accommodate non-cache data in the future. WAL mode is enabled for better concurrent write throughput. Cache entries are evicted at startup and lazily on read; every write goes directly to SQLite (no debounced flush). Set `DB_FILE=` (empty) in `.env` to use an in-memory database. Cache TTLs:

| Key prefix | TTL env var | Default | Reason |
|---|---|---|---|
| `resolve:` | `RESOLVE_CACHE_TTL_MINUTES` | 180 days | Steam ID resolution — essentially permanent. Not unbounded: a custom URL can be renamed and re-claimed by someone else, and no refresh path forces this tier |
| `rating:` | `RATING_CACHE_TTL_MINUTES` | 90 days | Steam review scores — drifts slowly |
| `hltb:`, `meta:`, `browse:`, `tagnames:` | `META_CACHE_TTL_MINUTES` | 180 days | Store metadata, HLTB, tags, demo link — rarely changes for an existing game |
| `games:`, `player:`, `wishlist:` | `LIBRARY_CACHE_TTL_MINUTES` | 7 days | Changes when users buy games / edit their wishlist — the UI states how old this data is ("Updated <when>", from `getCachedAt` via each route's `fetchedAt`) and offers the ↻ that forces it, so the TTL doesn't have to carry that job |
| `search:` | `SEARCH_CACHE_TTL_MINUTES` | 7 days | Game name → appid search results — the shortest metadata tier, since new games ship regularly |
| `news:` | `NEWS_CACHE_TTL_MINUTES` | 1 day | Recent news/announcements for a game — changes far more often than store metadata (patch notes, event posts) |
| `itad-bundles:`, `itad-price:` | `BUNDLES_CACHE_TTL_MINUTES` | 4 hours | IsThereAnyDeal bundle listings and per-region price lookups — the time-sensitive half (a bundle goes live/expires; a sale starts/ends), both refreshable on demand from the UI |
| `itad-shop:`, `itad-appid:`, `itad-gid:` | `ITAD_ID_CACHE_TTL_MINUTES` | 180 days | ITAD identity mappings — the Steam shop id and both directions of the gid↔appid resolution. Nothing about them is time-sensitive, so they get their own tier rather than being re-resolved every couple of hours as a side effect of sharing a table with bundle/price data |

**Every refreshable surface states how old its data is**, from the same `getCachedAt`-backed `fetchedAt` field: `/api/common-games`/`/api/wishlist` (oldest `games:`/`wishlist:` write across the slot's accounts), `POST /api/prices` (oldest `itad-price:` in the batch — a caller that chunks, like the wishlist, keeps the minimum across chunks), and `GET /api/bundles` (that page of the list; a load pulling several pages keeps the oldest). Always the *oldest* contributor, so a readout never claims data is fresher than its stalest part. `fetchGameDetails` reports one too, but the panel puts it in its ↻ button's tooltip rather than on screen — those tiers run to months, and a prominent "5 months ago" on a 2013 game whose store page genuinely hasn't changed would invite clicks that spend the app's most rate-limited upstream (`storeLimit`) re-fetching data that was already right.

**Cached misses get their own, much shorter expiry.** `setCache(key, value, { ttlMs })` overrides the group TTL for one entry (an `expires` column, `NULL` for the normal case), used wherever a *confirmed absence* is cached: `getAppDetails`' "this appid has no store page" and `resolveSteamAppIds`/`resolveItadIds`' "this game has no Steam listing" (`MISS_CACHE_TTL_MINUTES`, 1 day), and `resolveSteamId`'s "no such account" (`RESOLVE_MISS_CACHE_TTL_MINUTES`, 1 hour — a typo being retried, or a custom URL about to be registered). Caching these at all is what stops an unresolvable identifier from costing an upstream call every time it's submitted; capping their life is what stops a miss from outliving its truth by months now that the tiers around them are that long. A cached `resolve:` miss is stored as `null` and re-throws the original client error rather than being handed back as an id.

Run `npm run cache:clear` to wipe all cache entries without deleting the database file.

These TTLs are generous because both `getCached` and every `lib/steam.js`/`lib/hltb.js`/`lib/itad.js` fetch function accept `{ force: true }` to bypass the cache read for one call (the fetch still writes fresh data back to the cache). This backs three user-facing "↻ Refresh" affordances rather than being needed for background freshness:

- **Home's account card ↻** (`HomeRoute.tsx`'s `loadAccountData({ refresh: true })`) re-POSTs `/api/common-games`/`/api/wishlist` with `refresh: true`, forcing fresh owned-games/player/wishlist data for the account it shows. The routes also accept a narrower `refreshIds: [steamid, ...]` (forcing only the listed members of a Family, with `getPlayerSummaries` taking a matching `forceIds` option so one `GetPlayerSummaries` batch call bypasses the cache for just those IDs) — supported server-side, but nothing in the frontend sends it since the per-account chips it was built for went away with the legacy pages.
- The **side panel's Refresh button** re-fetches `GET /api/game-details/:appid?refresh=1`, forcing fresh rating/HLTB/store metadata/tags for that one game only, and in parallel `GET /api/game-news/:appid?refresh=1` for that game's news (see `handlePanelRefresh` in `panel.tsx`) — two separate requests since news isn't part of `fetchGameDetails` (see the panel.tsx bullet above). Both always count against their respective rate limiters (`DETAILS_RATE_LIMIT_MAX`/news's own limiter sharing that same budget) — the cache-hit skip is disabled for `refresh=1`, since a forced call never is a cache hit.
- **The list route's page-level "↻ Refresh prices" button** (wishlist and bundle kinds, next to Reset view — `ListRoute.tsx`) re-POSTs `/api/prices?refresh=1`, forcing fresh ITAD pricing for every game currently loaded. It re-sends the rows already on screen, so no re-resolution or re-streaming of ratings/HLTB/tags happens, just the one already-batched price call again. Deliberately one page-level control rather than per-game (unlike rating/HLTB/tags, which do differ enough per game to warrant the panel's own per-game refresh) — pricing is already fetched as a single batch call for the whole list, so refreshing it per-game would only add friction with no matching benefit. `force` only bypasses `itad-price:`; it deliberately does *not* force `itad-gid:`/`itad-appid:` appid↔gid resolution (see the route's own comment in `server.js`) — that mapping is closer to identity data than price data and near-permanent in practice, so forcing it on every price refresh would be an extra upstream call for nothing, same reasoning as the bullet just below about `resolve:`. `pricesLimit`'s cache-hit skip is disabled the same way for `refresh=1`.

None of the three refresh paths touch `resolve:` — a vanity-URL mapping isn't expected to change, so there's no user-facing reason to force it.
