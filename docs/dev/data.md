# Data & caching

The application database, the cache tiers over it, and the refresh paths that bypass them. Hit/miss counters: [observability.md](observability.md); the upstream calls behind each tier: [integrations.md](integrations.md).

## Database (`db.sqlite`)

- Opened with `node:sqlite` (`DatabaseSync`) in `lib/db.js`, WAL mode. `DB_FILE=` (empty) runs in memory.
- A write waits up to `DB_BUSY_TIMEOUT_MS` ([config.js](../../lib/config.js)) for another connection's lock (`cache:clear`, a second server) before throwing `database is locked`; `DatabaseSync` is synchronous, so the wait blocks the event loop.
- Holds the cache tables, `metrics_daily` (outbound status counts per day, [observability.md](observability.md#daily--daily)), plus signed-in users: `users`, `sessions` (swept of expired rows at startup) and `user_prefs` (one row per `(steamid, key)` with its `updated_at`, what lets devices merge prefs per key — [lists-and-accounts.md](lists-and-accounts.md#sync)).
- **Migrations**: `lib/db.js`'s `MIGRATIONS` is an ordered, append-only list of `{ version, up(db) }` applied against `PRAGMA user_version`. A migration only adds — never drops or rewrites a table — and is never edited once shipped; fix forward. Version 7 is the baseline; `users.prefs` (v8's blob, replaced by `user_prefs` in v9) stays unused for that reason.
- `node scripts/db-query.js "<sql>"` opens it read-only and prints rows as JSON lines; `npm run cache:clear` empties the cache tables only.

## Cache tiers

Every key prefix belongs to a group in `lib/cache.js`'s `GROUPS` (a key matching none throws). Entries are evicted at startup and lazily on read; writes go straight to SQLite. Defaults below are `default.env`'s — the one place they're set:

| Key prefix                                                                                                                    | TTL env var                 | Default  | Reason                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------------------------------------------------------------------------------------------------------------------- | --------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resolve:`                                                                                                                    | `RESOLVE_CACHE_TTL_MINUTES` | 180 days | Steam ID resolution — essentially permanent. Not unbounded: a custom URL can be renamed and re-claimed by someone else, and no refresh path forces this tier                                                                                                                                                                                                                                                                             |
| `rating:`                                                                                                                     | `RATING_CACHE_TTL_MINUTES`  | 365 days | Steam review scores — drifts slowly, forceable via the panel's ↻                                                                                                                                                                                                                                                                                                                                                                         |
| `hltb:`, `meta:`, `browse:`, `tagnames:`, `protondb:`, `schema:`, `achrarity:`, `steampkg:`, `steambundle:`, `msstore-title:` | `META_CACHE_TTL_MINUTES`    | 365 days | Store metadata, HLTB, tags, demo link, ProtonDB, achievement schema/rarity, Steam package/bundle contents, Microsoft Store product titles — rarely changes for an existing game, forceable via the panel's ↻ (except `tagnames:`, `steampkg:`, `steambundle:`, `msstore-title:`)                                                                                                                                                         |
| `games:`, `player:`, `wishlist:`, `friends:`, `playerach:`                                                                    | `LIBRARY_CACHE_TTL_MINUTES` | 30 days  | Changes when users buy games / edit their wishlist / add friends / unlock achievements — the UI states how old this data is ("Updated <when>", from `getCachedAt` via each route's `fetchedAt`) and offers the ↻ that forces it, so the TTL doesn't have to carry that job                                                                                                                                                               |
| `search:`, `creator:`                                                                                                         | `SEARCH_CACHE_TTL_MINUTES`  | 7 days   | Game name → appid search results, a developer's/publisher's games — the shortest metadata tier, since new games ship regularly; only `creator:` is forceable                                                                                                                                                                                                                                                                             |
| `news:`                                                                                                                       | `NEWS_CACHE_TTL_MINUTES`    | 1 day    | Recent news/announcements for a game — changes far more often than store metadata (patch notes, event posts)                                                                                                                                                                                                                                                                                                                             |
| `itad-bundles:`, `itad-gamebundles:`, `itad-price:`, `fanatical-pnm:`, `gamepass:`                                            | `BUNDLES_CACHE_TTL_MINUTES` | 12 hours | IsThereAnyDeal bundle listings and per-region price lookups, Fanatical's pick-and-mix tiers, and the per-market PC Game Pass catalog — the time-sensitive half (a bundle goes live/expires; a sale starts/ends), the ITAD ones refreshable on demand from the UI. `fanatical-pnm:` has no force path; instead a map older than 1 h is re-fetched when a requested slug is missing from it, and a failed fetch keeps the last map for 1 h |
| `itad-shop:`, `itad-appid:`, `itad-gid:`                                                                                      | `ITAD_ID_CACHE_TTL_MINUTES` | 365 days | ITAD identity mappings — the Steam shop id and both directions of the gid↔appid resolution. Nothing about them is time-sensitive and there's no force-refresh path, so they get the longest tier in the app rather than being re-resolved every couple of hours as a side effect of sharing a table with bundle/price data                                                                                                               |

**Every refreshable surface states its age**, from a `getCachedAt`-backed `fetchedAt`, always the _oldest_ contributor so a readout never claims fresher data than its stalest part: `/api/common-games`/`/api/wishlist` (across the slot's accounts), `POST /api/prices` (across the batch; a chunking caller keeps the minimum), `GET /api/bundles` (a multi-page load keeps the oldest). `fetchGameDetails`' age goes in the panel's ↻ button, with per-source ages in its tooltip.

**Confirmed absences get a short expiry** (`setCache(key, value, { ttlMs })`, the `expires` column), so a miss neither costs an upstream call per request nor outlives its truth by months:

- `MISS_CACHE_TTL_MINUTES`: no store page (`getAppDetails`), no Steam listing (`resolveSteamAppIds`/`resolveItadIds`), no achievement schema or rarity (a 403 on both, typical of an unreleased game), an HLTB lookup skipped by design (a non-played type, or no name — cached so ↻ can date it and the details limiter counts it as cached).
- `RESOLVE_MISS_CACHE_TTL_MINUTES`: `resolveSteamId`'s "no such account" (a typo being retried, a custom URL about to be registered). Stored as `null`; re-throws the original client error.
- An unreleased game (`coming_soon`) gets the miss expiry for its store page and any empty rating, ProtonDB or HLTB result (`capExpiry`, from `fetchGameDetails`); a released game's empty results keep their tier.

## Refresh paths

`getCached` and the fetch functions behind a refresh path below accept `{ force: true }`: skip the cache read, still write the fresh value back. That's what lets the tiers be long — each user-facing refresh is the readout that states the age ([frontend.md](frontend.md#each-list-kind-in-practice)). A forced request always counts against its route's rate limiter (the cache-hit skip is off for `refresh=1`).

- **Home's account card** (`HomeRoute.tsx`'s `loadAccountData({ refresh: true })`) — re-POSTs `/api/common-games`/`/api/wishlist` with `refresh: true`.
- **A list's Updated tile** (owned, wishlist, and any list built from an account fetch or a developer/publisher at any depth: compare, dynamic, ranked, a shared formula — `ListRoute.tsx`'s `handleRefreshList`) — the same, for _every_ account the list resolves through, and `GET /api/creator-games?refresh=1` for every developer/publisher (`listResolve.ts`'s `createDefaultFetchers({ refresh })`).
- **The Prices tile's age** (wishlist, bundle, developer/publisher and lists built from them) — re-POSTs the rows on screen to `/api/prices?refresh=1`. One control per list, since prices are fetched as one batch. Forces `itad-price:` only, not the near-permanent gid↔appid mappings.
- **The panel's ↻** — `GET /api/game-details/:appid?refresh=1` plus news, achievements, the game's bundles and the price (only when the panel priced the game itself; a list-priced game refreshes from the list's Prices tile, which the tooltip says).
- **The friends list's ↻** (`AccountFriends.tsx`) — `/api/friends` with `refresh: true` (`info.refetching` as force, like the panel's resources).
- **A developer/publisher list's Updated tile** — `GET /api/creator-games?refresh=1`.
- **The PC Game Pass list's Updated tile** — `GET /api/game-pass?refresh=1` (forces the catalog and its ITAD lookup, not the gid→appid mappings or product titles).
- **`/bundles`' Updated tile** — `GET /api/bundles?refresh=1`. A single bundle (`GET /api/bundles/:id`) has none: finding it walks up to `BUNDLE_SEARCH_MAX_PAGES` pages, so its hero states the age without forcing it.

No path forces `resolve:`, `search:`, `tagnames:`, `steampkg:`, `steambundle:`, `msstore-title:`, `fanatical-pnm:` or the ITAD id tier: a vanity-URL mapping, the tag names and a package's contents aren't expected to change, search results simply age out, and the Fanatical feed has its own refetch rule (above). The panel's ↻ skips DLC: forcing it would cost one store lookup per DLC.
