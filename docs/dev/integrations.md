## HLTB — no npm package

The `howlongtobeat` npm package was removed (it pulled in a vulnerable `axios`). HLTB is called directly with a two-step auth flow:

1. `GET https://howlongtobeat.com/api/search/site/init?t={ms}` → returns `{ token, hpKey, hpVal }`
2. `POST https://howlongtobeat.com/api/search/site` with `X-Auth-Token`, `X-Hp-Key`, `X-Hp-Val` headers and `{ [hpKey]: hpVal, ...payload }` in the body

(Previously `api/bleed/init` and `api/bleed` — HLTB renamed these endpoints; the `howlongtobeat-ts` npm package's source is what surfaced the new paths when the old ones started 404ing.)

The token is cached in memory for 5 minutes (not on disk — it's session-bound). A 401/403 from the search endpoint clears the cache so the next call re-fetches. Match quality is checked via Levenshtein similarity; results below 0.35 are discarded.

`pickBestMatch` extracts four times from the matched entry's raw fields (all in seconds, converted to hours rounded to the nearest half hour — the same granularity HLTB's own site displays, e.g. "2½ Hours" — rather than a whole hour, which would silently discard that precision): `main` (`comp_main`), `extra` (`comp_plus`), `completionist` (`comp_100`), and `all` (`comp_all`) — HLTB's "All PlayStyles" figure. `all` is **not** an average of the other three — it's the average of every individual completion-time submission pooled together regardless of category, weighted by how many people submitted each one (`comp_all_count` equals `comp_main_count + comp_plus_count + comp_100_count`). Since far more players report a Main Story time than a Completionist one, it usually lands much closer to Main Story than to the simple midpoint of all three. It's the default-displayed HLTB column in the game table (`hltbAll`, "All (h)") and shown first (leftmost) in the side panel's How Long To Beat section as "All PlayStyles", precisely because it's a single representative number rather than one specific playstyle.

If HLTB breaks again, recent npm packages (e.g. `howlongtobeat-ts`) tend to reverse-engineer the new flow quickly and are a good first place to look.

**Compliance note:** `/api/search/site` is an undocumented, internal HLTB endpoint reached with spoofed browser `User-Agent`/`Referer` headers — this is not a published public API and isn't guaranteed to be sanctioned by HLTB's terms of service. Usage here is low-volume and non-commercial, but treat it as liable to break or be blocked without notice, and don't scale up request volume without revisiting this.

## Wishlist — undocumented endpoint

`getWishlist` calls `https://api.steampowered.com/IWishlistService/GetWishlist/v1/?steamid={id}`, which is not listed in Valve's published Web API docs (same unofficial-endpoint situation as HLTB above, though no spoofed headers are needed here — it works with a plain request). A private wishlist, a private profile, and a genuinely empty wishlist are all indistinguishable: each returns `200 OK` with `{"response":{}}` (no `items` key). The app treats a missing `items` key as an empty wishlist rather than surfacing an error, since there's no way to tell those cases apart.

## Tags & demo link — Steam's own store browse data, not SteamSpy

`getSteamTags` (`lib/steam.js`) fetches the same user tags shown on a game's own Steam store page (and, downstream of that, SteamDB and IsThereAnyDeal) rather than SteamSpy's separate crowd-voted dataset, which this used to pull from and which can be sparse or empty for a game Steam itself has plenty of tag data for — especially anything niche or too recent for SteamSpy's own community to have caught up on. Two undocumented, key-less endpoints (same trust tier as the other endpoints covered by this compliance note) stand in for it:

- `https://api.steampowered.com/IStoreBrowseService/GetItems/v1/?input_json={"ids":[{"appid":N}],"context":{"language":"english","country_code":"US"},"data_request":{"include_tag_count":30}}` returns that one app's whole "store browse item" — `tagids` (already ordered by relevance weight descending, the same order the store page itself displays them in — all returned tagids are shown, no further display cap on top of this) plus other fields riding along on the same response for free. `getGameDemo` reads one of those: `related_items.demo_appid`, the appid of the game's free demo if it has one, surfaced in the side panel as a standalone "🎮 Try the Free Demo" banner (`public/panel.tsx`'s `demoBannerHtml`) right under the sticky header — deliberately not folded into the "⋯ More" icon menu alongside Website/Workshop, since a demo is a call to action worth surfacing without an extra click, unlike those two which are just supplementary info. The **whole raw item** is cached (`browse:{appid}`, not just the extracted tagids) — the usual "cache raw, extract at read time" approach used everywhere else in this file (see the cache-table intro above) — specifically so that adding another field this same call already returns, like the demo link, never needs a new upstream request, just a new extractor over the already-cached response. `getSteamTags` and `getGameDemo` share one upstream fetch per appid this way, via the same cache entry plus the usual in-flight dedup.
- `https://store.steampowered.com/actions/ajaxgetstoretags?l=english` maps every tagid to its human-readable name — a single, near-static ~430-entry list, not per-game, so it's fetched once and cached long-term (`tagnames:all`, same 60-day `META_CACHE_TTL_MINUTES` group as `browse:` — see the cache table above) rather than repeated for every game lookup.

The `browse:` cache key is the third one used for this data — `tags:` (SteamSpy's `{tagname: voteCount}` object) then briefly `tagids:` (a bare `tagid[]`) came before it. Each format change got a new key rather than reusing the old one: a shape check alone can't safely tell an old value apart from a new one when both can legitimately be the same JS type (e.g. a game with zero SteamSpy votes cached a bare `[]`, indistinguishable from an empty `tagid[]` result). Retired-key entries are simply never read again and age out on their own via the existing TTL sweep.

## Looking up an arbitrary game

The nav bar has a "look up any game" search box (`public/gameSearch.ts`, mounted once by `AppShell.tsx`) for previewing a game in the shared side panel regardless of whether anyone in the current search owns or has wishlisted it — see the "Ratings" and "HLTB" sections above for what that panel shows. `GET /api/game-details/:appid` has no ownership check at all (it already has to work for wishlist items, which aren't "owned" either), so the only missing piece was turning a typed name into an appid.

Opening a looked-up game writes `?game=<appid>` to the current list route's URL (and, within it, `&shot=<idx>` for an open lightbox screenshot/video); `/game/:appid` is the canonical shareable address for a game on its own. Either link reopens the game once the app loads, falling back to fetching the appid directly if it isn't part of whatever list is currently loaded. Looked-up games are remembered by `public/recentGames.ts` and browsable as the "Recently Looked Up" system list at `/game` — see [frontend.md](frontend.md).

`GET /api/game-details/:appid` never accepts or trusts a client-supplied name — it always resolves the game's name itself from store metadata (`getAppDetails(appid)`), the same appid-keyed source used for everything else about the game, and searches HLTB using that resolved name. A name picked from the search dropdown (or carried on a standalone-lookup row) exists purely client-side, to avoid a title flash in the panel while the fetch is in flight — it's never sent to the server or written to the URL. The cost is that HLTB search always waits for store metadata to resolve first, rather than starting in parallel using an already-known name (e.g. an owned game's name from Steam's library API) — a deliberate trade against treating any client-provided string as ground truth on a public, key-less, ownership-free endpoint.

`GET /api/search-games?q=<term>` (`searchStoreGames` in `lib/steam.js`) wraps `store.steampowered.com/api/storesearch/?term=...&l=english&cc=US` — the same undocumented endpoint Steam's own store search box uses, no key or auth required. Same trust tier as the HLTB/wishlist endpoints documented elsewhere in this file: not a published API, not guaranteed to be sanctioned by Steam's terms, liable to break or be blocked without notice. Usage here is low-volume (client-side debounced, and each distinct term only costs one upstream call — repeats hit the `search:` cache tier) and non-commercial; don't scale up request volume without revisiting this note. A bare appid or a pasted store URL (`store.steampowered.com/app/<id>/...`) typed into the box bypasses this endpoint entirely and goes straight to `/api/game-details`.

## IsThereAnyDeal

Bundle browsing (`/bundles`, `/lists/bundle/:bundleId`) and every price column in the app are backed by the [IsThereAnyDeal API](https://docs.isthereanydeal.com/) via `lib/itad.js` — a free, key-gated API with published (if sparse) OpenAPI docs, a distinct trust tier from the undocumented Steam/HLTB endpoints above. Entirely optional: gated behind `ITAD_API_KEY` (`.env`), which is not required for the rest of the app to run. `server.js`'s `isItadConfigured()` checks it per-request; `GET /api/bundles`/`POST /api/bundles/resolve`/`POST /api/prices` return 503 when unset, and the frontend hides the bundle/price surfaces instead of showing a feature that isn't running (`GET /api/health`'s `itadConfigured` field drives that check).

- **`GET /bundles/v1`** (wrapped by `getBundles` / `GET /api/bundles`) lists current bundles, paginated (`offset`/`limit`, max 50/page), with a `country` param that drives both currency and (per ITAD, presumably regional storefront) pricing. `mature=true` is sent unconditionally — it's ITAD's *include* switch, not an "only mature" filter, and this app never hides a bundle from whoever's browsing (no age gate exists anywhere here, and mature games get no special treatment in any other list). It's deliberately not a parameter: it used to default to `false` with nothing anywhere overriding it, which read like a content policy but was an unexercised default, and cost real bundles — measured live, 33 of 35 active ones, hiding an ordinary Humble narrative-games bundle none of whose games carried ITAD's own per-game `mature` flag. `findBundleById` inherits it too, so a deep link to a mature-flagged bundle resolves rather than 404ing. There is no single-bundle-fetch endpoint upstream, so `?bundle=<id>` deep linking (same idea as `?game=`/`?u=` elsewhere) is backed by a bounded server-side search instead: `findBundleById` (`lib/itad.js` / `GET /api/bundles/:id`) pages through `GET /bundles/v1` — active bundles first (`expired=false`), then expired — up to `BUNDLE_SEARCH_MAX_PAGES` (6) pages of 50 each per expired-state, and 404s rather than searching indefinitely if the id never turns up (very old/deleted bundle, or a bad id). Each page it fetches reuses `getBundles`' own per-page cache, so a second deep link into a bundle on an already-searched page costs no extra upstream call. `fetchBundle` (`public/bundleData.ts`) always goes straight to this route when `/lists/bundle/:bundleId` opens, rather than checking whatever the `/bundles` picker happens to have loaded — that list may be a different sort/page, or not loaded at all. The bundle id is a path segment now, not a `?bundle=` param, so a 404 is the route's own not-found state rather than something to strip back out of the URL.
- Each bundle's `tiers[]` lists the games unlocked at that price tier; a game can appear in more than one tier (a cheap tier's games are still included in every pricier tier above it) — `flattenBundleGames` (`public/bundleData.ts`) dedupes by ITAD game id, keeping the cheapest tier's price, since ITAD's tiers are observed to always be price-ascending.
- Bundle games carry no Steam appid directly — only an ITAD-internal id (uuid), slug, and title. Resolving to Steam is a separate step: `resolveSteamAppIds` (`lib/itad.js`) first resolves ITAD's numeric shop id for Steam via `GET /service/shops/v1` (cached under `itad-shop:steam`, effectively permanent), then batches the bundle's game ids through `POST /lookup/shop/{shopId}/id/v1` (`POST /api/bundles/resolve` on this app's side) — **not** the more RPC-shaped `/lookup/{shopId}/gid/v1` path the sibling lookup endpoints' naming might suggest; the real path follows ITAD's own `/lookup/{lookup-what}/{by-what}/` convention and was confirmed against the live API, not just the docs. The response namespaces each shop id as `"app/<id>"` (a store page) or `"sub/<id>"` (a package/bundle sub, not a single game page) — only an `"app/"` entry resolves to something `GET /api/game-details/:appid` can look up; a game listed only as a `"sub"` resolves to `null`, same as no Steam listing at all. Each ITAD game id's resolution is cached individually (`itad-appid:{gid}`) so a game seen in one bundle is never re-resolved for another.
- **`POST /games/prices/v3`** (wrapped by `getPrices`/`extractPriceInfo` in `lib/itad.js`, `POST /api/prices` on this app's side) supplies the pricing columns — batched separately from `resolveSteamAppIds` above since it needs `country` (prices are region-specific; appid resolution isn't) and returns, per ITAD game id, `historyLow.{all,y1,m3}` (the lowest price seen across every shop ITAD tracks — not Steam-specific; "have I ever seen this cheaper anywhere" is the more useful question than a Steam-only low) plus a `deals[]` array with each shop's current `price`/`regular`/`cut`/`url` (ITAD's own affiliate/redirect link for that specific deal). `extractPriceInfo` reads this array twice: once for the `deals[]` entry whose `shop.id` matches the Steam shop id (from `getSteamShopId`), returning its `regular` (Steam's own non-discounted price), and once scanning every entry for the lowest `price.amount` regardless of shop (`bestDeal: {price, shop, url}` — `url` exists purely so the side panel's Price card, see `panel.tsx`'s own bullet above, can link straight to the shop; passed through unmodified, same as every other ITAD-sourced link/price in this app) — every entry in one response is already in the same requested `country`'s currency, so they're directly comparable with no conversion needed. Both this call and `resolveSteamAppIds`'s lookup run for a bundle's games concurrently with the `game-details/stream` fetch (`Promise.all` in `openBundle`) — pricing has nothing to do with ratings/HLTB/tags, so there's no reason to sequence them. Cached per `(gid, country)` (`itad-price:{country}:{gid}`), unlike the appid resolution above which only needs to be resolved once ever — a price is meaningfully different per region, not just a currency relabeling. Best Deal and Discount are visible by default (answers "is this bundle actually a good deal, and where's it cheapest right now" at a glance); Steam Full Price (named that way, not the shorter "Steam Price", specifically to make clear it's the non-discounted list price), All-Time Low, Best Deal Shop, and 1yr Low/3mo Low are hidden by default, same "secondary number" convention as Wilson Score/Steam %/Achievements elsewhere in this column set — Steam Full Price and All-Time Low specifically because Best Deal + Discount together already answer "is this a good deal, and by how much" for the common case, not because the exact numbers stopped being useful. A bundle tier's own price (`tierPrice`/`tierCurrency` on each row) can be `null` for a free/pay-what-you-want-or-more tier.
  - **Discount is its own column (`bestDealCut`), not a percentage folded into the Best Deal cell — and it's computed against Steam Full Price, not taken from ITAD's own per-deal `cut` field.** `cut` (an integer percentage ITAD does return per deal, e.g. `70` for 70% off) is that shop's own discount off *its own* regular price — a number shops set independently and don't compute consistently with each other, so it means something different from row to row (whatever that particular shop happens to list). `discountPct(bestDealAmt, steamRegularAmt)` (`public/gameColumns.ts`, one shared definition for every game table) computes `1 - bestDeal/steamRegular` instead, so every row's Discount answers the same question against the one stable, Valve-set anchor this app already treats as the reference price throughout (the same reasoning that keeps Steam Full Price around as its own column at all). Safe to compute without clamping: Best Deal is defined as the cheapest price across *every* shop including Steam, so `bestDealAmt <= steamRegularAmt` always holds. `extractPriceInfo` (`lib/itad.js`) deliberately does *not* surface `cut` at all, for exactly this reason. `renderCut` renders `0` (the best deal genuinely isn't any cheaper than Steam) the same as "—" — a flat "0%" would read as noise next to every other row's real discount, and nothing else in this column set treats a confirmed zero differently from "nothing to show" either.
  - **`POST /api/prices` is one shared route for the bundle and wishlist list kinds**, not two near-identical ones — the actual pricing operation (resolve to an ITAD gid if needed, then `getPrices`/`extractPriceInfo`) is identical either way; only the identifier space the caller already has differs. A bundle list passes `gids` (it already has ITAD gids off a bundle's own `tiers[].games[].id`); a wishlist passes `appids` instead (a wishlist row only has a Steam appid) and the route resolves those to gids internally first via `resolveItadIds` (`lib/itad.js`) — the reverse direction of `resolveSteamAppIds` above, via `POST /lookup/id/shop/{shopId}/v1` (confirmed against the live API: takes `["app/<appid>", ...]`, returns `{"app/<appid>": "<uuid>"|null, ...}`, keyed by exactly what was sent). That reverse resolution isn't exposed as its own route the way `/api/bundles/resolve`'s gid→appid mapping is — nothing needs the raw gid itself, unlike Bundles' own "which of these games have no Steam listing at all" list. Each appid's resolution is cached individually (`itad-gid:{appid}`, same `cache_bundles` tier as `itad-appid:` — see the Database section below), same "confirmed miss cached the same as a real mapping" treatment as `resolveSteamAppIds`. Exactly one of `gids`/`appids` must be provided; the route 400s on both-or-neither. See [frontend.md](frontend.md) for how each list kind loads and renders these.
  - **`tierCurrency` and `priceCurrency` are deliberately two separate fields on a row, not one shared `currency`.** An earlier version had one shared field, populated first from whichever value arrived first and never overwritten — this was a real bug, confirmed live: a bundle's own tier price can come back from ITAD in USD only regardless of requested `country` (same "this shop doesn't offer this region's currency" situation as bundle-level pricing generally — see the region-selection bullet below), while that *same* bundle's games' Steam/other-shop prices, a separate upstream call, correctly come back in the requested currency. With one shared field, whichever request resolved first "won" and silently mislabeled the other's amounts with the wrong currency symbol (right number, wrong label — easy to miss). `tierCurrency` (from the bundle's own tier data) backs only the Tier Price column; `priceCurrency` (from `loadPrices`, always set unconditionally from that response — never conditionally backfilled) backs the other five price columns. `formatMoney(v, currency)` (`public/utils.ts` — see its own file-listing bullet above for why it lives there rather than in `gameColumns.ts` alongside the rest of this logic) is the shared low-level formatter both `renderPrice` (`gameColumns.ts`) and `renderTierPrice` (`ListRoute.tsx`, bundle-specific) call with the correct field for their own column, rather than each reimplementing `Intl.NumberFormat` against a shared field.
- A bundle tier's `price` can be `null` even when the tier lists real games — this is **not** the same as free. In practice this is Fanatical's "Build Your Own ⟨N⟩ Bundle" pick-and-mix format: one tier, a pool of 15-30 games, price scales with however many you pick rather than being a fixed property of the bundle. A genuinely free/pay-what-you-want-or-more tier would carry an explicit `{amount: 0, ...}` price object instead (truthy, so it's grouped with priced tiers, not with the `null` case) — never observed in practice as of writing, but the correct thing to special-case if ITAD ever sends one. `cheapestTierPrice`/`fmtBundleListPrice` (bundle list) and `renderTierPrice`/the `tierPrice` column's own `format` (game table) both render `null` as "Varies"/"Price varies", reserving "Free" for an actual `amount === 0`. The `tierPrice` column also needs `compare: compareNumMissingLast` for this same reason — without it, `null` coerces to `0` under the column's default numeric comparator, which would sort every "Build Your Own" bundle's games as the single cheapest thing in the table under the default ascending Tier Price sort.
- An opened bundle shows two outbound links (`ListRoute.tsx`'s hero card): "View on IsThereAnyDeal ↗" (the bundle's `details` field, ITAD's own page for it) and "Get this bundle ↗" (`url`, the real shop/affiliate purchase link exactly as ITAD returned it — never rewritten or stripped of tracking params; ITAD's terms require passing prices/links through unmodified, same as the compliance note on the other third-party integrations in this file).
- Bundle listings, Steam-appid resolutions, and per-region price lookups share one cache tier (`BUNDLES_CACHE_TTL_MINUTES`, default 2 hours — see the Database section below) rather than each getting its own: a bundle can go live or expire at any time (shorter-lived than store metadata), while the appid mapping itself is closer to permanent, but it's cheap to over-invalidate the latter two in exchange for one fewer cache table.
- `BUNDLES_RATE_LIMIT_MAX` backs 4 separate `rateLimit()` instances (`bundlesListLimit`/`bundlesByIdLimit`/`bundlesResolveLimit`/`pricesLimit`), not one shared limiter — each `skip`s a request it can answer entirely from cache, by reconstructing that route's own cache key from the request and checking `getCached` directly (same "cache hits don't count" pattern `detailsLimit`/`gameSearchLimit`/`achievementsLimit` already use elsewhere in `server.js`). `pricesLimit` (named generically, not `bundlesPricesLimit` — see the shared-route bullet above) branches its `skip` on whichever of `gids`/`appids` the request actually sent, checking `itad-price:`'s cache key either way plus `itad-gid:` too for the `appids` case, since that route resolves appids to gids as its own internal step. This matters more here than it might look: simply reloading a bundle route a handful of times re-requests the list and re-opens that bundle every time, and without the skip, every one of those re-requests — even though none of them touch ITAD — counted against the same budget a genuinely new bundle open needs, silently 429ing it with no obvious cause. `bundlesByIdLimit` (`GET /api/bundles/:id`) is the one exception — `findBundleById`'s search walks a variable number of pages depending on where the id turns up, so there's no single cache key to check in advance; it gets a looser budget (`BUNDLES_RATE_LIMIT_MAX * 2`) instead of a skip, on the reasoning that deep links are a comparatively rare action next to list browsing, and the pages it walks are still individually cached underneath via `getBundles`.
- A failed `POST /api/prices` call (rate limited, transient upstream error) does not leave the Steam Price/All-Time Low/1yr Low/3mo Low columns stuck on `undefined` (rendered as "…", indistinguishable from "still loading") forever — `loadBundlePrices`'s catch block (`ListRoute.tsx`) sets every resolved row's price fields to `null` (rendered "—", same as any other "no data" case) and writes a visible explanation to `#price-status`, a dedicated status line kept separate from `#detail-status` (which `streamGameDetails`'s own progress messages would otherwise overwrite). `loadWishlistPrices` does the same for a wishlist.

### Currency is passed through, not converted

**Not every bundle actually follows it** — the currency on a tier/game price is whatever ITAD's upstream shop itself charges in, passed straight through; most shops (Humble, GreenManGaming, most Fanatical bundles) do switch currency per region, but some (verified live: a shop ITAD lists as "Digiphile", and at least one specific Fanatical bundle) only ever price in USD regardless of `country` — this is genuine upstream behavior, not a bug to "fix" by converting currencies client-side, and the page has a note next to the region picker explaining it.

### Price lookups from a Steam appid

**A wishlist row only has a Steam appid, not an ITAD game id** — the reverse of a bundle's own games, which start as ITAD gids and get resolved *to* a Steam appid (`resolveSteamAppIds`, `/api/bundles/resolve`). `loadWishlistPrices` (`ListRoute.tsx`) instead calls the shared `POST /api/prices` with `appids` (see the shared-route bullet above), which resolves them to gids server-side first via `resolveItadIds` before running the identical price lookup — so a wishlist never sees a raw ITAD gid.

**Chunked client-side into batches of `MAX_PRICE_LOOKUP_GAMES` (500, mirroring the server's own cap)**, run sequentially rather than in parallel — unlike a bundle's game list (which never exceeds the cap, so `loadBundlePrices` always sends everything in one call), a Steam wishlist can run well past it, and firing several chunks at once would just be several concurrent ITAD-backed requests for no benefit.
