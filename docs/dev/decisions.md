# Computed values & heuristics

Numbers this app derives itself rather than reading off an upstream, and the reasoning behind each. All of them are columns in the shared game-table column set (`public/gameColumns.ts`) and/or lines in the side panel — see [frontend.md](frontend.md).

## Ratings — Wilson score vs. Weighted Rating

The hidden-by-default "Wilson Score" column shows the **Wilson score lower bound** at 95% confidence, computed server-side in `getGameRating`/`computeRating` from Steam's own review counts (`store.steampowered.com/appreviews/:appid`). Do not replace it with a simple positive/total ratio — that's exactly the naive approach the Wilson bound is meant to avoid, since it lets a game with 2 positive reviews outrank one with 50,000 mostly-positive reviews. (SteamDB itself used to use this same formula but has since switched to a different one — see below — so don't assume parity with what SteamDB currently shows.)

Client-side, from the same `rating.positive`/`.total` numbers already delivered to the frontend (no extra backend calls), `computeSteamdbRating(positive, total)` in `public/utils.ts` computes a formula adapted from SteamDB's current one instead: `p − (p − 0.5) × 2^(−k × log₁₀(n + 1))` where `p = positive/total`, `n = total reviews`, and `k` is `STEAMDB_RATING_SHRINK_STRENGTH`. A Bayesian shrinkage toward a neutral 50% prior that fades as review volume grows. SteamDB's own published formula is `k = 1` (their worked example: 90% positive over 100 reviews lands at 80%); this app runs hotter, at `k = 2`, so it converges to the raw ratio faster (the same 90%/100-review example lands at ~87-88% here) — a deliberate app-specific tuning choice, not a claim about what SteamDB itself currently shows. Whatever `k` is, the result is mathematically guaranteed to stay between 50 and `p`, moving monotonically closer to `p` as `n` grows — it can never overshoot past `p`. SteamDB moved to this general shape from the Wilson interval specifically because it's easier to explain to users; see [steamdb.info-issues#793](https://github.com/SteamDatabase/steamdb.info-issues/issues/793). It returns the **raw, unrounded** value — round only for display; the Weighted Rating column sorts on the unrounded number so otherwise-tied displayed integers still order deterministically, and isn't groupable (grouping keys off the raw value, which would otherwise split into a near-useless one-row-per-group table). The internal function/field/URL-param name (`computeSteamdbRating`, the `steamdbRating` row key, `?sort=steamdbRating`) is left as-is rather than renamed alongside the label — renaming it would silently break any already-shared library URL with that in its `sort`/`view` param, for a purely internal identifier no user ever sees.

This one function backs two different, intentionally-asymmetric surfaces:

- **The game table** — "Weighted Rating" is the default-visible, default-sorted score column; "Wilson Score" and "Steam %" (the raw, unadjusted ratio) both exist too, hidden by default.
- **Game detail side panel** (`public/panel.tsx`, shared by every route) — shows only the Weighted Rating (labeled just "Weighted", linking to the game's Steam reviews, since the number/caption is this app's own weighted rating, not SteamDB's) plus a compact reviews line (e.g. "99% positive of 465k reviews"), no Wilson score and no Steam review-summary text tier (e.g. "Very Positive"). So a table showing the Wilson Score column and the panel beside it intentionally report two different numbers for the same game — expected, not a bug.

## Production Tier — a heuristic, not Steam-provided data

Steam's API has no field for a game's budget or studio size, so the "Production Tier (est.)" column (hidden by default) is a best-effort AAA/AA/Indie guess, computed client-side by `computeProductionTier` in `public/utils.ts` from three signals already delivered to the frontend for every row: `meta.isFree`/`meta.priceInitial` (the undiscounted launch price in cents, USD — new fields on `extractAppDetails` in `lib/steam.js`, backed by the same appdetails response already fetched for everything else about the game; `getAppDetails`'s upstream fetch now pins `cc=us` specifically so this price is always USD regardless of the server's own geolocation), `rating.total` (review count, a reach proxy) and whether a Metacritic entry exists at all (professional press coverage tends to skip most indie releases). Deliberately **no publisher/developer allowlist** — that would be the single strongest signal (works before any reviews accumulate, survives sales, survives free-to-play) but requires externally maintained, ever-drifting knowledge Steam's API doesn't provide (legal-entity name variants, acquisitions, studio spin-offs); the heuristic stays entirely self-updating from Steam's own data instead, at the cost of accuracy in exactly the cases only a publisher list would catch.

Decision order: DLC/expansion appids (`meta.fullgame` set) and Steam's other non-game content types (`meta.type` being `dlc`/`demo`/`music`/`video`/`series`/`episode`/`mod`/`hardware`/`advertising` — see the "Type" column in `gameColumns.ts`) return `null` outright rather than being scored on their own price — a cheap DLC attached to a AAA base game would otherwise misclassify as Indie, and no parent-game lookup is attempted to avoid an extra fetch just for this. Free-to-play games have no price signal at all, so they're judged on review volume alone against a deliberately high bar (200k+) — the only lever available. Priced games ≥$50 are "AAA"; $20–$50 is the AA/premium-indie overlap zone, requiring either 20k+ reviews or a Metacritic entry to clear "AA" rather than fall to "Indie"; below $20 is always "Indie" regardless of review count (this is where breakout indie hits with huge review counts — Vampire Survivors, Stardew Valley, Terraria — correctly stay classified as Indie rather than reading as AAA). Known, accepted misclassifications with no data-side fix: cheap rereleases/remasters of old AAA IP, prestige-priced niche sim/strategy games from small studios, and veteran-founded small studios shipping a low-budget but polished game. This is why the column label spells out "(est.)" rather than presenting the value as fact.
